# 领域设计文档

## 角色与依据

本技能把 [core-principle](../core-principle/SKILL.md) 的核心认知要求落成领域设计文档的七维结构、内容判据、职责归属和交付检查；十维到七维的对应见下节，本技能不另立一套标准。产品事实与定义来自[核心认知](../../../_task/system-design/spec/核心认知.md)，写作遵循[沟通与写作](../../../standard/沟通与写作-20260917-194638.md)，目录、命名与审批遵循[_task/system-design 规则](../../../_task/system-design/AGENTS.md)，领域入口与编写规范遵循 [Domain 入口](../../../_task/system-design/spec/domain/README.md)。

核心认知自身的章节骨架见 [core-principle 的核心认知模版](../core-principle/references/core-cognition-template.md)；需要新建或重写核心认知时按该模版执行，本技能只负责下游领域文档。

领域设计回答一个问题：**这个上下文按什么理由存在、怎么组织、做什么、和谁怎么连、靠什么识别、如何变化、边界在哪。**

## 唯一认知标准

七维是七个认知问题，定义只有一个来源：核心认知。

| 维度 | core-principle 对应项 | 认知问题 | 本文写 | 引用核心认知 |
| --- | --- | --- | --- | --- |
| 目的 | 目标 | 为什么存在、投入多少 | 职责依据、子域类型引用、支撑的产品目标、不追求什么 | §5.1、§5.1.1、§5.4、§3 |
| 结构 | 结构、实体 | 内部怎么组织 | 聚合归属、稳定内核与可扩展点、编号缺口 | §7 实体与属性、§5.1 |
| 功能 | 功能 | 做什么 | 用例编排、领域服务、发布的命令与查询、失败分支 | §6 功能编号、§7.11 事件 |
| 关系 | 关系 | 谁依赖谁 | 聚合内依附、聚合间 ID 引用、上下文映射模式、依赖方向 | §8 关系编号、§5.2 |
| 属性 | 属性、术语 | 如何识别 | 识别方式核对、术语唯一性、业务唯一约束归属 | §2 术语、§7 属性编号 |
| 状态 | 状态 | 如何变化 | 迁移驱动、保护的不变量、发布的事件 | §9 状态与图、§4 全局不变量 |
| 边界 | 界限 | 范围到哪 | 上下文边界、聚合边界与事务边界、团队边界、不做什么 | §5.1.2 限界上下文、§10 界限、上下文映射 |

`术语` 并入属性，`实体` 并入结构，`参考文档&引用` 落到文末依据段与定义引用表，其余一一对应。

判定方法：一段文字如果回答的是「是什么、有哪些字段、状态叫什么」，它属于核心认知，本文改成引用。如果回答的是「为什么这样、谁来执行、失败怎么办、范围到哪」，它属于本文。

## 七维写法

### 一、目的

先引职责依据：核心认知 §5.1 的模块职责、§5.1.1 的子域类型与编号（`SD-01~12`）、§5.4 的支撑能力责任。子域类型直接引用编号，不在本文重新判定，也不另立分类标准。

类型判定与投入方式以 §5.1.1 为准：核心域建深模型，支撑域做到够用，通用域优先复用。类型变化的结论先改核心认知，再改本文。本上下文在 §5.1.1 尚无编号时登记待确认项并写明拥有方。

再写三件事：本上下文支撑哪个产品目标、投入深度到什么程度、明确不追求什么。

判据：核心域能指出去掉它会消失的用户能力；支撑域与通用域能指出它支撑哪个核心域用例、为何不自研。

### 二、结构

列出上下文内的聚合：聚合根、内部实体、值对象，引用核心认知编号，只补聚合归属与存在理由。

核心认知目前只对 Identity 给出功能编号（`F-ID-01~05`）、实体编号与唯一聚合根（`E-ID-01`）。Content、Artifact、Relationship、Explorer 没有编号也没有聚合根。这些上下文登记「编号缺口」：缺什么、由谁补、补齐前本维依据什么组织。缺口不阻塞写作，但必须可见，不自行发明编号或聚合根。

标出稳定内核与可变策略。策略变化频繁的部分放在聚合外，用参数或端口表达。

判据：每个聚合能说出根是谁、里面有哪些成员、为什么它们必须放在一起。

### 三、功能

按用例展开，标注它是命令还是查询。跨聚合但同属本上下文的业务动作写为领域服务。

每个用例给出：触发方、编排顺序、协作方、成功结果、失败分支。失败分支必须包含「结果未知」，它与「失败」的处理不同。

判据：实现者读完能写出调用顺序，不用猜下一步找谁。

### 四、关系

四个层次分开写。

聚合内：内部实体和值对象依附于根，生命周期由根决定，外部只能经根访问。

聚合间：只用 ID 引用，列出跨聚合持有的标识字段，不用对象引用。

上下文间：写明映射模式——客户-供应商、防腐层、开放主机服务、发布语言、共享内核、遵奉者、分离方式，并写方向与翻译位置。模式名取自 DDD 通用术语；核心认知与上下文映射未逐一命名时，把它作为本文的判断写出，不当作既有产品事实。

分层间：领域定义端口，基础设施实现端口，依赖朝内。

判据：每个跨边界依赖能说出「谁依赖谁、在哪翻译、变了影响谁」。

### 五、属性

不重写属性表。只核对三件事：识别方式与核心认知编号前缀一致（`E-*` 实体、`V-*` 值对象、`Q-*` 查询结果）；同一概念在本上下文只有一个词，列出禁用同义词；业务唯一约束由谁保护。

术语唯一性的依据是 §2.1 术语表与 §2.3 用词禁区。跨上下文同名异义是允许的，但要显式写出。

判据：每个概念能说出靠什么判断是同一个，且业务唯一约束有明确保护位置。

### 六、状态

引用核心认知的状态集合与状态图，不另画一份。本文补充的是迁移责任：每个迁移由哪个业务动作驱动、保护哪条 §4 不变量、发布哪个事件、非法迁移在哪拒绝。

分别表达「业务状态」与「操作状态」。查询失败、来源冲突、链序不明产出未知，不落到任何业务状态上。

核心认知未定义事件或拒绝位置的迁移，在「发布事件」列标注待确认编号，把缺口暴露出来，不留空。

判据：非法迁移能被拒绝，拒绝位置写在持有该状态的模型内。

### 七、边界

写出三层边界：上下文边界（负责与不负责）、聚合边界（什么必须同时正确、事务画在哪）、团队边界（谁拥有模型与术语解释权，若适用）。

上下文边界引用核心认知 §5.1.2 的限界上下文映射表，写明本上下文承载哪些子域、对应哪个业务模块、边界说明。规则本体以 §10 界限为准，本节只判断本上下文的适用范围。

边界内统一语言、强一致；边界外允许同名异义，通过映射与事件协作。边界按语言与模型划分，部署方式是独立决策。

最后写边界如何随其他六维变化：目的依据变了边界要不要收缩，功能变复杂了聚合要不要拆。

判据：能明确说出「什么绝不放在这里」。

## 体裁边界

领域设计不写 React Hook、Spring Controller、Mongo 集合、HTTP 路径、DTO 字段或迁移脚本。接口形状归 [Contracts](../../../_task/system-design/spec/contracts/README.md)，代码调用归 Frontend / Backend 实现设计。

## 工作步骤

1. 先判断目的与边界，再用文字落章。边界是容器，虽然写在第七章，判断在第一章之前。
2. 建立定义引用表：从核心认知抄编号与章节锚点，凡是能查到的，本文只留引用。
3. 写功能与关系，把跨边界协作的模式定下来。
4. 写结构与属性，确认聚合划分与识别方式，登记编号缺口。
5. 写状态，检查每条迁移都有驱动动作与保护规则。
6. 标出未知：待确认项用 `OQ-*` 编号，写拥有方与关闭证据。
7. 按交付检查过一遍；更新目标目录的稳定 `README.md` 入口，证据写入 `feature_list.json` 与 `progress.md`，保持 needs-review 直到人工复核。

既有 needs-review 草案按原结构评审，不强制套七维；新写或重写时按本技能执行。

## 交付检查

- [ ] 七维齐全，每维回答了对应认知问题，没有把定义搬进来；确实不适用的维度写明理由，不留空标题。
- [ ] 目的引用 §5.1.1 的子域编号；未覆盖时已登记待确认与拥有方；边界引用 §5.1.2 并写明承载的子域与业务模块，有不做什么。
- [ ] 定义引用表已建立，术语、实体、属性、关系、状态与事件编号都指向核心认知锚点。
- [ ] 结构登记编号缺口；每个聚合有根、成员、存在理由；跨聚合只用 ID。
- [ ] 每个用例有成功结果与失败分支，包含结果未知。
- [ ] 每条跨上下文依赖有映射模式、方向与翻译位置。
- [ ] 每个概念识别方式与编号前缀一致；业务唯一约束有保护位置。
- [ ] 每条状态迁移有驱动动作、保护的不变量、事件归属。
- [ ] 待确认项有 `OQ-*` 编号、拥有方与关闭证据；验收映射区分应有与已通过。
- [ ] 相对路径与锚点可解析。
- [ ] 稳定 `README.md` 入口已更新，证据已写入 `feature_list.json` 与 `progress.md`。
