# 七维要点

## 框架定位

七维用七个认知问题覆盖领域建模的全部判断：为什么建模、怎么组织、做什么、如何连接、如何识别、如何变化、范围到哪。维度定义、与 core-principle 的对应关系和每维判据只在 [SKILL.md](../SKILL.md) 维护，本文件不重复。

本文补的是落地时的判断要点、反模式与自问清单。

它是一套提问顺序，不是七份清单。七个维度互相咬合：目的决定边界与投入，边界决定语言的有效范围，结构在边界内组织模型，功能承载行为，关系连接内外，属性识别概念，状态表达变化。

> 以目的为牵引，在有限边界内，用结构组织模型，用功能承载业务，用关系连接上下文，用属性识别概念，用状态表达变化，用统一语言贯穿始终。

一句话判据：**答案是「是什么」的写进核心认知并引用；答案是「为什么、谁来做、失败了怎么办、范围到哪」的写在领域设计。**

## 各维要点

### 目的

先分类再定性。分类与投入方式引用核心认知 §5.1.1 的 `SD-nn`，不在领域文档重新判定：核心域建深模型，支撑域做到够用，通用域优先复用。

分类依据来自用户能力而非技术难度。「这个模块代码多」不构成核心域的理由。

本上下文在 §5.1.1 没有编号时，登记待确认项并写明拥有方与关闭证据；补齐前先改核心认知。分类变化也先改核心认知，再改领域文档。

写清不追求什么。一个上下文如果什么都想负责，边界一定守不住。

### 结构

聚合是「必须同时正确」的最小范围。聚合要小，跨聚合用 ID，一次事务只改一个聚合。

稳定内核与可变策略分开。费率、上限、开关这类高频变化的东西外置为策略或端口，不要把聚合改造成配置容器。

不要让聚合包揽多个上下文的能力。订单聚合里出现支付状态机，就是边界破了。

### 功能

命令改变状态，查询不改变状态。查询绕开聚合，直接读投影。

跨聚合的业务动作写成领域服务，服务负责编排，不负责持有规则。规则仍在聚合内。

失败分三类，处理各不相同：拒绝（规则不允许）、取消（用户中止）、结果未知（丢回执、超时）。把结果未知当成失败会导致重复提交。

### 关系

四层分开看：聚合内依附、聚合间 ID 引用、上下文间映射、分层间依赖方向。

聚合内，成员的生命周期由根决定，外部只能经根访问。绕过根直接改内部成员，等于取消一致性保护。

上下文映射要显式写出模式。九种模式各有适用条件：共享内核、客户-供应商、遵奉者、防腐层、开放主机服务、发布语言、分离方式、大泥球、伙伴关系。定义与选择依据见 [bounded-contexts.md](../../domain-driven-design/references/bounded-contexts.md#context-mapping-patterns)。没有模式说明的跨上下文调用，默认就是隐性耦合。

外部模型不可控、变化频繁、语言差异大时用防腐层。核心域之间语言接近直接协作即可，防腐层不是越多越好。遗留系统无明确边界时，先标注为大泥球并隔离，再逐步提炼，不假装它已是清晰上下文。

### 属性

先判断实体还是值对象：需要跟踪生命周期、需要区分「同一个变了」和「换了一个」，就是实体；只由属性值定义、不可变，就是值对象。

身份作用域要明确：跨上下文引用用全局唯一 ID，聚合内部成员只在聚合内唯一。

ID 要类型安全。`String` 传遍全场，最终分不清是哪个标识。

术语唯一性按上下文检查。同一概念只有一个词，禁用同义词写出来。跨上下文同名异义是允许的，但要显式记录。这部分内容 core-principle 归在「术语」，本文并入属性。

业务唯一约束（一个身份同时只有一个有效关联、同一方向不重复计数）由聚合根保护，不靠数据库唯一索引兜底。

### 状态

状态来自业务语言，不用技术词。业务说「宽限期」，代码就不能写 `OVERDUE`。

变化由业务动作驱动，禁止直接 set。每个迁移前置校验、方法内完成、留下事件。

非法迁移在聚合根被拒绝，不下沉到应用服务，也不依赖数据库约束。

事件分两类。领域事件留在本上下文内，表达业务事实；集成事件跨上下文边界，需要稳定 schema 与版本策略，消费方按事件引用幂等重放。同一事件不能既是领域事件又靠集成事件的宽松契约交付。

分别表达业务状态与操作状态。查询失败、来源冲突、链序不明产出未知，绝不落到任何业务状态上。

### 边界

三层边界：上下文（负责与不负责）、聚合（什么必须同时正确）、团队（谁拥有模型与术语解释权）。

上下文边界的承载关系以核心认知 §5.1.2 为准。子域是问题空间的能力划分，限界上下文是解决方案空间的语言与模型边界，两者不必一一对应；写作时引用映射表，不重新划线。

边界内统一语言、强一致；边界外允许同名异义，靠映射与事件协作。

部署单元不构成边界。一个上下文可以在同一个进程里，微服务化是独立决策。

写清「什么绝不放在这里」。这条比「负责什么」更能防止边界被侵蚀。

边界随其他六维变化。目的依据变化，边界要收缩；功能变复杂，聚合可能要拆；关系新增上游依赖，要重新评估翻译位置。

## 自问清单

**目的**：这类问题值得深挖，还是买或复用更划算？依据是用户能力还是代码量？分类是否有核心认知出处？

**结构**：聚合根是谁？一次事务是否只改一个聚合？是否按领域而非技术分层组织？

**功能**：每个用例的失败分支写全了吗？查询是否绕开了聚合？

**关系**：跨聚合是否只用 ID？上下文之间是什么映射模式？是否存在循环依赖？领域层是否依赖基础设施？

**属性**：实体靠 ID 判断相等吗？值对象是否不可变？同一上下文内概念是否只有一个词？业务唯一约束在哪保护？

**状态**：状态名是否来自业务语言？非法迁移在哪里被拒绝？每个迁移是否留下事件？

**边界**：边界内统一语言是什么？什么必须强一致、什么可以最终一致？团队边界与上下文边界一致吗？

**跨维**：目的变了，边界和投入跟着变了吗？关系变了，一致性策略跟着变了吗？

## 常见反模式

| 维度 | 反模式 | 结果 | 修正 |
| --- | --- | --- | --- |
| 目的 | 什么都当核心域 | 精力分散，通用能力重复造 | 按用户能力分类，通用域优先复用 |
| 目的 | 引用已取代的旧草案作分类依据 | 与当前核心认知冲突 | 先补核心认知，或标待确认 |
| 结构 | 聚合过大 | 事务冲突、并发差、加载慢 | 拆聚合，跨聚合用 ID |
| 结构 | 聚合内包揽多上下文 | 模型互相拉扯 | 按语言边界切开 |
| 功能 | 只写成功路径 | 恢复逻辑靠临场发挥 | 补拒绝、取消、结果未知 |
| 功能 | 查询加载整个聚合 | 性能差 | 走读模型 |
| 关系 | 跨聚合对象引用 | 加载整图，边界消失 | 改 ID 引用 |
| 关系 | 跨上下文共享数据库 | 无法独立演进 | 改 API 或事件 |
| 关系 | 循环依赖 | 无法独立测试与部署 | 引入事件或反转方向 |
| 关系 | 领域层依赖框架 | 模型被技术污染 | 端口定义在领域，实现在外 |
| 关系 | 映射模式缺省 | 隐性耦合 | 每条依赖写明模式与翻译位置 |
| 属性 | 给值对象加 ID | 值对象退化为实体 | 去掉 ID，用属性值相等 |
| 属性 | 实体靠属性判断相等 | 两个对象被当成一个 | 用 ID 判断 |
| 属性 | ID 用原始类型 | 标识互相串用 | 用类型安全的值对象 |
| 属性 | 术语不唯一 | 业务、代码、数据库三套词 | 建术语表并列禁用同义词 |
| 状态 | 直接 set 状态 | 不变量失效 | 业务动作驱动，聚合根校验 |
| 状态 | 迁移散落在应用服务 | 规则重复、难以追溯 | 下沉到聚合根 |
| 状态 | 事件只带 ID | 消费方无法处理 | 携带业务含义 |
| 状态 | 跨聚合强一致 | 锁冲突、扩展差 | 事件最终一致 |
| 边界 | 全局统一模型 | 模型臃肿、含义模糊 | 分上下文，允许同名异义 |
| 边界 | 把部署单元当边界 | 边界随基础设施漂移 | 以语言与模型划界 |
| 边界 | 边界内语言不统一 | 统一语言断裂 | 一个概念一个词 |

## 一致性、事务与扩展

这三件事由同一组边界决定。

聚合内强一致：由聚合根保护不变量，单机事务即可。

聚合间最终一致：领域事件驱动，消费端幂等，可靠投递用发件箱，长流程用 Saga 并配补偿。

扩展靠边界：上下文独立演进，写模型保不变量、读模型按查询优化，外部依赖经防腐层隔离。

原则是优先最终一致，不用分布式强事务硬扛。
