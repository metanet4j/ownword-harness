# S2 补丁草案：让 `signInputs` 的返回值能表达"是否真的签成了"

> **状态**：**草案，未提交、未改动任何生产代码**。供您在裁决 D2 时审阅。
> **依据**：§84（首次判定）、§272（第二次实证：确有一处被跳过，`signInputs` 仍返回 `true`）。

## 1. 问题（一句话）

`signInputs` **只在 `tx == null` 时返回 `false`**；其余一切异常（缺连接输出／脚本不可识别／缺预签名上下文／无公钥无密钥）**全部 `continue` 后仍 `return true`** ——
**调用方无法区分"全部签好"与"一个都没签"**。

## 2. 涉及两个类（同型缺陷，应一并修正）

| 类 | 位置 | 现状 |
| --- | --- | --- |
| `OrdinalsTransactionSigner` | `:90—107` | 跳过时 `log.warn`，末尾 `return true` |
| `RemoteTransactionSigner` | `:41—115` | 同上（且其 `signInput` 等价逻辑内联在该方法里） |

**两处的判据完全一致**，故**修正方案也一致**——**这也是"同一语义散落多处"的又一例**（§87 同族）。

## 3. 建议的改动（方案 A）

**核心思路**：**记录是否发生过"跳过"，并在"有跳过且无任何输入被签"时返回 `false`**。

```java
public boolean signInputs(Transaction tx, SigningKeyProvider keyProvider, int hashFlags,
                          boolean anyoneCanPay) {
    if (tx == null) {
        return false;
    }
    int signed = 0;        // 新增：真正被签的输入数
    int skipped = 0;       // 新增：被跳过的输入数
    for (int i = 0; i < tx.inputs.size(); i++) {
        if (signInput(tx, i, keyProvider, hashFlags, anyoneCanPay)) {
            signed++;
        } else {
            skipped++;
            log.warn("Skip input {} during batch signing", i);
        }
    }
    try {
        tx.sign().toCompletableFuture().join();
    } catch (RuntimeException e) {
        log.warn("交易签名失败：{}", e.getMessage());
        return false;
    }
    // 新增：一个都没签成时，如实返回失败（此前无论跳过多少都返回 true）
    if (signed == 0 && skipped > 0) {
        log.warn("没有任何输入被签名（{} 个被跳过），返回失败", skipped);
        return false;
    }
    return true;
}
```

**取值语义**（修正后）：

| 情形 | 返回值 | 说明 |
| --- | --- | --- |
| `tx == null` | `false` | 不变 |
| 全部输入签成 | `true` | 不变 |
| **部分签成、部分跳过** | **`true`** | **保持不变**——"跳过"是既定契约（§240／§247），**不应因此判整批失败** |
| **一个都没签成（且确有输入被跳过）** | **`false`** | **新增**——这正是当前缺失的能力 |
| 零输入 | `true` | 不变（无输入可签，但也没有失败） |
| `tx.sign()` 抛错 | `false` | 不变 |

## 4. 为什么选这个判据（而不是别的）

| 备选判据 | 为何不选 |
| --- | --- |
| **只要有跳过就返回 false** | **会破坏既有契约**——§240／§247 明确"局部问题局部降级、不升级为整体失败"；且实际业务中"某些输入本就无需本地签名"是正常情形 |
| **返回被跳过的数量**（改返回类型） | **改签名会波及所有调用方**（含 component 侧），**超出 R3 范围** |
| **只加注释、不改行为**（方案 B） | **等于把已知的假检查留在代码里**——调用方读到注释前仍会依赖它 |

**选"一个都没签成 ⇒ false"的理由**：它**恰好补上"无法区分全成与全败"这个缺口**，
**同时完全不改变"部分成功"的既有语义**——**改动面最小、语义提升最大**。

## 5. 影响面

| 项 | 评估 |
| --- | --- |
| **改动的类** | 2 个（`OrdinalsTransactionSigner`、`RemoteTransactionSigner`） |
| **改动的行数** | 每个方法约 ＋6 行、改 2 行 |
| **调用方影响** | **只有在"一个都没签成"时返回值由 `true` 变 `false`** —— 而这正是调用方**希望**知道的情况 |
| **现有测试** | **需逐一核对**：凡断言"某输入被跳过时仍返回 true"的用例，**若其场景是"全部跳过"则需改为断言 false**；"部分跳过"的用例不受影响 |
| **component 侧（R4／R5）** | **R4 尚未开始**，故**现在改最省事**——**这也是建议 R4 待 R3 收口后再启动的原因**（§110.4） |

## 6. 配套测试（草案）

| # | 用例 | 断言 |
| --- | --- | --- |
| 1 | **全部输入都签不成**（如提供者解析不到密钥，且无预签名上下文） | **返回 `false`**（**新增能力**） |
| 2 | **部分签成、部分跳过** | **返回 `true`**（**回归保护**：确认既有契约未被破坏） |
| 3 | 全部签成 | 返回 `true`（回归） |
| 4 | `tx == null` | 返回 `false`（回归） |
| 5 | 零输入 | 返回 `true`（回归） |

**用例 2 是最重要的一条**——它保证方案 A **没有**把"部分成功"误判为失败。
