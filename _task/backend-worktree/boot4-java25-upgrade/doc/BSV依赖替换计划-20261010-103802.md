## 1 依据与范围

产品与协议约束引用 [核心认知](../../../system-design/spec/核心认知.md)，特别是第 6.4 节的身份签名要求及第 10.1 节的钱包与密钥边界。迁移不得将 UTXO 花费签名当作身份签名，也不得为接入新 SDK 增加后端接收用户私钥的产品接口。

工具链与 Maven 使用引用 [共享工程规则](../../AGENTS.md)及 [Maven 命令模板](../../mvn-command.md)。现有测试要求引用 [单元测试全覆盖计划](单元测试全覆盖计划-20260920-090603.md)。本计划是本次依赖替换的阶段、改动范围和验收依据；既有升级计划中“bitcoinj-sv 不参与升级”的边界属于已结束的升级事项，不适用于本次明确提出的替换任务。

范围包括：

- 四个目标仓库的 POM、受影响源码、测试、必要配置与接口调用。
- 目标任务的 `init.sh`、`verify-unit.py`、源码及测试清单、精确覆盖例外、计划和状态文件。
- `bitcoinj-base`、`bitcoinj-legacy`、`io.bitcoinsv.jcl` 的直接依赖、传递依赖、dependencyManagement 与版本属性，以及生产和测试源码中的旧类型。
- 新 SDK 制品在两个隔离 Maven 缓存之间的接入与来源绑定。

指定 SDK 的源码、测试、POM、原迁移任务工具和冻结证据作为只读输入；构建仅允许生成其本地构建产物。`backend/` 基线、其他工作树、共享基础设施配置及远端仓库不属于改动范围。发现必须修改新 SDK 才能解决的能力缺口时，提交具体失败样本与缺口说明，由胡先生决定另立事项或扩展范围。

Java 接口中暴露的旧库类型需要替换，并同步修改本任务内全部调用方。本计划不承诺对依赖旧库类型的外部 Java 调用方保持二进制兼容；R0 的 API 映射必须列出这些变更。现有 HTTP DTO、持久化字段、协议编码及历史交易的兼容要求继续适用。

## 3 类型与行为迁移方案

| 原能力或类型 | 新实现方向 | 必须核对的行为 |
| --- | --- | --- |
| Base58、Utils、Sha256Hash、VarInt | primitives 中 Utils、Hash、Reader／Writer；哈希值采用现有业务包装或字节表示 | 前导零、校验和、UTF-8、CompactSize、哈希字节序与显示顺序 |
| ECKey／ECKeyLite、ECDSASignature | primitives 的 PrivateKey、PublicKey、Signature；保留现有业务包装入口 | 压缩公钥、地址、WIF、DER／compact 签名、公钥恢复、非法输入 |
| NetworkParameters／Net、Address、Coin | 复用现有业务值类型；必要时加入最小网络值类型，以整数 satoshi 表示业务金额 | 主网／测试网／regtest 编码、网络不匹配拒绝、金额精度与溢出 |
| DeterministicKey、HDKeyDerivation、ChildNumber、MnemonicCode | compat.HD、Mnemonic，适配现有路径与版本字节 | 助记词与 seed、xprv／xpub、硬化／非硬化路径、BAP ID 与轮换稳定性 |
| 旧消息签名、ECIES | compat.BSM／ECIES 及 Signature 公钥恢复 | 消息前缀、Base64 65 字节格式、签名地址、已有密文解密与错误处理 |
| Script、ScriptBuilder、ScriptChunk、ScriptUtils、验证标志 | script.Script／LockingScript／UnlockingScript／OP／Spend 与模板 | pushdata 长度、ASM、OP_RETURN、Ordinals 包络、历史脚本及验证结果 |
| Transaction、TxBean／Tx、输入、输出、OutPoint、UTXO、TxActor | transaction 模型与 compat.Utxo，改写读取器及转换调用 | raw hex 往返、txid／outpoint、sequence、lockTime、输出金额、协议字段 |
| TransactionSigner、KeyBag、RedeemData、SigHash | 新 SDK 的 TransactionSignature、脚本模板及业务签名入口 | ForkID 与旧入口支持的标志、前像、费率／找零、预签名和远程回填 |

该表给出已在本地源码中确认存在的能力方向，方法级对应由 R0 收口。每个被使用的旧 API 必须标记为直接替换、业务适配、删除无用代码或能力缺口，并列明全部调用文件和验证用例。

新 SDK 的网络版本字节、部分 List 字节表示及 `Object` 数值字段，须在业务边界明确转换与验证。金额验证覆盖负数、非整数、超出业务及 SDK 精确表示范围、累加溢出；避免直接将业务整数无检查地转为浮点值。

优先直接使用新 SDK。旧库的继承扩展类按其实际业务职责改写或删除，不能复制旧库包名、重建完整旧类型体系，或通过反射继续加载旧 JAR。为了逐步迁移，R1—R4 允许尚未迁完的模块保留旧依赖；R5 必须清除全部过渡引用。

### 3.1 助记词兼容与修复边界

2026-10-12 验收确认：组件测试源码尚未编译通过，测试分层被覆盖，集成资源尚未全部隔离，最终依赖树与提交绑定缺失。胡先生已明确批准修复至本计划全部完成；实际状态及顺序由 feature_list.json 维护。

既有 `MasterPrivateKey.fromSeed` 和 `CryptoHelper.generateRootCryptoBase` 是历史 Java 派生入口。旧版对传入词串直接执行 PBKDF2 派生；迁移后新增的 checksum 拒绝会使旧输入无法恢复原密钥。修复必须用旧制品独立生成的固定向量证明词串、passphrase、主密钥及派生地址保持一致，不修改历史词串或将其替换成另一个钱包。该兼容行为不增加产品接口，不改变核心认知中的 Wallet 私钥边界。

新钱包的标准长度词表（12、15、18、21、24 词）必须包含合法 BIP39 checksum；重复单词合法，不能用“不重复”代替有效性。`generateWordList(int)` 原有非标准长度的字典采样用途与越界拒绝保留并单独测试。

本轮测试沿用已批准的公开边界：主密钥导入／生成、根密钥与地址派生、交易组装与远程签名，以及组件的 service、repository、HTTP、消息和存储入口。逐个失败行为先补回归，再作最小修复。覆盖例外仅做有据的迁移对齐；新增可执行分支必须测试，不能自动扩大排除。

批量签名修复采用 S2 草案的最小语义：非空交易的全部输入均跳过时返回 false，避免调用方将未签名交易当作签名成功；部分输入签成仍返回 true，零输入交易仍返回 true。该返回值表示本轮签名有进展，不承诺交易所有输入均有效；最终脚本与交易验证义务保留。本地与远程批量签名均跳过缺少连接输出的输入，单输入签名仍显式报错；不能只用远程测试承接旧本地批量用例。通过公开入口验证全跳过、部分成功、全部成功及零输入。

## 4 实施阶段与门禁

### R0 固定基线与完成方法级映射

前置条件：取得代码实施批准；读取本任务规则、状态和本计划。

工作：

门禁：提交与既有改动全部记录；旧调用无遗漏；本次必须覆盖的能力缺口全部有结论，不能把未支持的行为留给编译阶段猜测；向量来源可追溯；`./init.sh` 对实际异常返回非零。中间件不可达只阻塞集成阶段，允许继续已授权的离线迁移。
