## 2. P0

### P0-A 测试门禁仍会假绿：JUnit 4 用例的真实分布没进计划

**事实**（`grep -rl '^import org.junit.Test;' --include='*.java'`）：

| 模块 | JUnit 4 测试类 | 该模块是否声明 test 依赖 | 计划是否给 vintage |
|---|---|---|---|
| `metanet4j-component/metanet4j-component-test` | 21 | 有 `spring-boot-starter-test` | 有（§6.5） |
| `metanet4j-sdk` | 13（共 15 个测试 Java 文件） | **无**（只经 base 传递 `junit`，且 base 的 junit 是 compile scope） | 无 |
| `metanet4j-base` | 2（`BapTest`、`AipTest`） | junit compile scope，无 starter-test | 无 |
| `metanet4j-connect-planaria` | 1（`AppTest`） | **无任何测试依赖声明** | 无 |
| `metanet4j-component-file` | 0（4 个 Jupiter 文件） | `spring-boot-starter-test` + `junit` + `mockito-inline` | 无（Jupiter 侧另见 P1-4） |

**后果**：

1. 计划 §7.3/§7.4 写的"21 个 JUnit4 用例经 vintage 执行""实际执行数 > 0"只覆盖 component-test；base/sdk/planaria 的 **16 个 JUnit 4 测试类**既没有 vintage 引擎，sdk/planaria 连 JUnit Platform 都不在 test classpath（无 starter-test）。`mvn -pl metanet4j-component-test -am test` 会连带跑这些模块，结果是**跳过或直接报"无测试引擎"**，而计划把这条当作门禁通过条件。
2. `component-test` 的 21 与真实总数 37（21+13+2+1）差异巨大；§7.3 又写"测试文件 24 个"，与实测 25 个（含重名 `CommonTest` ×2 与非测试类 `LocalTestUtxoProvider`）也不吻合。
3. sdk 的 JUnit 4 依赖是**靠 base 的 compile-scope junit 传递**才存在的，Boot 4 + JUnit Vintage 的 classpath 需要显式声明，不能依赖传递。

**修复方向**（任选，但必须写清）：

- **方案 A（推荐，最小改动）**：在**每个含 JUnit 4 测试的模块**（base、sdk、component-test、connect-planaria）显式加 `junit-vintage-engine`（test scope，版本由 Boot BOM = 6.0.3 管理）+ `junit 4.13.2`；把 §7.4 的验收改成"按模块列出 surefire 实际执行数，总和 ≥ 37 且每模块 > 0"。
- **方案 B**：把 base/sdk/planaria 的 JUnit 4 测试统一迁 Jupiter（sdk 13 个类 + base 2 个 + planaria 1 个），component-test 走 vintage。工作量更大但 classpath 更干净。
- 无论哪个方案，§7.4 的判定口径要从"执行数 > 0"改为"逐模块执行数 ⊇ 指定清单"，否则门禁依旧可被 1 个用例蒙过。

### P0-B 测试基类改造方案自相矛盾，基类用例会消失

**现状**（`metanet4j-component-test/.../Metanet4jComponentTestApplicationTests.java`）：

```java
import org.junit.jupiter.api.Test;      // 第 3 行：Jupiter
import org.junit.runner.RunWith;        // 第 4 行：JUnit 4
@SpringBootTest
@RunWith(SpringRunner.class)
public class Metanet4jComponentTestApplicationTests {
    @Test void contextLoads() {}        // Jupiter 注解
}
```

**计划 D17/§6.5 的写法**："基类去掉 `@RunWith` 与 JUnit 4 import，保持 Jupiter `@Test`" **并且**"12 个继承基类的类各自补 `@RunWith(SpringRunner.class)`"。这两条同时执行会得到：基类方法带 Jupiter `@Test`、子类带 JUnit 4 `@RunWith`。

- vintage 引擎（SpringRunner → JUnit 4 runner）**只识别** `org.junit.Test`，基类那个 `contextLoads()` 带的是 Jupiter `@Test`，vintage 看不到它 → 基类用例不会因这次改造被执行；
- 同时把 `@RunWith` 放到子类、把 Jupiter `@Test` 留在基类，等于同一个类层次里混用两套注解体系：该类是否被 Jupiter 引擎发现、继承来的 `contextLoads()` 是否被收集，取决于 platform 的 discovery 细节，而不是写在计划里的确定性行为。**门禁不能建立在这种"取决于实现"的判定上**；
- 结论：P0-B 的写法没有把"上下文启动"这条冒烟变成可执行断言，反而可能让 `contextLoads()` 从原本（JUnit 4 全量时代）可执行变成不可执行。

**修复方向**（二选一，写明并加断言）：

- **全 JUnit 4 路线**：基类改 `org.junit.Test` + 保留 `@RunWith(SpringRunner.class)`；12 个子类（它们本来就是 `import org.junit.Test;`）不动。最简单，风险最低。
- **全 Jupiter 路线**：基类改 `org.junit.jupiter.api.Test`，删 `@RunWith`，**子类各自加 `@SpringBootTest`**（不能靠继承 `@RunWith`），并把 21 个 component-test 类的 `org.junit.Test` 全量替换为 `org.junit.jupiter.api.Test`（同时处理 `Assert.*` → `Assertions.*`，及 `@Before/@After` → `@BeforeEach/@AfterEach`）。工作量需重新评估，评估结果必须回写计划。
- 门禁断言：`mvn -pl metanet4j-component-test test` 后，surefire 报告须断言**基类的 `contextLoads` 在用例列表中真的出现**（`grep contextLoads target/surefire-reports/*.txt`），否则"上下文启动"这条冒烟等于没跑。

## 3. P1

### P1-1（新发现，会导致 P2 编译失败）父 POM 的 Lombok 处理器路径引用了将被删除的属性

`metanet4j-parent/pom.xml:404-422` 的 `annotationProcessorPaths` 用 `${lombok.version}` 指定 Lombok 处理器版本，而 §6.2 要求**删除** `<lombok.version>` 属性。删属性不改引用 → 编译期表达式解析失败（或解析为空导致处理器缺失），P0-1 的修复手段本身会被打断。

**修复**：把该 path 的 `<version>` 改为字面量 `1.18.46`（与 §2 版本矩阵一致），或保留 `<lombok.version>1.18.46</lombok.version>` 属性只删 depMgmt 钉死。并把这条写进 §6.2 的改动清单与 P2 Gate（`mvn help:effective-pom` 中 annotationProcessorPaths 必须解析出三个具体版本）。

### P1-2 D20 的论证与事实不符（结论对、依据错）

D20 写"Gate0 探针实际继承的是 3.15.0"，但 `/tmp/gate0/pom.xml` **没有 parent**，只 import 了 `spring-boot-dependencies`；而依赖 BOM 的 `dependencyManagement` 的 `import` **不携带 `pluginManagement`**。因此 Gate0 里的 3.15.0 与"BOM 管理插件版本"无关（`build.log` 显示的 3.15.0 另有来源）。同时 §11 又说 Gate0"继承 3.15.0，父 POM 显式 3.8.1 会覆盖它，故 D20 要求删除显式版本"——这句把"探针是哪来的"讲反了。

对真实工程而言，删掉 metanet4j-parent 的显式 3.8.1 后，compiler 版本来自 **`spring-boot-starter-parent` 的 pluginManagement**（Boot 的 parent POM 才管插件），结论仍是 3.15.0，**方向正确**。

**修复**：把 D20 与 §11 的依据改成"spring-boot-starter-parent 的 pluginManagement 提供 3.15.0；依赖 BOM 不提供插件版本"；同时把 `/tmp/probe-compiler`（有 parent、显式 3.8.1、release 25 成功）作为 P2 的对照证据。

### P1-3 探针证据链不完整（缺 BUILD SUCCESS 记录、缺运行验证）

- `/tmp/probe-lombok/build.log`（35 行）只证明 **1.18.20 失败**；
- `/tmp/probe-lombok/build46.log` 只有 **4 行 warning**（Unsafe 警告），没有 BUILD SUCCESS，也没有编译行；1.18.46 的成功目前只能由 `target/classes/ProbeLombok.class` + `javap` 反推；
- §10 写"1.18.46 BUILD SUCCESS **且可运行**"，运行部分无任何证据（无 `java` 执行输出）。

**修复**：重跑一次并**完整落盘日志**（`mvn ... clean compile | tee build46.log`，不截断），并用 `java -cp target/classes ProbeLombok` 或 `javap -c` 断言 `getName()` 输出、class 文件 major version=69。探针结论是要被后面所有 Gate 引用的，证据链不能靠反推。

## 5. 准入结论与下一步

**结论：有条件准入。** 计划的工程主体（版本矩阵、坐标、Boot 4 包迁移、显式钉死清理、javax/Jackson 清单、环境与构建模板）已逐条复核成立，前次 Review 的 P0-1..P0-9 全部落入文档，且我复现了关键证据。问题集中在**测试门禁这一块仍然失真**：vintage 放错模块（P0-A）、基类改造自相矛盾（P0-B），加上父 POM 处理器路径（P1-1）会在 P2 直接报错。

建议顺序：
