### 2.2 必须解决的现有缺口

1. `component-file` 的本地、FTP、SFTP、S3 测试全部 `@Disabled`；旧文档“8 通过”的表述与 XML 不符。

## 3. “完整覆盖率”的验收口径

| 项目 | 要求 |
| --- | --- |
| 纳入范围 | 所有模块 `src/main/java` 的手写可执行代码，包括工具、DTO 自定义逻辑、配置、客户端封装、仓储实现、应用入口和代码生成工具 |
| 覆盖率 | 每个有可执行代码的模块及其手写类，`LINE`、`BRANCH`、`METHOD` 的 `MISSEDCOUNT = 0`；分母非零时为 100% |
| 无可执行代码 | POM、纯接口及纯注解等按实际字节码标记 N/A；无分支的方法只将分支指标标为 N/A，不伪造 100% |
| 生成代码 | 逐项识别 Lombok、MapStruct、编译器生成内容和 JaCoCo 内置过滤结果；手写映射规则、默认方法与序列化契约仍须测试；不以 DTO/entity/config/repository 等整包通配排除 |
| 测试结果 | 单元测试 failures = 0、errors = 0、skipped = 0；测试发现清单与 XML 对账，没有未说明的漏执行 |
| 测试质量 | 成功、空值、边界、非法输入、异常传播和副作用均有有意义的断言；关键协议、签名与交易用例使用确定性夹具和独立预期值 |
| 数据来源 | 单元测试专用执行数据；集成测试命中不得充入单元覆盖率报告 |
| 报告完整性 | 有可执行代码却缺测试、缺 `.exec`、缺 XML、出现 0 执行或覆盖率未达标，均导致最终验收失败 |

同时输出指令和类覆盖率用于排查。JaCoCo 的分支计数不包含异常处理，因此额外维护异常路径清单；100% 行/分支覆盖率也不代表穷尽所有输入组合或证明没有缺陷。[JaCoCo 计数说明](https://www.jacoco.org/jacoco/trunk/doc/counters.html)

默认不新增任何手写代码排除项。若遇到无法合理触达的防御分支或死代码，先给出源码、调用链和实验依据，优先采用不改变行为的最小可测性调整；确需删除逻辑、改变契约或放宽范围时提交具体决策。在决定前保留缺口，不降低阈值或宣称完成。

## 4. 测试方式与公共配置

### 4.1 复用现有技术栈

- 使用现有 Jupiter/JUnit Platform 与 Maven Surefire；参数化测试覆盖同类输入边界。Mockito 复用现有 BOM 管理，仅在需要的模块加入 test scope 依赖，优先真实值对象与简单替身。
- 在 parent 统一管理 JaCoCo，计划锁定 **0.8.14**，该版本已正式支持 Java 25；U0 核验 effective POM、制品解析与实际插桩。无需为本任务升级现有业务依赖。[官方版本记录](https://www.jacoco.org/jacoco/trunk/doc/changes.html)
- 通过统一的 `unit-coverage` profile 启用单元测试覆盖率采集，profile 内默认排除 `integration,external`，不能只依赖调用者记住命令行参数；JaCoCo 的 agent 参数与 Surefire/Mockito 所需参数合并，不能覆盖掉已有 agent。核验 fork 中实际生成采集文件。[agent 配置](https://www.jacoco.org/jacoco/trunk/doc/prepare-agent-mojo.html)
- JaCoCo 默认 `check` 绑定 `verify`，单跑 `test` 不代表检查已执行。本计划的单元验收命令显式调用 `jacoco:report jacoco:check`。[check 配置](https://www.jacoco.org/jacoco/trunk/doc/check-mojo.html)
- 采集与验收分开调用：基线执行 `clean test jacoco:report`，不调用 `check`；严格验收执行 `clean test jacoco:report jacoco:check`，规则固定为 §3，不按阶段修改阈值。`rules` 和采集文件路径放在插件级配置，确保命令行直接调用 `check` 也能取得规则；`prepare-agent` 绑定初始化阶段。
- U0 统计全部模块的未达标状态；U1—U8 仅对当前模块及其构建依赖严格验收，使用 `-pl <模块> -am` 时不触发尚未处理的下游模块。U9 逐一检查全部清单，不允许用缩小模块范围或跳过检查的开关完成验收。

### 4.2 单元测试与外部依赖

- 单元测试位于被测代码所属模块的 `src/test/java`，默认不启动完整 Spring 应用、不连接中间件或公网。对配置类可使用不联网的最小上下文验证绑定与条件分支。
- 外部边界使用受控替身：数据库模板/mapper、ES client、KafkaTemplate、Redis/Redisson、HTTP client、FTP/SFTP/S3 client。真实测试被测逻辑，仅替换协作者；验证请求结构、参数、回调、结果与异常，不只验证方法被调用。
- 本地文件采用 `@TempDir`；协议交易、UTXO、响应 JSON、字节流采用仓库内固定夹具。时间、随机数及异步回调可控，避免依赖等待和墙上时钟。ThreadLocal、静态 mock、线程池、流与系统输入均恢复或关闭。
- 将现有纯逻辑测试下沉到所属模块，消除不必要的 `@SpringBootTest` 继承。所有外部用例逐个判定：可离线化的改成单元测试；确属实连验证的标为 `integration` 或 `external` 并保留用途与替代单元用例映射。
- 默认单元命令排除 `integration,external`，这属于明确的测试分层。不得给失败的单元测试加标签以通过门禁，不得用 `@Disabled`、条件跳过或放宽断言掩盖问题。
- 实际数据库查询、索引行为、事务和 Spring 装配仍通过独立集成回归验证，报告单列。需要实连时依工作区规则提权运行，先确认共享设施、日志和连接配置；公网广播和真实资金操作不进入自动验收。

### 4.3 集成测试边界与环境

- 集成测试从公开的 service、repository、client、消息生产／消费或应用入口观察结果，覆盖 MongoDB、Elasticsearch、MySQL、Kafka、Redis、文件存储和 HTTP 适配器实际存在的交互。父 POM、纯数据和纯算法模块没有跨服务边界时记录 N/A，不制造空集成用例。
- 共享中间件使用 `infra/` 的现有五服务。测试必须使用每轮唯一的数据库、索引、表／记录、topic 与 Redis 键前缀；通过被测接口读回结果并在 `finally` 或生命周期钩子中清理。禁止删除固定业务索引、整库、共享 topic 或其他任务的数据。当前 `EsTest#recreateIndex` 使用固定索引，必须先隔离再纳入新门禁。
- HTTP、S3、FTP、SFTP 等外部协议用本地可控服务验证请求、响应和错误处理；不调用公网 API、主网广播、收费服务或个人凭据。真实第三方服务验证另列人工范围，不充作自动集成通过数。
- 集成测试使用 `@Tag("integration")`，单元测试排除该标签。执行前核对 `infra/README-*.md` 的连接配置、`docker logs` 的服务日志、Surefire XML 与应用日志位置；按工作区要求提权在宿主环境执行。
- 每个实际边界至少验证成功、失败／异常与数据可观察性，且保证独立重跑；通过清单把被排除的旧 `external` 用例逐一映射到新的单元或集成用例，无法自动化者记录原因。

### 4.4 U0 的前置顺序与退出条件

1. **先清点，后执行**：按测试源码、继承关系和调用链建立 `unit-test-inventory.json`，记录模块、手写生产类、生成类来源、单元/集成/外部测试及待修复测试。先处理未标注联网用例、`@SpringBootTest` 基类及其子类的分类；未完成分类的测试不得进入自动基线。测试发现与方法签名核对不能执行测试体。
2. **先验证采集，再扩展基线**：先在 base 验证 JDK 25 插桩、agent 合并、Jupiter 发现与报告生成，再采集 sdk/component。无测试或无数据模块列为缺口，不伪造覆盖率；已有测试失败如实记录。单个仓库失败仍收集其他仓库的基线，退出码与报告状态一致，不把基线调查完成标为测试验收通过。
3. **验证验收入口能拒绝缺失证据**：在临时报告副本或隔离探针中构造缺少 `.exec`、缺少 Surefire/XML、零测试、漏掉生产类、存在 skipped 五种情况，确认严格入口全部返回非零；不修改产品代码来制造失败。
4. **前置识别覆盖率障碍**：核对生成代码过滤和难以触达分支，例如 `StateHelper` 枚举 switch 的 default、生成器 `Scanner.next()` 后的空白判断、JWT 初始化异常。用真实采集结果判断是否计入分母及能否有意义地触达；不得伪造枚举值或删除防御逻辑来凑比例。U0 交付障碍清单和最小处理建议；后续未消解项保留为未完成，只暂停受其影响的事项。

U0 完成条件包括：25 个 POM 的清单完整、所有将运行的测试分类明确、至少一个模块真实采集成功、上述门禁反例得到预期失败、全量基线及覆盖率障碍有去向；集成清单应列明每个跨服务边界、资源隔离和观测方式。无需在 U0 达到全部模块 100%，但必须证明后续严格验收入口有效。

## 6. 验证命令与证据

工具链、settings 和跨仓库安装规则引用 [Maven 命令模板](../../mvn-command.md)。每轮测试从 `clean` 开始，按模块读取完整 `TEST-*.xml`；测试通过不能只看 `BUILD SUCCESS` 或日志末行。

U0 交付任务根目录的 `verify-unit.py`，使用 Python 标准库串联 Maven、报告校验和证据保存。**它是完成判定的必需入口**；单独运行 Maven 只作为调试，不能替代报告完整性检查。脚本按 `unit-test-inventory.json` 核验应有模块和生产类，最终 `--scope all` 必须覆盖全部清单。

U0 已创建并执行基线入口；以下命令继续用于逐模块及最终验收：

base、sdk 完成验证后，在进入下游仓库前安装同一提交的产物；如安装阶段跳过重复测试，该命令只作为产物安装证据，不作为测试通过证据。单元验收禁止 `-DskipTests`、`maven.test.skip`、忽略失败和关闭覆盖率检查。

每模块保留 Surefire XML、JaCoCo HTML/XML、执行日志、提交 ID、工具链和完整命令。逐模块输出发现数、执行数、通过数、失败数、错误数、跳过数及行/分支/方法的 covered/missed 分母；`external` 排除数单列，不记入通过数。继承、参数化和动态用例按实际执行实例对账，不能只数 `@Test`。

四仓库没有共同 Maven reactor，统一入口逐仓库执行并在最终汇总前检查每个模块。**所有 Maven 命令成功且严格报告检查成功，才返回 0**。JaCoCo 0.8.14 在缺少执行数据时直接跳过检查；本地 Surefire 3.5.6 的 `failIfNoTests` 默认 false，因此两者成功不能替代此门禁。[JaCoCo 0.8.14 源码](https://github.com/jacoco/jacoco/blob/v0.8.14/jacoco-maven-plugin/src/org/jacoco/maven/CheckMojo.java)

采集与证据隔离如下：

- 单元采集固定为模块 `target/jacoco-unit.exec`，report 和 check 必须读取同一路径；单元 HTML/XML 写入 `target/site/jacoco-unit/`。
- 每次运行使用独立 run ID，记录 HEAD、源码状态指纹、工具链、命令和测试分层。每模块执行结束立即把单元 XML/HTML、Surefire XML、日志和元数据复制到任务 `evidence/<run-id>/<仓库>/<模块>/unit/`，包括失败结果；完成保存后才能进行后续 install 或任何 `clean`。
- 集成回归使用独立命令 `clean test -Dgroups=integration -DexcludedGroups=external`，不启用 `unit-coverage`；执行前确认其发现清单仅包含获准的实连测试。结果存入同一轮证据的 `integration/`，不得读写或合并 `jacoco-unit.exec`。
- 缺模块、缺生产类、缺采集数据、缺 XML、零单元执行、skipped、测试发现不符或覆盖率未达标均失败；POM 和无可执行代码项仅按清单中的有据 N/A 处理。集成回归完成后读取已保存的单元证据，不读取被后续 `clean` 重建的 target。
- Git 提交清单、校验入口、汇总与可复现命令；构建产物和大体积原始报告不提交。未完成模块的缺口持续保留，不能因本轮未选择该模块而从最终范围消失。
