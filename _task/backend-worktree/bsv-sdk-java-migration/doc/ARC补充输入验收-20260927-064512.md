## 真实执行与修正

179 条输入包括构造 30、随机 30、广播入口 29、交易序列化替身回调 34、HTTP 请求 27、HTTP 响应 24、HTTP rejection 3、原循环迭代值 2。构造后直接退出的第 6 例仍记录构造与随机；第 21、26 例序列化异常后没有 HTTP 调用。

Java 原测试按原条件分支和循环执行。第 19 例现经真实 FetchHttpClient→ARC.broadcast 流程传入 `Undefined.INSTANCE`，并独立计算 `ERR_UNKNOWN`。`HttpClient.Response` 与 `FetchHttpClient.FetchResponse` 保留既有整数访问器和构造器，增加 `rawStatus` 保存原始值；FetchHttpClient 原样透传，ARC 失败分支读取此值。

第 22、28 例保留原 rejection 对象的 number／undefined message；第 23 例 HTTP 响应字段与固定原测试一致。序列化替身仅在原 SDK 实际调用时返回或抛出原输入，记录器不预先调用，也不以 TS 断言结果生成 Java 返回值。

30 次随机字节来自本轮固定原 Jest 执行，冻结后正式重跑 TS；Java 读取同一字节输入。输入计划、原用例身份、原站点、调用顺序和原断言顺序均单独核对。双端 179 个输入与 78 条断言的逐值差异列表为空，没有新增语义归一化例外。

## RED、GREEN 与反例

- API RED：缺少 `Response.rawStatus()` 和携带原值的 `FetchResponse` 构造器，干净编译失败。
- 行为 RED：30 例中仅第 19 例失败，原状态已真实保留为 undefined，但 ARC 仍读取兼容整数，实际 `0`、期望 `ERR_UNKNOWN`。
- GREEN：改为读取 rawStatus 后，累计 66 例全部通过；179 输入及 78 原断言逐值相等。
- 输入生产器反例：把真实状态 undefined 改为 number 0，生产器返回 1 并拒绝冻结输入不一致。
- 正式证据反例：独立修改输入状态或把原布尔断言 actual 从 true 改为 false，bundle 均返回 2；独立原断言比较也拒绝后者。
