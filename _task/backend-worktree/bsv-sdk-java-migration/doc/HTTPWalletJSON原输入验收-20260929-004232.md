## 实现与真实重放

TS 探针 `capture-http-wallet-json-inputs.cjs` 不改写原测试，通过模块工厂替换 `HTTPWalletJSON` 默认导出：构造与公开 `api` 调用在测试体内即时记录，mock fetch 的请求与响应在 `afterEach` 按客户端创建顺序补记；`prepare-http-wallet-json-inputs.py freeze` 把 214 条真实入口冻结为计划与重放语料。

Java 侧 `HTTPWalletJSONInputReplay` 按 `javaMethod` 消费同一语料：`construct` 与 `ReplayClient.api` 即时核对，fetch 事件在用例结束时按调用顺序核对；请求体另按解析后的 JSON 与固定 TS 线上字节比较。两端顺序、参数编码（`String`／`Number`／`Boolean`／`Array`／`Object`／`JestMock`／`Uint8Array`／`Undefined`）、接收者身份与 `preState.priorEvents` 全部逐字段比对，任何一项不同即拒绝。

跨语言表示按以下固定规则落地，不新增语义例外：

- TS `undefined` 与 Java `null`：`HTTPWalletJSON` 的 `String originator` 无法区分两者，本文件固定语料只有 `undefined`（缺省 originator 用例），Java 侧统一记为 `Undefined`。
- TS `Uint8Array` 对应 Java `ByteView`；TS `number[]` 对应 Java `byte[]`，按 BRC100 线上数组记录。原 `inputBEEF` 用例因此改为传入 `ByteView`，`internalizeAction` 的 `tx: []` 仍按 `byte[]` 记录。
- 原 `rejects.toThrow(SomeClass)` 的期望是类源码文本，按固定 TS 文本保存为 `httpwalletjson-werr-*-class-source.txt` 三个资源；原 `expect(promise).resolves.toEqual(x)` 的实际值是 promise 的字符串表示，新增 `assertResolvedEquals` 按同一表示记录并在 Java 侧完成真实对象比较。

## RED、GREEN 与反例

- 首轮 RED：`repairsBeefAndHmac` 先调用再构造第二个客户端，与原测试“先建两个客户端再依次调用”的入口顺序不同，重放拒绝“入口顺序与原测试不同：api，期望 constructor”。
- 第二轮 RED：`routesInternalizeAction` 的 `tx: []` 被记为 `Uint8Array`，与原语料的 `Array` 不符；据此确定 `byte[]` 与 `ByteView` 的区分规则。
- 首次汇总比较拒绝 6 条断言：三条 `toThrow(WERR_*)` 的期望类源码、两条 `toThrow(Error)` 的原生函数源码、一条 `resolves.toEqual` 的 promise 实际值；改为固定资源与专用记录入口后 73／73 一致。原 hmac 用例中常量自比的空断言同时替换为真实对象比较。
- 采集脚本缺陷：两侧共用同一运行目录时，TS 与 Java 的原始断言轨迹会写入同一文件，`emit-assertion-observations.py` 读到混装记录；已按侧别拆分文件名（`<side>-inputs.raw.jsonl`、`<side>-assertions.raw.jsonl`、`<side>-network.jsonl`）。
- 输入篡改：Java 侧把一条入口 `method` 改为 `*-tampered`，汇总拒绝“TS/Java 输入或前置状态不同”。
- 断言篡改：Java 侧把一条断言实际值改为 `tampered`，汇总拒绝“实际结果不一致”。
