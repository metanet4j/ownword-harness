# TS 逐局部串行全量采集（路径 B）设计与实测

工具：`run-full-ts-serial.py`（driver）、`build-ts-serial-entries.py`（入口映射表生成器）、`ts-serial-entries.json`（47 条非标准局部入口）。
配套改动：`script-vector-evidence.py` / `transaction-vector-evidence.py` 的 `run_id` 改为「有外层 `EVIDENCE_RUN_ID` 就继承、否则自生成」（与全部标准适配器同一口径）。

> **口径声明（不回避）**：本方案的 TS 侧是 **154 次逐局部串行真实采集，在同一个运行目录、同一个 `EVIDENCE_RUN_ID` 下合并**成一份证据，**不是**单进程单次 Jest 运行。`full-evidence-run.py` 的阶段时间窗与 `ts-run.json`／`java-run.json` 身份仍由它自己的 `capture-side` 真实生成，未伪造任何 manifest、时间窗或来源摘要。可验证性是：同一 Java/TS 冻结来源 + 同一份汇总输入计划 + 逐用例两侧同输入 + 逐断言实际值比较。

## 1. 为什么需要路径 B

最终门禁要求**同一轮、同一来源**的双侧全量证据，其中 TS 侧有两处硬约束：

- `audit-tests.py::compare_ts` 要求**一份报告覆盖全部 133 个原文件**（`same_keys(files, actual_ts)`），且逐文件的用例名多重集与 `module-tests.json` 完全一致；
- `audit.compare` 要求 Java 侧实际执行全部映射用例，逐断言比较依赖 TS/Java 两侧同一份输入计划。

原有的一次性单进程分派（`capture-full-dispatch.cjs` + `run-full-ts-capture.py`）在多轮实测中失败：9 个原文件解析不到探针、11 个局部原始轨迹缺失或为空、34 个局部转换器缺失或转换失败、少 24028 个计划样本（63%）、断言转换报「原 TS matcher 序号不连续」。而**逐局部采集机制完全可用**（统一窗口 v2：108 项处理／107 篡改门禁通过／0 失败，106 个局部同源）。路径 B 就是把这些已跑通的逐局部采集**串行化并合并**成同一轮证据。

## 4. driver 行为

每个局部在独立子目录 `<runDir>/local/<局部>/` 内运行它自己的 TS 入口，环境变量全部指向本轮：

- `EVIDENCE_SIDE=ts`、`EVIDENCE_RUN_ID=<本轮身份>`、`EVIDENCE_INPUTS_PATH=<子目录>/inputs.jsonl`、`EVIDENCE_ASSERTIONS_PATH=<子目录>/assertions.jsonl`、`EVIDENCE_INPUT_PLAN=<该局部计划>`；
- 兜底 `MIGRATION_NETWORK_LOG` 与 `MIGRATION_PARITY_TS_OBSERVATIONS`（适配器/探针会覆盖成自己的路径）。

**逐局部校验**（任一不过即记为该局部失败，并在报告里给出**局部名 + caseId + 具体标识**）：输入/断言行必须都是本轮 `runId` 与 `side=ts`；逐用例的 `sampleId`／`assertionId` 序列与**该局部计划**完全一致；Jest 报告全绿且有用例执行。

**合并**：

- `ts-inputs.jsonl`：各局部输入按**汇总计划**重排去重（复用 `run-full-ts-capture.order_rows`），并报缺失/多余/重复；
- `ts-assertions.jsonl`：各局部**当场转换好的**断言行按汇总计划拼接。这里刻意**不**用「合并 parity 轨迹再全局转换」：同一原文件被多个局部采集时，合并轨迹里同一 `(文件, 用例, matcher)` 会出现多次，`emit-assertion-observations.py` 的序号连续性校验必然断档——这正是路径 A 失败的那条错误；
- `ts-assertions.raw.jsonl`：合并轨迹仍然落盘作溯源，并对它跑一次全局转换作**诊断**（结论如实记录在 `mergedRawConversion`，不作硬门禁）；
- `ts-jest.json`：各局部 Jest JSON **按文件去重**后合并成一份，计数从合并后的 `testResults` 重算（`compare_ts` 只要求一份报告覆盖全部原文件，不要求同一 Jest 进程，与 `capture-legacy-side.py::merge_reports` 的既有口径一致）；
- `ts-serial-report.json`：逐局部记录（形态、命令、耗时、计划/用例/输入/断言数）、覆盖统计、缺口清单（缺哪些文件、归属哪些局部）、逐局部轨迹重放一致性、诊断结论。

**硬门禁**：选中范围内缺样本/缺断言、出现重复或计划外行、原文件未全覆盖、`--allow-partial` 之外覆盖不足，都非零退出，防止「跑完但没有输入」的假绿。

### 7.5 Java 阶段暴露的休眠变量缺陷与修复

`HashPbkdf2InputReplay.load()`（冻结的 SDK 测试代码，**未改**）要求 `caseId ∈ 13 个固定 id 且 sampleId == "call-0"`；而汇总计划里这 13 个用例的 sampleId 是标准局部 `hash` 的 **`pbkdf2-01`** 口径 → `IllegalStateException: PBKDF2 固定 TS 输入缺失或重复：0`。

- 逐局部为何全绿：`derive()` 在 `MIGRATION_HASH_PBKDF2_TS_INPUTS` **未设置**时直接走生产实现、不消费语料；逐局部采集从不设置它（`hash` 局部只设 `MIGRATION_HASH_TS_INPUTS`）。它属于**已退役**局部 `hash-pbkdf2-vectors`。
- 全量为何必炸：`run-full-java-capture.py::main()` 会把**分派表 `full-run-probes.json` 登记的 115 个 `*_TS_INPUTS`** 与**源码扫描到的 78 个**取并集，再全部指向本轮汇总输入，把该休眠 replay 激活。
- **真正的注入点是那个并集**（`full-run-13` 的教训）：只在 `java_ts_input_envs()` 里排除不够，分派表会把变量并回来。修复 = 在并集处减去排除集：
  ```python
  EXCLUDED_TS_INPUT_ENVS = ('MIGRATION_HASH_PBKDF2_TS_INPUTS',)
  targets = sorted((set(configured) | set(discovered)) - set(EXCLUDED_TS_INPUT_ENVS))
  ```
  报告（`java-capture-report.json`）记录 `tsInputEnvs`（114）与 `excludedTsInputEnvs`，便于审计追溯。
- 依据：①该变量全仓仅被 `HashPbkdf2InputReplay.java` 读取；②不设置它时，这些样本由 `HashTest` 主路径按 `pbkdf2-01` 正常消费（逐局部 `hash` 的 `java-inputs.jsonl` 已证实），不丢证据；③反过来硬塞 `call-0` 语料会让 Java 输入出现计划外样本，直接被 `evidence-bundle` 拒。
- **改前单点预验证**（都用 `full-run-13` 的 `ts-inputs.jsonl` 复刻注入表达式，单跑 `HashTest`）：

  | 注入表达式 | 变量数 | 含 pbkdf2 | `HashTest` |
  | --- | --- | --- | --- |
  | 修复前（并集） | 115 | 是 | 13 errors（精确复现 run-13） |
  | 修复后（并集 − 排除项） | 114 | 否 | Tests run: 30, Errors: 0, BUILD SUCCESS |

### 9.2 WalletWire 大数组（4 条 132 MB 巨行 → OOM 的真正原因）

`java-assertions.raw.jsonl` 839 MB 里 **4 行占 795 MB**：全是
`WalletWireIntegrationTest#preservesLargeTypedBeef` 的 `actual`（有时含 `expected`），每行 132 MB／3300 万元素。
单行解析峰值实测 **2.88 GB**（`Maximum resident set size: 2887788 kB`），累计必然 OOM——kernel log
`Oct 01 06:54:12 Out of memory: Killed process (python3) anon-rss:5907048kB` 就是它。

**这不是发射器扛不住，而是既有大数组约定没被打开**：逐局部 `wallet-wire` 目录里
`java-assertions.raw.jsonl` 只有 0.1 MB，另有大数组见证 `java-large-actuals.jsonl` 33.6 MB。
按 `capture-wallet-wire-side.py:47-58` 复刻并预验证的完整 recipe（4 项必须齐全）：
```
env  MIGRATION_WALLET_WIRE_ASSERTION_INDEX=<plan>/assertion-index.json
env  MIGRATION_WALLET_WIRE_JAVA_LARGE_ACTUALS=<runDir>/java-large-actuals.jsonl
mvn  -Dmigration.walletWire.plan=<plan>/replay-inputs.jsonl
mvn  -Dmigration.parity.largeArrays=true
```
预验证结果（`WalletWireIntegrationTest` 单跑）：`Tests run: 82, 0 failures/errors`、
`java-assertions.raw.jsonl` **0.12 MB**（修前 839 MB）、`java-large-actuals.jsonl` **33.56 MB**（4 条见证）、
`java-inputs.jsonl` **8.53 MB**（该局部 82 例输入补齐）。只加 `largeArrays` 不加 `walletWire.plan` 时原始轨迹同样变小，
但**见证不产出**（`largeActual` 因 `PLAN == null` 直接 return），故 4 项要一起给。

结论：**发射器无需流式化改造**（避免动共享工具与比较层口径）；这两处按既有约定接线即可，剩余 743 例／34 类的
`-Dmigration.*`／自有 env 逐局部映射由另一路代理负责。

## 10. 已知限制与风险

1. **不是单进程单次 Jest**：TS 侧是 154 次串行 Jest 采集在同一运行目录、同一 `runId` 下合并。`full-evidence-run.py` 的阶段时间窗与 `-run.json` 身份仍由它自己的 `capture-side` 生成（不伪造），但「一次 Jest 进程覆盖全部原文件」这一形式不成立——验收依据是**同源摘要 + 同一输入计划 + 逐用例双侧同输入**，报告中如实写明。
2. `subprocess` 逐局部串行，单局部超时默认 7200 s（与 `recapture-all.sh` 一致）；`aesgcm-man` 实测约 40–42 min。
3. 合并轨迹的全局转换只作诊断（原因见 §4）；断言行以各局部当场转换为准，并由逐局部轨迹重放（`crossCheck`）确认轨迹与断言行一致。
4. 5 处语料回退的等价性由适配器自身的计划校验保证；若某个回退语料与当年不同，该局部会直接失败而不是产出错误证据。
5. **开跑前必须冻结任务侧工具**：`full-evidence-run.py::producers()` 覆盖任务根目录下全部 `.py/.cjs/.mjs/.sh`，SDK 源码与任务侧工具必须同时静止，否则整轮作废（`full-run-11` 即因此白跑 51 分钟）。`.cache/run-full-e2e.sh` 已内置「近 10 分钟无任务侧工具改动 + SDK/TS 工作树干净」的静默窗口守卫。
6. 被作废的一轮**无法部分复用**：`capture-side` 要求新运行目录、新身份，且禁止沿用已有产物，所以 `--resume` 只在**独立运行**（同目录 + 同 `--run-id`）时有效（实测：154 选中、152 复用、仅重跑 2 个失败局部，5.4 s）。
