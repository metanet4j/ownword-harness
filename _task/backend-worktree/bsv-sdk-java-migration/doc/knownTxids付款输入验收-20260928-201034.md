## 范围与结果

固定 `src/auth/clients/__tests__/AuthFetch.knownTxids.test.ts`（17 例）中的 6 个付款入口用例已完成双端同输入局部门禁。

| 双端付款输入 | 6／6 用例，8 次付款调用逐字段一致 |
| 双端原断言 | 25／25 一致 |

| 篡改反例 | 付款输入篡改、断言篡改均被拒绝 |

局部门禁 `auth-fetch-knownTxids-payment-local-gate.py` 的输出始终 `formalAcceptance=false`，只是该切片的独立验收，不代替任务级门禁。

## 实现与真实重放

`AuthFetchKnownTxidsInputReplay` 在原有解析路径（10 例）之外新增付款路径：`payment(...)` 按固定 TS 语料消费 `handlePaymentAndRetry` 的 url、config 与 `Response`（status/statusText/headers），Java 侧独立重建响应并执行付款流程，随后逐字段复核本次付款调用；`PaymentContext` 以 `details()` 的快照参与比较，配置与 JS 侧同字段。

宿主表示按门禁规则分离：TS 记录的 `Response.bodyUsed` 是 JavaScript 宿主字段，Java 侧不伪造该字段，比较前统一移除；`toThrow` 之外的 `expect.any(String)` 期望以既有 `ParityRecorder.record("toEqual", …, "Any", …)` 表示。

## RED、GREEN 与反例

- 初始主仓只有解析路径：门禁报“六例真实付款输入覆盖数量错误”（Java 侧 10 条，缺 6 条付款条目）；补付款路径后 16 条齐备。
- 首版 Java 快照带入 `bodyUsed`，门禁报“Java 伪造 Response.bodyUsed”；改为不写该字段、仅在比较前统一移除。
- 首个付款断言把 `x-bsv-payment` 与字面量比较，门禁报“实际结果不一致”（TS 期望 `Any`）；改为记录 `Any` 并实际校验字符串类型。
- `tamper`：篡改付款输入（`x-bsv-payment-known-txids`）与断言实际值均被拒绝。
