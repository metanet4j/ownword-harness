# wallet-keys 剩余两个文件的采集方案

wallet-keys 六个原测试文件中已完成四个的标准双侧同输入局部（KeyDeriver、CachedKeyDeriver、ProtoWallet.additional、ProtoWallet）。本文件记录剩余两个文件（ProtoWallet.async-backend、ProtoWallet.native-hash）的边界、已试过的路子和必须换的做法，避免重复试错。

## 当前状态

| --- | ---: | --- |
| KeyDeriver | 17 | 标准双侧局部（49 入口／37 断言） |
| CachedKeyDeriver | 13 | 标准双侧局部（49 入口／44 断言） |

## ProtoWallet.async-backend

边界有三类，缺一不可：

1. `ProtoWallet` 的公开方法（`createSignature`、`verifySignature`、`getPublicKey`、`encrypt`…），其中首个用例用最长 256 次 `createSignature` 搜索出"缺少必需补零的 DER"夹具；
2. `KeyDeriver.deriveSymmetricKeyAsync`——第 5 个用例不使用 ProtoWallet，直接用 `KeyDeriver` 与异步后端；
3. `registerAsyncCryptoBackend`／`unregisterAsyncCryptoBackend` 的全局注册，它决定每个用例走加速路径还是 JavaScript 路径（属于前置状态，不是普通 fixture）。

已试过的两轮探针（原型级包装、实例级包装）都只记录到 `constructor`，公开方法调用一条都没进账本，而同一探针在 `ProtoWallet.test.ts` 上工作正常。两次实验共同点是：该文件从 `../../../mod` 桶文件导入，`KeyDeriver` 的命名导出包装生效、`ProtoWallet` 的默认导出包装只在构造阶段生效。下一步不要在实例／原型包装上继续加码，改为下列任一做法后再采集：

- 不替换类，而是从桶文件出口做 `jest.doMock('../../../mod', ...)`，把 `ProtoWallet` 与 `KeyDeriver` 两个名字一起换成记录型包装；
- 或者把边界探针下沉到 `WalletInterface`（`ProtoWallet` 对外暴露的调用面）并在测试侧用同一入口调用。

## ProtoWallet.native-hash

两个额外问题：

1. `const wallet = new ProtoWallet(new PrivateKey(42))` 写在 `describe` 体内，构造发生在任何用例之前；探针需要允许"固定用例之外"的构造并把它归到该 describe 的首个用例，或改为按 `describe` 归属记录。
2. 载荷是 65536 个数字（`data`）以及 `Hash.sha256(data)`；账本行按现有写法会接近 0.5MB／条。登记口径应沿用既有 `ParityRecorder.largeArraysEnabled` 的摘要约定：大数组在计划里记 `digestSummary`（长度＋SHA-256），两侧比较摘要而不是逐元素，并在文档中写明该局部不逐元素比较。
3. 该文件的 `crypto.subtle` 被替换成 mock（`install()`），五个 `it.each` 用例分别覆盖原生摘要成功、短载荷、字节强转、无 Web Crypto 宿主和原生结果异常回退；摘要 mock 的调用次数与实参属于断言面，不属于输入账本。

## 顺序建议

先做 native-hash（边界只有 ProtoWallet 一个类，问题集中在账本口径），再做 async-backend（边界跨三个模块，需要先解决桶文件包装）。两者完成后统一重采 wallet-keys 及其余受影响局部，跑同来源全量回归，再结项 `migration-impl-wallet-keys`。
