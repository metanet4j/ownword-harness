## 现有 Java 入口

现有 Java 代码仅作为选择模块的只读依据。以下入口对应能力类别，不表示旧 Java API 和 TS 已经等价，也不承诺本次替换旧工程依赖。

| 只读入口 | 实际能力与完整模块 |
| --- | --- |
| `metanet4j-sdk/.../PrivateKey.java` 的 fromWIF/sign、PublicKey、EcKeyLiteExtend | WIF、Base58Check、密钥、ECDSA 与签名恢复，对应 primitives |
| `metanet4j-sdk/.../crypto/CryptoHelper.java` 的 HDKeyDerivation/MnemonicCode，MasterPrivateKey | HD 与助记词，对应 compat；内部密码学依赖 primitives |

| `metanet4j-sdk/.../transcation/TransactionBuilder.java`，remote/RemoteTransactionSigner | 输入输出、费率、序列化、签名摘要，对应完整 transaction |

具体文件路径保存在 moduleReviews.evidence。BAP、AIP、Sigma、Ordinals 等业务协议不因此成为本次新增工程；只读现有调用不等于授权业务适配。

## 必须扩展为六模块的依据

原扫描对 TS 编译后的运行时 import 建图，并跳过测试目录，会遗漏类型接口和测试依赖。实际源码存在以下边：

| 源码位置（均相对 `packages/sdk`） | 依赖及处理 |
| --- | --- |
| `src/script/templates/PushDrop.ts:12` | WalletInterface/WalletProtocol 来自 wallet；锁定和解锁实际调用 getPublicKey/createSignature，不能删除钱包入口 |
| `src/transaction/Transaction.ts:26`、completeWithWallet | 钱包接口及 createAction/signAction 协议属于公开交易能力；类型被 TS 擦除不意味着 Java 不需要对应契约 |
| `src/script/templates/__tests/PushDrop.test.ts:3` | 使用 auth 的 CompletedProtoWallet；真实创建脚本、签名和 Spend 验证，不是只返回固定值的 mock |
| `src/auth/certificates/__tests/CompletedProtoWallet.ts` | 继承 ProtoWallet，使用 KeyDeriver/CachedKeyDeriver。不能把这些计算换成固定输出来声称复刻测试 |
| `src/wallet/substrates/WalletWireProcessor.ts:5`、WalletWireTransceiver.ts:50 | 完整 wallet 使用 auth Certificate；选入 wallet 后须完整纳入 auth |
| `src/transaction/__tests/Transaction.test.ts:12` | 导入 compat/Utxo，交易模块验收不能留待 compat 后续实现 |
| `src/primitives/TransactionSignature.ts:6`、TransactionSignature.additional.test.ts:5 | 类型及测试指向 transaction；不能只依据编译后依赖安排阶段 |

因此新增 wallet、auth 两个完整模块，保留其所有 substrates、证书、会话、客户端、传输、辅助源码和测试。不能只抽出 ProtoWallet 或只写钱包接口而省略已纳入模块的其他功能。

清点器现对原始 TS AST 检查静态 import/export、import type、类型查询及字面量 require/import，并递归包含测试及辅助文件。当前完整依赖图为：

六模块闭合且形成循环依赖；阶段安排按[模块迁移计划](模块迁移计划-20260920-103547.md)执行。范围内无指向另外九模块的直接源码、类型或测试依赖。

还人工复核了静态模块图不能独自决定的边界：

- 根入口 `mod.ts` 是全 SDK 汇总导出。范围内通过该入口导入的具体符号均归属六个已选模块，包括 PrivateKey、PublicKey、P2PKH、Script、Spend、Transaction、Hash、ProtoWallet、SymmetricKey、Utils、Random 和异步密码学后端注册接口。仅加载汇总入口不会把其未使用的上层服务全部视为需要迁移的能力；原 TS 测试执行仍使用固定上游入口。
- 根目录 `src/__tests/LookupResolver.diagnostics.test.ts` 与 `src/__tests__/BRC100OverlayTransport.test.ts` 的直接被测对象分别为 LookupResolver、HTTPSOverlayLookupFacilitator，归属 overlay-tools；前者使用 telemetry 观察诊断。两项均不是基础交易模块测试，归属记录已保留，未归属跨目录测试为零。
- 除根目录两项外，测试均按其顶层模块纳入或排除。其他九模块对基础密钥、脚本、交易的使用属于上层服务的依赖，不能反向推出本次必须实现这些服务。各项排除依据在 moduleReviews 中记录。
- `Random.ts` 的 process.getBuiltinModule、`DefaultHttpClient.ts` 和 `BinaryFetchClient.ts` 的 nodeRequire 别名均指向 Node 平台的 crypto/https；这些是平台能力，不是隐藏的 SDK 模块。Java 对应平台接口与可控测试环境属于下一项 API 契约工作。
- 外部测试依赖包括 Node crypto/fs/path/https/vm、Jest 和 fast-check；保留原测试及属性生成约束，Java 重放方式在 P0 输入语料工作中落实。测试文件里的浏览器、React Native 与跨 realm 行为也不得因 Java 环境不同而直接跳过。
- NormativeVectors 从 script 内的 fixtures 读取向量；完整文件清单包含这些目录及校验值。AESGCM.man.test.ts 保留原超过 512 MiB 的输入，不因默认 Jest 排除而省略。
