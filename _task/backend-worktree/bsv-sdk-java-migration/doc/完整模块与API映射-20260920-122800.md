### 已确定的共同约束

1. 工程及包根保持 `metanet4j-bsv-sdk` / `com.metanet4j.bsv`，底层不依赖 base/sdk。TS 类名、公开成员名和模块归属优先保留；自由函数采用模块工具类，具体入口逐项写入 api-map.json。不能仅凭命名规则自动认定已复核。
2. bigint 使用 Java BigInteger 的精确数值能力；上游 BigNumber 仍保留自己的兼容类，不能直接用 BigInteger 替换其公开状态或返回自身的可变操作。TS number、number[]、Uint8Array 分别处理，不能全部转换为 int 或 byte[]。
3. 可省略参数的默认值按源码表达式和求值时机保留。不得把每次新建的数组、Map、对象变成共享静态默认值；缺失、undefined、null 和空值按测试契约区分。
4. Promise 返回接口采用 CompletionStage 表达异步完成，原同步接口保持同步。异常拒绝、回调先后、取消与清理仍要分别复刻，不能只在同步方法外套 completedFuture。
5. 常规 Error 对应 `com.metanet4j.bsv.errors.SdkException`，TypeError 对应其子类 SdkTypeException，RangeError 对应 SdkRangeException；原错误消息、码、字段和触发时机保留。WalletError、ScriptEvaluationError、ScriptResourceLimitError、TransactionEvidenceError 保留各自类型与字段。Java CompletionException 等调度包装只在结果采集边界按已登记规则解包，不能吞掉原始失败。
6. 原测试直接检查 BigNumber/Hash 等内部状态的断言必须保留。优先在同包测试中访问等价状态；不得为了遵从技能的常规封装建议删除这些断言。最终访问方式仍需在逐项映射中登记，不提前给生产 API 增加任意调试入口。
7. 每个 Java 预期来自固定 TS 原断言、原向量或记录的 TS 实际输入输出，不能由 Java 被测实现生成。随机、时钟和环境能力通过后续确定性重放处理；独立探针只用于确认行为，不能充抵上游用例或迁移 PASS 数。

### API-VALUES

数值和容器采用以下表示。它们是 Java 设计约束，P1 按原用例逐行为 TDD 创建实现，不在 P0 提前批量建类或测试。除 JDK 类型外，表内类型归属 `com.metanet4j.bsv.primitives`。

| TS 值 | Java 表示及转换时机 |
| --- | --- |
| number | 一般使用 double/Double，保留 NaN、Infinity、负零及 IEEE 754 舍入。不能在入口统一改成 int/long；位运算按 TS 的 ToInt32/ToUint32、位移计数掩码处理，字节写入才做 ToUint8。Java 强制窄化的饱和规则不能代替取模规则 |
| bigint | BigInteger，精确构造和运算，不经过 double；与 number 的混合入口用 Object 分支识别。Java 调用者的常规 Number 按 TS number 解释，大于安全范围的精确整数须用 BigInteger 或原字符串 |
| undefined、null、对象缺字段 | `Undefined.INSTANCE`、Java null、Map.containsKey 分别表示；不统一使用 Optional.empty。返回值可能为 undefined 的读接口用 Object；数值仍返回 Double，不能用 NaN 冒充 undefined |
| number[] / any[] | 保留列表身份与元素值；只读输入用 List<?>，需要原样存取或写回的动态列表用 List<Object>；保证只产出 number 的新列表可用 List<Double>。不得在复制前截断浮点数、负数或替换元素 |
| 稀疏数组 | List 中的 `ArrayHole.INSTANCE` 表示缺索引，与显式 Undefined 不同。索引读取按 undefined；slice 保留空洞，Array.from/迭代在相应位置产生 undefined，JSON 数组位置序列化为 null。后续采集还必须记录索引是否存在，不能只看 JSON 数组 |
| Uint8Array | `ByteView` 保存 backing byte[]、offset、length，描述信息固定，内容可变；读为无符号 0..255。subarray 共享 backing，slice 创建新 backing；可比较 Java 引用及 backing 身份、观察偏移。不能提前复制所有输入，也不能把 JDK ByteBuffer 的可变 position/limit 带进该契约 |
| WriterChunk | Object 承接 List<?> 或 ByteView；不为每个输入再造包装对象。旧 Writer 保留传入的列表/视图引用，新 Writer 在 write 时复制并转换 |
| 普通对象 / Symbol | 对象使用保留插入顺序的 Map；`JsSymbol` 保留 description 缺失与空字符串的区别及符号身份。仅为原 SDK 接口和测试实际使用的值提供桥接，不创建通用 JS 解释器 |

逐项 javaSignature 保存完整参数形式；凡源码具有默认值或可选尾参数，Java 同时提供相应省略尾参数的重载，委托时传 Undefined，再由完整入口按源码求值。需要省略中间参数时直接传 Undefined，例如 `new BigNumber(number, Undefined.INSTANCE, "le")`。null 只在源码明确 `??` 或 null 检查的地方触发对应行为，不自动等同于省略。布尔分支分别保留 truthiness 与 `=== true` 的区别。

映射包括所有内部声明，是为了追溯行为覆盖，不要求 Java 按行复制私有函数。记录指向所属 Java 类的内部算法可合并或用 JDK 实现，但原测试观察的状态、异常顺序和对象身份不能消失。BufferCtor/CAN_USE_BUFFER 由对应类的编码路径承接，不公开 Node 的 Buffer 对象；Buffer 存在/缺失环境的原测试均需复刻，并记录其实际结果。具体 Java 宿主替换入口在剩余平台契约中完成。

### API-UTILS-ENCODING

toArray 对 List 做浅复制并保留元素/空洞；Undefined 得空列表；非字符串走 Array.from 的截断语义；字符串才按 enc 分派。toUint8Array 对 ByteView 返回同一对象，对其他输入复制并转换。encode 在 enc 非 hex/utf8 时返回传入列表本身，不能无条件复制。

hexToUint8Array 先使用 hex 校验，奇数位补前导零，输出无符号字节；hexToArray 再复制为普通数值列表。zero2 只按字符长度补零。toHex 保留 Buffer/无 Buffer 的原测试语义。

base64ToArray 的校验不能用“更严格”的解码器替代：接受 URL-safe 字符及指定空白，只校验尾部 1/2 个等号格式；源码的非零 padding bits 校验已经注释掉。实际 `Z → []`、`Zh → [102]`、`Zh== → [102]`、`Z=== → Error('Invalid base64 padding')`。非法字符文本包含原字符串中的索引；按 UTF-16 code unit 遍历及 codePointAt 行为处理。toBase64 逐组执行源码位运算和 charAt，不能先将任意 number[] 强转为字节再编码。

UTF-8 遵循 TS TextEncoder/TextDecoder 的可见行为：孤立 surrogate 编码为 U+FFFD 的 `ef bf bd`；默认解码去掉开头 BOM；非法序列的替换数量也要一致。探针 `ed a0 80` 解码为三个 U+FFFD。Java 默认 String.getBytes/解码替换策略不能未经原向量核对直接作为等价实现；按原用例补足这些明确差异。

### API-UTILS-BASE58

fromBase58 必须保留空/非字符串拒绝和弯引号错误消息、非法字符按出现顺序汇总、前导 1 对应零字节。toBase58 保留前导零和原数值运算顺序；不能靠十进制字符串往返而丢失零前缀。

### API-UTILS-DIAGNOSTICS

### API-BN-CONVERSION

构造默认 `(0,10,'be')`，number 的 null/Undefined 经 nullish 归零；字符串、number、BigInteger、列表走不同分支。base 为 le/be 时重解释为端序，'hex' 等价 16，其他进制须为整数 2..36；字符串去除 JS 空白，单独的 + 或 - 为零。普通 number 先执行 BigInt(abs(number)) 再断言安全范围，因此 1.5/NaN/Infinity 的错误类型、消息和触发顺序不能改成同一个参数异常。

十六进制 BE 严格解析，LE 按双字符 parseInt；实测 `new BigNumber('1g',16,'le') → 1`，BE 为 `Invalid character in 1g`。这与 Hex.normalizeHex 的严格规则不同，不可合并为一个严格入口。数组构造按元素位运算取低字节。符号在字节端序转换后保留。

toString 的 hex padding 按源码处理偶数位及指定倍数，其他进制是最小宽度；toJSON 是其 hex 表达，不等同 toHex。toNumber 拒绝超出 ±(2^53−1)，toBigInt 精确返回。零值分别为 `toHex()=''`、`toJSON()='0'`、`toArray()=[0]`、`toSm()=[]`、bitLength/byteLength/toBits=0，不能统一为空或一个零字节。

toArray 先 strip 当前对象，再检查目标长度；失败仍保留 strip 的副作用。nullish length 使用至少 1 字节，按 magnitude 编码而非二进制补码。静态/实例 toBitArray 均按最低有效位在前，零返回空列表。bitLength/byteLength/zeroBits 各自保持零输入分支。

fromHex 接受 little/le 别名，其余为 BE；fromString 保留显式 Undefined 的默认 base。fromSm 先复制并按端序处理符号位，不修改输入；toSm 根据最高位补符号字节。fromScriptNum 先检查可选 maxNumSize，再处理空值和 requireMinimal，最后按小端 signed magnitude；toScriptNum 委托 toSm('little')。fromBits/toBits 保留指数、mantissa、负号位和无符号 32 位结果，strict 分支不自行放宽。

### API-BN-BITS

toTwos/fromTwos 保留指定位宽的掩码及符号判断，返回新 BN。带符号 and/or/xor/i* 校验双方非负；无符号 u* 对 magnitude 运算并按原代码保留符号和 nominal 状态。非原地 uor/uand/uxor 会克隆 nominal 较长的操作数，相等时克隆 this，不能总是复制左操作数。

inotn 保留指定宽度对应的 nominal 长度；maskn 按其自身规则规范长度；setn 只有 val===1 或 true 才置位，其他值清位，不能简单使用 Java truthiness。bincn、testn 和 andln 保留独立限制及按位结果。

### API-BN-ARITHMETIC

add/sub 返回新对象；iadd/isub 更新当前对象并保留 red。mul/imul/sqr/isqr/mulTo 的 nominal 长度按原公式处理，并清除 red；mulTo 返回 out 对象，out 与输入别名时也要保持源码语句顺序。iaddn/isubn/imuln/idivn 及其委托方法限制绝对值 ≤2^26−1，但错误文本各自保留，不能统一，例如 imuln 越界为 `Assertion failed`，iaddn 为 `num is too large`；不能将此上限推广到没有该检查的 modrn/andln。pow 使用非负指数；neg/abs 与 ineg/iabs 的复制/变异区别保留。

divmod 使用向零截断商和带符号余数；positive 仅在严格 true 时规范余数。Java 返回可变、保序 Map，包含 div/mod 两个键，不使用 Optional；被 mode 排除的结果为 null。分子为零且两项都需要时，两个键指向同一个零 BN。divRound 按半数远离零，零除的校验消息与 divmod 不同。modrn 根据除数符号返回结果，不可直接使用带符号 BigInteger.remainder 替代。

egcd 返回 a/b/gcd 三个字段，gcd 非负，保留原系数；invm 校验 gcd=1。`_invmp` 是公开可调用方法，执行模 p 的 Fermat 指数 p−2，不做素数检查；不能直接改用 modInverse。实测 3、模 8 时 `_invmp → 1` 而 `invm → 3`。这项差异属于固定上游行为，未授权修复。

cmp/cmpn/ucmp 只返回 -1、正零、1；原测试验证 `1 / result === Infinity`，Java 复刻时须用浮点除法，不能引入整数除零异常。大小、相等、奇偶和零判断保留各自委托关系及 small-number 限制。

### API-REDUCTIONCONTEXT

23 项声明全部映射。构造传入 BigNumber 时保留原 m 对象并校验 m>1；传入字符串 k256 时新建 K256，m 指向其 p，prime 指向它。public m/prime 保持可变，不通过复制改变别名。

verify1 只检查 a 非负且存在 red；verify2 只检查双方非负、a.red 非 null 且与 b.red 相同，**并不要求它们的 red 就是接收调用的 this**。实测另一上下文的同一 a 可通过这两个检查，不能顺手收紧校验。各入口按源码决定是否调用 verify，不在所有方法前统一插入校验。

pow 先 verify1，再按指数 magnitude 的 bitLength/testn 执行平方乘法；没有额外的负指数拒绝。实测模 17 下 3 的指数 -2 返回 9，不是模逆幂。invm 仍调用 BigNumber._invmp，保留其假设和符号分支。

### API-MONTGOMORYMETHOD

12 项声明全部映射。类名保留上游拼写 MontgomoryMethod，继承 ReductionContext。shift 向 26 的倍数上取整；r、r2、rinv、minv 的公式、计算顺序和 BN/red 状态逐项保留，不只保存一个 modulus。字段 public，可被测试及调用者观察。

convertTo 先左移 shift 再 imod；convertFrom 乘 rinv、imod 再清除 red。mul/imul 的非零分支保留 maskn、minv/m 相乘、减法、无符号右移以及最后仅一次范围调整。invm 乘 r2 后 imod 并 forceRed。覆盖方法没有显式 verify2 的地方，不自行增加与父类一样的检查。

**固定上游的零乘异常**：imul 的零分支先写入 `a.words[0]`（getter 返回的临时数组），再赋值只有 getter 的 a.length，实际抛 TypeError，a 的数值没有变成零。探针中 a 的原始红域值为 12，失败后仍为 12；错误为 `Cannot set property length of [object Object] which has only a getter`。Java 保留对应 SdkTypeException 和失败前状态；非原地 mul 的零分支仍返回新零 BN。此项未获修复授权，不能套用 WUA-ZERO-CAPACITY 的授权改变它，也不能因数学结果应为零就掩盖失败。

### API-MERSENNE

11 项声明全部映射。构造由十六进制 p 得到 n=bitLength(p)、k=2^n-p；name/p/k/n 保持公开可变。tmp 是每实例私有固定引用的可变 BN，按 ceil(n/26) 至少一词扩容，不改成跨实例共享对象。

ireduce 原地返回 num，保留至少一次 split/imulK/加 tmp 的循环、最后与 p 比较及 strip 顺序；相等时通过 words=[0] 归零。split 将低 n 位写入 out，并在 input 中保留高位；imulK 调用 num.imul(k)。tmp 的复用和 BN nominal 状态属于行为，不仅检查模运算的数学结果。

### API-K256

4 项声明全部映射，继承 Mersenne。固定名称 k256、素数 `fffffffffffffffffffffffffffffffffffffffffffffffffffffffefffffc2f`、n=256 和 k=2^32+977。

split 按 26 位 words 和 nominal length 分支，前 9 词与第 10 词的低 22 位进入 output；其余位重组 input，两个 words setter 的执行顺序保留，包括 input 与 output 别名时的最终状态。不能直接用 BigInteger 除余后 strip 所有结果：实测数值 1、expand(12) 后，split 得到 input 数值 0/length 3，output 数值 1/length 10。

imulK 使用 0x3d1 与 0x40 的乘加进位，给原 nominal length 增加两词，再经 words setter 写回并返回同一 num；不额外 strip。实测零值 expand(4) 后 imulK 仍为零，length 为 6、words 六项全零。

<a id="api-hash-input"></a>
#### Hash 输入、编码和字节序

- 自由函数映射为 `Hash` 的静态方法，公开 SHA/RIPEMD/HMAC 类保持顶层类名。内部同名 `Hash<T>` 映射为 `Hash.HashCore<T>`，避免与模块工具类冲突；内部 HashMD/FastSHA256/FastSHA512/HMAC/Hasher/IHash/FallbackHashLike 为 Hash 的嵌套类型。非导出的 BaseHash 为包内父类，其公开继承状态保留。Object 联合入口接受 String、List、ByteView 及契约已有缺失值，完整签名和省略参数规则沿用 API-VALUES。
- `Hash.toArray` 和 `Utils.toArray` 不合并：前者对 List 先 slice 复制，保留越界值、浮点、NaN、负零和空洞；falsy 输入返回新空列表；字符串只有 enc 严格等于 hex 才调用 Hex 校验/奇数补零；否则逐 UTF-16 code point 转换。**孤立代理项保留其三字节编码**，例如 `\ud800 → ed a0 80`，不能用默认替换字符的 JDK UTF-8 编码代替。其余 array-like 输入按 length 逐项 Math.trunc，不在此截断成字节。
- `toHashBytes` 对 ByteView 保留引用，对 List 按 ToUint8 新建字节视图，其余先 Hash.toArray 后转字节；`toHashKeyBytes` 的字符串一律按 hex，消息的 enc 不影响 key。`HashInput` 用 Object 承载该联合；内部 Input 仅 String/ByteView，TypedArray 内部以 ByteView 或 int[] 等对应位宽数组表示，不新增对外容器协议。
- 内部 `toBytes/utf8ToBytes` 使用 TextEncoder 的替换规则（孤立代理项为 U+FFFD），与上面的 Hash.toArray 路径不同；ByteView 原样返回。`isBytes/abytes` 保留跨 realm Uint8Array 和错误类型/长度校验，不将任意数组当 Uint8Array。JVM 内部以同一种 ByteView 表示这些跨 realm 实例；原测试跨 realm 的原始类别在重放记录保留。
- `join32` 要求长度为 4 的倍数，对输入直接做 JS 位运算，不逐元素先 `& 255`；因此越界数可影响相邻位。split32 产生新字节列表；toHex32 按 word 的基数 16 字符串和 zero8 规则处理，不无条件截短。Buffer 能力在加载时确定，bytesToHex 两条路径都返回小写 hex。
- `htonl` 是 `swapBytes32` 的行为别名；二者无条件换序并返回无符号 32 位数。`realHtonl` 按宿主字节序决定换序或 ToUint32，Java 使用 ByteOrder.nativeOrder，测试可独立设置宿主字节序上下文。number 接口保留 double，不因 Java int 有符号而改变 0xffffffff 的结果。

<a id="api-hash-base"></a>
#### BaseHash、SHA1、RIPEMD160

BaseHash 的 pending 初始 null、pendingTotal 初始 0；blockSize/outSize/hmacStrength 保留 bit 单位，padLength 在构造时除以 8，delta8/delta32 分别除以 8/32，endian 初始 big。RIPEMD160 配置 512/160/192/64，endian 改 little；SHA1 配置 512/160/80/64，保留公开 h、W、k 及数组身份。W 的初始元素是 undefined，不是假定全部 0。

update 先执行 Hash.toArray，追加 pending 并累加原始元素个数；满块后先更新剩余 pending（空则 null），再 join32、逐块 `_update`，返回自身。失败前的状态变化保留。`digest/digestHex` 每次都将 `_pad()` 交给 update，确认 pending 严格为 null 后调用输出方法；**无 finished 标志，也不复位**。重复 digest 或摘要后 update 继续累计状态，不能使用自动 reset 的 MessageDigest 直接替换。

`_pad` 原测试通过 TS any 访问，Java 设计为包内同名方法，保留原断言而不新增公开调试接口。先校验 pendingTotal 为非负安全整数，再算块填充；用 BigInteger 生成完整长度位域，若 `len*8 >= 2^(padLength*8)` 则抛 SdkException，消息 `Message too long for this hash function`。负数、小数、NaN、超过安全整数和手动缩短 padLength 均不可漏测。原 `_update/_digest/_digestHex` 基类实现抛 `Not implemented`，不改为 Java 抽象方法而丢失可观察异常。

SHA1 的 `_update` start 按 `??=0` 处理缺失和 null；RIPEMD160 没有这一默认值。二者直接输出方法只读取当前 h，不填充、不清理；返回新列表/字符串。SHA1 80 轮及 RIPEMD160 双路 80 轮、r/rh/s/sh 表和 K/Kh 分段常量按固定源码保留。sum32 系列返回 ToUint32；轮转、布尔组合返回 ToInt32；不能把全部中间结果统一为 Java 有符号 int 后直接暴露。

<a id="api-hash-platform"></a>
#### SHA256、SHA512 与同步后端

同步 NODE_CRYPTO 与 AsyncCryptoBackend 是不同机制。Hash 在模块初始化时查 globalThis.process.getBuiltinModule，绑定接收者调用并捕获加载异常；createHash/createHmac 缺失或构造抛错才返回 undefined 并选择 fallback。已选后端的 update/digest/PBKDF2 失败直接传播，不能捕获后改算纯实现。一次性函数每次新建摘要对象；流式 SHA256/SHA512 构造时选择并固定后端，只有 native 或 h 一个有效。update 先转换输入再调用所选后端，返回自身。

Java 设计：生产缺省同步宿主配置对齐固定 Node 原生分支，用 JCA 的 SHA/Mac 等计算能力加 SDK 兼容状态/校验；算法不可用时按源码进入 fallback。RIPEMD160 可使用本模块纯算法承接宿主接口，输入转换仍遵循所选择的分支。原生可用性、加载/构造失败、Buffer 和字节序由包内 `Hash.Runtime` 上下文表示；每个隔离测试创建新上下文，加载时捕获 NodeCrypto 对象（后续方法替换仍可见）。原公共构造和静态函数不增必填参数；包内上下文入口供原环境测试和确定性采集，不增加外部注册服务。Map/Object 表示宿主能力槽，调用通过明确的 createHash/createHmac/pbkdf2Sync 适配，不构造通用 JS 解释器。宿主错误转换为 SdkException/SdkTypeException/SdkRangeException，保留原 name/message/code，不泄漏 JCA 原始异常文本。

| 生命周期 | 固定 Node 24.14.0 原生路径 | 纯 TS 路径 |
| --- | --- | --- |
| SHA256/SHA512 首次 digest/hex | 返回 32/64 字节，实例终结 | 返回相同字节，finished=true，清零状态与 buffer |
| 上述类第二次 digest 或再次 update | Error：`Digest already called`，code=`ERR_CRYPTO_HASH_FINALIZED` | Error：`Hash#digest() has already been called` |
| SHA256HMAC/SHA512HMAC 第二次 digest/hex | 返回新空列表/空串 | Error：`Hash instance has been destroyed` |
| 上述 HMAC 摘要后 update | Error：`Digest already called`，同一 code | Error：`Hash instance has been destroyed` |

公开 SHA256/SHA512 实际没有 BaseHash 的 pending/blockSize 等状态，不按过期注释添加继承。`ripemd160` 原生路径先 ToUint8，纯路径直接 BaseHash；输入 `[256,-1,3.5]` 的两种摘要实际不同，Java 必须按环境选择相同分支。sha1 始终走 SHA1；hash256 是两次 SHA256，hash160 是 SHA256 后 RIPEMD160，第二次输入始终为字节，不再次套消息 enc。正常字节输入两种环境的原测试和探针摘要相同，并不证明所有 JS 输入相同。

<a id="api-hash-fast"></a>
#### Fast SHA 核心与 HMAC 内部状态

内部 HashCore 的 update/digestInto/digest/destroy/clone/_cloneInto 和长度访问接口完整保留；具体子类为 blockLen/outputLen 字段提供同名只读访问方法。IHash/Hasher 的可调用对象映射为 `apply`，create、blockLen、outputLen 映射为方法。原 hmac.create 是函数属性（不另产生 AST 声明 ID），Java 明确映射为包内 `Hash.hmacCreate`；不能因清点没有单独计数而遗漏。FallbackHashLike 映射为包内接口，只有 update/digest，HashCore 实现该接口；允许多个原内部声明合并实现，但各映射证据保留。

HashMD 构造初始化独立 buffer 及同 backing 的 ByteBuffer view，finished/destroyed=false、length/pos=0。update 先 aexists、转字节并校验，再分整块直读和余量复制，累加 length、清理轮次工作区，返回自身。digestInto 先检查状态和输出至少 outputLen，才 finished=true，填充、写低 64 位 bit 长度、压缩、校验输出对齐/状态长度并写输出前缀，输出剩余部分保留。SHA512 的 padOffset=16，但该实现只写尾部 8 字节长度，不能改成另一种观测状态。digest 将 buffer 作为输出，slice 复制后 destroy。

clone/_cloneInto 复制状态、length/pos/finished/destroyed；只有 length 非整块时才复制 buffer。to 为 null/undefined 才新建，否则复用传入实例。FastSHA256/FastSHA512 的 destroy 清零 buffer 和状态，**不设置 destroyed，不复位 finished/length/pos**；手动 destroy 后仍可 update，不能擅自修复。HMAC.destroy 则设置 destroyed=true，再销毁内外摘要；aexists 总是先检查 destroyed，再检查 finished。

FastSHA256 的 8 个状态、64 轮 K/W，FastSHA512 的 16 个高低状态、80 轮 Kh/Kl/W_H/W_L 均有映射。常量表保留原位模式；内部 TypedArray 用 Java int[] 承载时按读操作解释为无符号，普通 number 状态仍保留源码的有/无符号转换时机。fromBig 的 le=true 交换高低并返回无符号，le=false 返回有符号；add/旋转/移位按 32 位掩码，add3H/add4H 是 Math.trunc，add5H 为 ToInt32，不一概替换为同一窄化操作。共享 W 在单线程 TS 每轮清理；Java 采用实例工作区或局部数组避免跨线程污染，未完成实例的可观察状态不受影响。

HMAC 核心先 ahash，再转 key，构造 iHash 并验证 update 可调用；key 超块则先摘要，零填充后 xor 0x36/0x5c 初始化内外状态并清理 pad。digestInto 要求输出**恰好** outputLen，设 finished、依次算内外摘要后 destroy。clone 复制独立内外状态并保留标志，可复用旧对象，这是 PBKDF2 的关键依赖。anumber/abytes/aoutput/ahash/aexists 的验证顺序与错误文本按源码，不能由 Java 类型系统提前消除全部错误路径。

<a id="api-hash-hmac"></a>
#### 公开 HMAC

SHA256HMAC、SHA512HMAC 的 key 都先 `toHashKeyBytes`；字符串按严格 hex，奇数补零，空串有效，含空格或非法字符拒绝。HMAC.test.ts 的空格由**原测试自身** normalizeKey 去除，生产 API 不增加容错。update 返回自身；digest 返回新无符号字节列表，digestHex 小写。一次性 sha256hmac/sha512hmac 的 enc 只用于消息；后端缺失时按源码委托包装类。

SHA256HMAC 的 blockSize/outSize 为 64/32；**SHA512HMAC 实际为 128/32，输出仍是 64 字节**，保留可写字段及这个值，不按注释改为 64。改变这两个包装类字段不重新配置内部摘要。SHA1HMAC 则公开 inner/outer 两个 SHA1 和 blockSize=64，构造先复制 key，超过 64 字节先 SHA1，再填充和异或；每次 digest 将 inner.digest 追加到 outer 后继续 digest，不加终结保护。

<a id="api-hash-pbkdf2"></a>
#### PBKDF2

公开 `Hash.pbkdf2(Object password, Object salt, Object iterations, Object keylen, Object digest)` 用 Object 保留 undefined/null/错误类型；digest 省略才默认 sha512，先严格拒绝其余值，错误为 `Only sha512 is supported in this PBKDF2 implementation`。输出新字节列表，长度单位为字节。不能直接把 byte 密码交给按字符解释的 PBEKeySpec。

原生存在 pbkdf2Sync 时：先 toHashBytes(password/salt)，再调用宿主；整数/范围错误保留 Node 的 TypeError/RangeError 和 code，实际异常不回退。固定环境中 keylen=undefined/null 为 TypeError，keylen=0 为 Error `Deriving bits failed`。iterations 必须整数且 1..2147483647，keylen 为整数且 0..2147483647，然后由实际算法执行；可用 JCA Mac 计算 PBKDF2，但外层校验与错误必须对齐固定宿主。

fallback 先对 password/salt 做 Uint8Array.from，再调用 pbkdf2Fast/Core；Core 顺序为 ahash、c 的非负安全整数校验、dkLen 同样校验、c>=1。dkLen 仅 undefined 默认 32，0 返回空字节；null 拒绝。错误包括 `positive integer expected, got ...`、`iterations (c) should be >= 1`。异常输入 string 在这条路径按 iterable 字符 ToUint8，与原生的 UTF-8 输入存在实测差异。保留路径，不统一成“参数先规范化”。

Core 用 HMAC-SHA512，块编号从 1 起、4 字节大端，PRF/PRFSalt 克隆重用，U1 后再执行 c-1 次并按需截断异或，最后销毁 PRF、PRFSalt、工作克隆并清理 U。dkLen=0 仍执行初始化和收尾。所有 13 个原向量（含跨摘要块的 100 字节、Unicode/NUL 和 4096 次迭代）均已运行；不以少量标准向量替代原文件。

<a id="api-drbg"></a>
#### DRBG

DRBG 保留公开可变 `K/V` 列表及 constructor/hmac/update/generate 全部成员。只用于原 ECDSA 确定性 nonce；不替代 Random。构造先分别 Utils.toArray(entropy/nonce,hex)，**两次转换完成后**才校验 entropy、nonce 恰好 32；例如 entropy=[]、nonce=zz 先报 `Invalid hex string`。长度错误分别为 `Entropy must be exactly 32 bytes (256 bits)` 和 `Nonce must be exactly 32 bytes (256 bits)`，不是旧注释的“至少 32”。种子为两数组拼接，新建 32 个 0 的 K、32 个 1 的 V，再 update(seed)。

hmac 每次以当前 K 创建新的 SHA256HMAC。update(seed) 先算 K=HMAC(K,V||00||seed)、再 V=HMAC(K,V)；seed 严格 undefined 时返回，否则再做 01 轮及一次 V。K/V 每次替换新列表，旧引用保留旧值。seed=[] 与 seed=undefined 不同；null 在当前 Hash 转换下等于空内容但仍执行第二轮。Java update(Object seed) 加无参重载，不能把缺失、null、空列表合并。

generate(double len) 每轮 V=HMAC(K,V) 并拼接 32 字节，最后按 JS slice(0,len) 截取，**始终 update()** 后返回小写 hex。0、负数、NaN 输出空串但仍推进状态；1.5 产生一个完整块后只返回 1 字节，33 需两块。没有上限或安全整数校验，不擅自新增；Infinity 原循环不终止，未执行该危险输入也不声称等价测试通过。原 29 用例中的状态推进、输入形式、RFC6979 sample/test 实际结果全部保留到未来 TDD 映射。

<a id="api-random"></a>
#### Random 随机源

默认导出函数映射为 `Random.random(double len)`；内部 Rand 为 `Random.Rand`，_rand 为 DoubleFunction<List<Double>>，ayn 是延迟创建并缓存的实例。Java `Random.Runtime` 是包内隔离上下文，包含 global/self/window 的 crypto 能力槽及 process.getBuiltinModule；生产以 SecureRandom 支持缺省 global WebCrypto 槽，测试按原环境逐项提供能力和调用记录。默认函数的签名不暴露浏览器对象；模块隔离对应新 Runtime 与空 ayn，禁止各测试共享污染后的单例。

选择顺序严格 globalThis.crypto.getRandomValues → self.crypto.getRandomValues → window.crypto.getRandomValues → process.getBuiltinModule('node:crypto').randomBytes → noRand；判断必须是可调用函数。global/self/window 路径每次调用重新读取对应对象/方法，Node 路径捕获 crypto 对象后动态读 randomBytes。WebCrypto 分配 Uint8Array、调用一次并忽略函数返回值，最后从被填充数组复制 number[]；Node 从 randomBytes 返回值复制。noRand 的构造成功且被缓存，后续新增能力也仍报 `No secure random number generator is available in this environment.`；getBuiltinModule 抛错则构造未完成，下一次调用会重试，不 catch 成 noRand。

WebCrypto 路径先按 ToIndex 分配（1.5→1、NaN/-0.5→0、-1 为 RangeError），再检查单次请求 65536 字节限制。超过限制固定宿主抛 QuotaExceededError、code=22、消息 `The requested length exceeds 65,536 bytes`，Java 用保留 name/code 的 SdkException 表示，不擅自分块绕过。Node 路径不受此配额限制，但拒绝负数/NaN，保留 RangeError、ERR_OUT_OF_RANGE 和原文；1.5 实测产生 1 字节。真实熵仍用安全随机源，未来 TS 原随机用例采集每次请求的输入/返回字节，Java 重放相同序列且检查消费次数；不能要求两次独立物理随机运行得到相同字节，也不能只比较长度就声称结果一致。

<a id="api-curve"></a>
### API-CURVE 曲线和点

本批次覆盖 BasePoint、Curve、JacobianPoint、Point 四个完整源文件的 153 项声明。Java 入口分别为 `BasePoint`、`Curve`、`JacobianPoint`、`Point`；Point.ts 文件级导出的整数常量、域运算和 Jacobian BigInt 算法收于 `PointBigInt`。逐项声明与 Java 符号以 [api-map.json](../api-map.json) 为准，实际可用性还须由本批次原测试及逐断言证据确认。

`Curve` 固定为 secp256k1：域素数 p、群阶 n、系数 a=0/b=7、生成点 g 及其 doubles/NAF 预计算数据均来自固定源码。TS `new Curve()` 返回进程内同一个实例；Java 通过 `Curve.shared()` 提供单例入口，需保持生成点、约减上下文及可观察的预计算状态一致。TS `cachedProperty` 修改原型并懒计算；Java 用显式实例 Map 与 Supplier 表达同一首次读取/缓存行为，缓存值为 `Undefined.INSTANCE` 时重新计算。NAF、JSF 和小端整数转换保留原输入、位宽与数组顺序。`validate` 对无穷点返回 true，对非无穷且坐标为 null 的点抛出原消息，再按模 p 曲线方程判定。

Endomorphism 保留 beta、lambda、两个基向量，以及由缺省配置推导这些值的路径。根计算分别在 p 与 n 上执行，beta 选择较小根，lambda 以生成点乘法和 beta 作用后的 x 坐标选择；无法取得生成点、坐标或根时保留原拒绝边界。`endoSplit` 用两个基向量和 divRound 分解标量，须满足 `k1 + k2 * lambda ≡ k (mod n)`。预计算表、按点求反时传播表、Jacobian 与仿射坐标转换均按原测试的状态和实际值核对。

`Point` 构造器区分 `isRed`：true 对传入 BigNumber 强制标记 red 上下文，false 在未标记时转换；无穷点用 null 坐标表示。DER 接受压缩 02/03、非压缩 04、混合 06/07，混合编码先核对 y 奇偶，再校验点在曲线上；非法格式、错误长度、无平方根和离曲线点按固定 TS 错误边界拒绝。JSON 字符串和坐标数组都需解析；doubles/NAF 嵌套点逐个验曲线，序列化时不重复写入表头的自身点。`mul` 和 `mulCT` 按固定 Point.ts 先对绝对标量取 **p 模**、最后恢复负号；此处 p 模是固定实现的实际行为，不擅自改为群阶 n。`mulCT` 只描述固定运算序列，不将 JVM BigInteger 宣称为侧信道常数时间实现。`mulAdd`、`jmulAdd`、NAF/endomorphism 内部运算应与对应原测试及直接 API 行为一致。

`PointBigInt` 承接 Point.ts 直接导出的 `red`、`biMod*`、`jpAdd/jpDouble/jpNeg`、`scalarMultiplyWNAF`、`modN/modMulN/modInvN` 和相关常量；JacobianPointBI 用可写 Java 类承载 X/Y/Z。该文件级导出独立于 `Point` 对象方法，不能仅凭 `Point.mul` 测试通过而视为已验收。Java 的 `Point.fromJSON(String, ...)` 需要解析 JSON，因此现有 Jackson 依赖进入生产编译作用域；其他模块不因此获得通用 JSON 行为。

<a id="api-keys-signatures"></a>
### API-KEYS-SIGNATURES 密钥与签名

本编码任务完整收口 ECDSA、Polynomial、PrivateKey、PublicKey、Schnorr、Secp256r1、Signature 七个源文件的 129 项声明。API-05 批次还包含归后续交易任务的 TransactionSignature 和 primitives/index.ts；本任务只对七个文件声明负责，不提前把整批次标为完成。逐项 Java 符号、签名及源码位置见 [api-map.json](../api-map.json)。

ECDSA.sign 对超过群阶位数的消息直接拒绝，默认 `forceLowS=false`；传固定 customK 时无效值直接报错，传函数时可按迭代次数重试。PrivateKey.sign 先对消息 SHA-256，再显式以 `forceLowS=true` 调用 ECDSA，两处默认值不能合并。Signature 的 DER 解析保留 short-form 长度及前导零校验；compact 与 DER 编码分别保留原头字节、长度和异常。TS 的 `Signature.toString()` 无参数返回数组，但 Java `Object.toString()` 必须返回 String；Java 用显式 `toString(Undefined.INSTANCE)` 表达省略参数的数组结果，`toString("hex")` 表达 hex 结果，不改变 Object 的覆盖规则。

PrivateKey 继承 BigNumber；构造默认按曲线阶 n 归约，`modN=error` 对越界报 `Input is out of field`，`nocheck` 保留原值。fromWif 需要 33 字节数据和末尾 0x01；toWif 对越界报 `Value is out of field`。BRC42 私钥子键按压缩 ECDH 点与 UTF-8 invoice 计算 HMAC-SHA256 后在 n 中相加；公钥子键在原点上加相应生成点倍数。Shamir 拆分/恢复在曲线域 p 中执行，原密钥是 x=0 截距；x 值按固定 HMAC-SHA512 输入、非零和去重重试规则生成。10,000 次随机密钥原测试保留原规模，并将 TS 实际随机输入记录后由 Java 重放。

PublicKey 继承 Point；66/130 字符的 DER hex 不能交给构造器误当坐标，须通过 fromString/fromDER。toDER 采用压缩点，toHash 对压缩点作 HASH160；toAddress 的 main/mainnet/test/testnet 与显式字节前缀按原分支处理。ECDH 先验证公钥点，再求共享点；无效点报 `Public key not valid for ECDH secret derivation`。

Schnorr 证明由 `{R, SPrime, z}` 组成：随机标量 r 经 PrivateKey.fromRandom 取得；挑战值为 A、B、S、SPrime、R 五个压缩点串接后 SHA-256 再模 n。验证分别核对 `zG = R + eA` 与 `zB = SPrime + eS`，空输入的 TypeError 保留原消息。原测试中的随机密钥序列由 TS 实际调用记录并在 Java 重放。

Secp256r1 使用独立 P-256 曲线，点编码支持压缩 02/03、非压缩 04 和无穷远 00，解码时核对点是否在曲线上。签名对消息 SHA-256 或接受预哈希输入，nonce 由 HMAC-SHA256 确定性生成，规范化 low-S，r/s 各编码为 32 字节 hex；验证接受点对象或编码。字符串消息为偶数长度的全 hex 时按 hex 解释，否则按 UTF-8，字节数组与 ByteBuffer 保持原字节。P-256 原测试中的 Random(32) 输入由 TS 记录并在 Java 重放；Node ieee-p1363 互操作仍以原测试的实际结果验收。

<a id="api-symmetric"></a>
### API-SYMMETRIC 对称加密与可选后端

AESGCM 的字节 API 接受 16/24/32 字节 AES key、非空 IV、无 AAD，并使用 16 字节认证标签。12 字节 IV 直接构造 J0，其他长度经 GHASH；Java 的 `AES/GCM/NoPadding` 与 `AES/ECB/NoPadding` 映射原加密/GCTR 行为。固定 NIST/TS 小向量及空明文标签已对照；源码注释所说额外零块在这些输入上不改变初值为零的 GHASH 结果，不能仅凭注释判定 provider 不兼容。公开的 checkBit、getBytes/getBytes64、XOR、rightShift、GF(2^128) multiply/ghash 与低 32 位计数器环绕保留独立 Java 入口；私有轮函数和密钥展开逐项映射到 JDK provider。空 IV/key 保留原异常，空密文先拒绝，认证标签错误返回 null。纯 GCTR/GHASH 路径保留用于无 provider 情形并与原向量对照。

AsyncCryptoBackend 是进程全局可选槽位：注册覆盖当前值，只按对象身份注销。ready 缺失、未就绪或不支持目标操作时返回 undefined（Java 适配为 null）；未就绪触发后台 preload，但本次调用不等待。仅已就绪且支持时选用后端，已选结果权威。32 字节 digest 的每个元素须为 0..255 整数；返回类型及可选长度先校验，错误消息与固定 TS 一致。

SymmetricKey 继承 BigNumber，fromRandom 取 Random(32)，密钥以 32 字节大端规范化，31 字节十六进制输入向左补零。encrypt 每次取 Random(32) 作为 IV，输出布局为 `IV32|ciphertext|tag16`，按 enc 返回字节数组或 hex；decrypt 按同一布局拆分，小于 48 字节报 `Ciphertext too short`，认证失败报 `Decryption failed!`，成功按 enc 返回字节、UTF-8 或 hex。TS 模块初始化时探测 Node createCipheriv/createDecipheriv，失败走纯实现；Java 初始化探测 JCA，并保留同一回退路径及固定 IV 重放。原手工测试须完整执行 536,870,928 字节加解密、长度断言和逐字节循环；大数组用独立 SHA-256 与资源证据对照，不能缩小输入或把摘要充作原始逐字节断言轨迹。

### API-TRANSACTION-NETWORK HTTP 与链服务

HTTP/chain 编码任务负责 Broadcaster、ChainTracker、chaintrackers 与 http 目录共 13 个完整源文件、113 项声明；同一 API 批次的另五个 broadcasters 源文件归后续任务，不能因本项映射完成就将整批次标为 done。Broadcaster.broadcast 是必需异步入口，broadcastMany 是可选能力；Java 用 `Broadcaster.BatchBroadcaster` 子接口表达。响应的 `status=success/error` 类型守卫保留可选字段缺省的 `Undefined` 值。ChainTracker 必需验证给定高度的 Merkle root 与获取当前高度；同步 verification context 和带 signal 的异步 context token 是两项可选能力，Java 分别用 `Contextual`、`Tokenized` 子接口及重载表达。

DefaultHttpClient 与 binaryHttpClient 在 TS 的选择顺序是 `window.fetch`、`global.fetch`、`require(node:https)`、最后拒绝客户端；Node 18+ 也可能命中 global.fetch。Java 无浏览器全局对象，默认使用 JDK HttpClient，测试注入入口按原顺序覆盖平台分支。FetchHttpClient 对 data 做 JSON.stringify，并按 Content-Type 的 `application/json` 前缀选择 `res.json()` 或 `res.text()`；BinaryFetchClient 原样转发二进制 data，响应始终走 text。Node helper 将 2xx（含 299）判为成功，仅 data 非 null/undefined 时写请求体，按小写 content-type 键决定 JSON 解析；error 事件异步拒绝。固定 mock 的 `json()` 可直接返回字符串，Java 适配器保留这一行为，不强制再解析。

BlockHeadersService 向 `/api/v1/chain/merkleroot/verify` 发送 POST，Bearer key 即使为空也拼装；仅 `CONFIRMED` 判 true。当前高度读取 `/api/v1/chain/tip/longest` 的数值 height；非 OK 与异常经过原两层包装，错误消息可出现双前缀。WhatsOnChain 对 `/block/{height}/header` 的 root 作相等比较，404 判 false，其他非 OK 传递原 data；`/block/headers` 取首条 height，非 OK 与网络异常再加错误前缀。请求 Accept 固定为 JSON，仅 apiKey.trim 非空时带原始 Authorization。两项链服务均无结果缓存；固定测试的 fetch 与平台分支全部离线注入。

<a id="api-script-model"></a>
### API-SCRIPT-MODEL 脚本模型、解析与错误

Script.fromHex/fromBinary 保留输入原字节缓存，并在需要脚本块时解析；malformed push 长度依原分支报错。仅在条件深度为 0 时，OP_RETURN 将剩余字节吞入同一块。ASM 以 OP 首个别名作为规范名称；PUSHDATA 的 size token 消费后依数据重算实际长度。removeCodeseparators 按原始字节跨越 push payload，findAndDelete 只匹配完整序列化脚本块，不误删 push 内部片段。ScriptEvaluationError 保留字段、消息与深拷贝行为，非法栈项沿原 TypeError；ResourceLimitError 是独立类型。SpendVerificationContext/Verifier 提供显式 consensus 输入及异步返回接口。P2PKH.lock 接受主网、测试网前缀及 20 字节哈希；本项只实现脚本模型所需行为，其余模板验收仍归后续任务。

<a id="api-compat"></a>
### API-COMPAT 兼容签名、加密与派生

`BSM` 对带 varint 长度的 `Bitcoin Signed Message:\n` 前缀和消息做双 SHA-256，使用低 S ECDSA 签名；raw 模式返回签名对象，默认模式带压缩公钥恢复编号并输出 compact base64。`ECIES` 的 Electrum 与 Bitcore 格式分别从 ECDH 的压缩点或 X 坐标派生 SHA-512 密钥材料，以 AES-CBC／PKCS#7 加密并用 HMAC-SHA256 验证完整消息；保留带发送方公钥、noKey 和临时发送方私钥路径，以及固定向量的字节序。

`HD` 按 BIP-32 派生和序列化扩展公私钥；`Mnemonic` 按 BIP-39 词表、checksum、规范化与 PBKDF2 生成种子。随机输入经兼容层统一入口注入以复核固定原测试，生产默认使用安全随机源。`Utxo` 六项 API 由完整交易任务收口，兼容批次在其完成前保持进行中。

<a id="api-wallet-contracts"></a>
### API-WALLET-CONTRACTS 钱包契约与参数验证

BRC100 字节边界接受真正的 Uint8Array、每项均为 0..255 整数的完整数组，以及连续数字键的历史对象；DataView、其他 TypedArray、稀疏数组、小数与越界值均拒绝。跨 realm 的对象按原构造器身份判断。`stringifyBRC100` 把字节视图写成普通数字数组；`normalizeBRC100ByteFields` 只转换约定字段并保持容器身份，递归钱包边界须处理循环引用，不能把任意应用 JSON 对象当成字节数组。

WERR 的错误码、默认消息和 `isError` 与固定源码一致；`WERR_REVIEW_ACTIONS` 的可选交易结果字段保留缺省。`WalletError` 保留 message、code 和可选 stack；`unknownToJson` 区分钱包错误、普通 Error 与非错误对象，`onUnknownError` 实际调用注入的处理函数。`WalletInterface` 用 `CompletableFuture<Result>` 和可选 originator 表达异步方法，参数与结果以对应 DTO 承载；`WalletLoggerInterface` 保留必需分组/记录/报错及可选 flush/merge。

`ValidationHelpers` 按固定源码区分整数与 satoshis、UTF-8 字节长度、base64 形状和长度、偶数长度 hex、outpoint、originator、未提供参数与显式默认值，并保留原错误文本。create/sign/list/certificate 参数的默认值、分页、标签 trim/lowercase 以及 `isSendWith`、`isRemixChange`、`isNewTx`、`isSignAction` 派生标志须逐项核对。内部交易导入解析真实 BEEF，要求至少一笔交易和一个输出；错误统一定位到交易参数。`validateAcquire*` 的错误类型依原分支区分普通 Error 和 `WERR_INVALID_PARAMETER`。

<a id="api-wallet-json"></a>
### API-WALLET-JSON 钱包 JSON 通信

`InvokableWalletBase` 的 28 个钱包方法逐一把原方法名和参数交给异步 `invoke`，不提前改写参数。`HTTPWalletJSON` 保存 originator、baseUrl（默认 `http://localhost:3321`）和可注入 fetch；每次调用向 `${baseUrl}/${call}` 发送 JSON POST，设置 Accept 与 Content-Type，并用 BRC100 编码请求参数。Node 环境缺 originator 在发送前报错；存在时经 `toOriginHeader(originator, "http")` 同时填 Origin 与 Originator，浏览器环境由浏览器处理 Origin。

响应 JSON 只对钱包约定的字节字段递归恢复 Uint8Array 语义，其他 JSON 结构不变。仅 HTTP 400 且 `isError=true` 时按 code 5/6/7 恢复三类 WERR，服务端 message 原样传递；其他非 OK 响应以含 call、args 和服务端 message 或 `HTTP Client error <status>` 的 JSON 字符串抛普通 Error，网络异常原样传播。`toOriginHeader` 对有 scheme 的 URL 取 origin 并去除路径和 query；缺 scheme 时加指定 fallbackScheme，非法输入保留原错误文本；独立工具可用 `https`，HTTP 调用固定 `http`。

<a id="api-wallet-keys"></a>
### API-WALLET-KEYS 钱包密钥派生与本地钱包

`KeyDeriver` 按协议 ID、密钥 ID、对端身份和用途生成确定性 invoice，保留 BRC-42 公私钥派生、对称密钥、批量共享 ECDH 与 linkage secret 的原始字节和错误边界；可选 AsyncCryptoBackend 只在原选择条件下执行。`CachedKeyDeriver` 以完整参数序列化结果为键维护 LRU，缓存命中复用结果对象，批量请求按输入顺序补算缺项。`ProtoWallet` 以真实派生密钥完成身份及派生公钥、BRC-2 加解密和 HMAC、BRC-3 签名验签、两种 linkage revelation；大消息 SHA-256 和异步后端调用保持原始输入与返回语义。

`CachedKeyDeriver` 原性能用例的首次与缓存命中耗时属于运行环境观测值。逐断言验收保留两侧实际毫秒轨迹，核对原阈值和实测是否满足断言，不要求两次运行的毫秒数相同。

<a id="api-transaction-base"></a>
### API-TRANSACTION-BASE 交易基础、签名与费率

`TransactionInput`、`TransactionOutput` 保留可选来源、脚本、金额和 change；`addInput` 默认 sequence 为 `0xffffffff` 并要求来源，`addOutput` 检查金额及锁定脚本。Transaction 的 raw/EF 序列化、hash/id 都按当前交易头、输入来源与脚本、输出金额与脚本的实际字节生成；缓存按这些字段及 EF 来源输出变化失效。未变化时 `toEFBinary`/`toEFUint8Array` 复用同一个字节数组。`sign` 先校验输出金额；跳过已有解锁脚本时保持原引用。

`P2PKH.unlock` 从来源交易读取 TXID、金额及锁定脚本，按 scope 生成 BIP143 预映像，经两次 SHA-256 签名，返回 DER 加 scope、压缩公钥两个 pushdata，估算长度为 108。`TransactionSignature` 保留 ALL/NONE/SINGLE、FORKID/CHRONICLE/ANYONECANPAY 路由、传统 OTDA 与 BIP143 预映像、SINGLE 越界边界及共享 hash 缓存；显式当前输入参数覆盖 `allInputs` 的对应项。`SatoshisPerKilobyte` 按固定字段和真实或模板脚本长度、varint 边界计算 `ceil(size/1000*rate)`；缺少解锁脚本和模板时异步报错。`LivePolicy` 首次确定缓存有效期，ARC policy 费率成功后缓存，失败时使用缓存值或 100 sat/kb；Java 的 HttpClient 可注入以复核网络边界。

Atomic BEEF 读写复用真实 Beef/MerklePath：常规 BEEF 缺少 BRC-95 subject TXID 时拒绝；写入时依次为四字节 Atomic 前缀、subject 原始 hash 和 V1 BEEF 内容。该格式的完整证明、排序与裁剪行为由交易 BEEF 任务验收。

<a id="api-transaction-beef"></a>
### API-TRANSACTION-BEEF Merkle 证明与 BEEF

`MerklePath` 按 BRC-74 读取和写入高度、各层 offset、txid/duplicate 标志及显示顺序哈希；默认检查合法 offset，显式宽松读取供合并延迟验证使用。`computeRoot(txid)` 从指定叶计算根，同一高度路径可 `combine`，随后 `trim` 去除可推导叶；固定 59 个原测试包含安全 offset、无效向量与 bench 规模，不能只用小证明代替。

`BeefTx` 保留原始交易字节、TXID、输入依赖与可选 bumpIndex；V1 将证明标记写在交易后，V2 使用交易格式前缀并允许 TXID-only。BEEF 解析支持 V1、V2 与带 subject TXID 的 Atomic 前缀；序列化按证明交易、已知 TXID、未证明依赖排序，并检测重复 TXID、缺失输入、错误证明索引、同高度不同 Merkle 根和 Atomic 依赖闭包。`isValid` 只校验结构及计算根的一致性，`verify` 再调用 ChainTracker 核对区块头根。

合并原始交易、Transaction 图、BEEF 和已证明批次时，按 TXID 去重并将同高度同根的证明合成；`mergeProvenTxs` 的结果须与逐笔合并的 BEEF 字节一致，提供根提示时须拒绝冲突。Atomic 序列化只保留 subject 及其递归输入，缓存值在直接可达的交易、证明或列表内容变化时失效，未变化时 `toUint8ArrayAtomic` 复用同一字节数组。`BeefParty` 对任意字符串参与方安全保存已知 TXID，发送前只裁剪已知的 TXID-only 项并重排引用的证明索引；批量接收按一次同步流程记录对方可验证的 TXID。

<a id="api-script-templates"></a>
### API-SCRIPT-TEMPLATES 脚本模板

`SignatureUtils` 从真实来源交易解析金额和锁定脚本，按 signOutputs 与 anyoneCanPay 生成签名 scope 和 BIP-143 预映像。`P2PKH.unlock` 在可用且就绪时调用已注册的异步后端签名与编码，返回值仍须是有效 DER 签名和压缩公钥；未注册或未就绪时使用本地密钥路径。

`PushDrop.lock` 按协议 ID、密钥 ID、counterparty 和 originator 向钱包请求派生公钥，按 lockPosition 生成字段、可选签名及公钥的锁定脚本；`decode` 恢复同序字段与公钥。`unlock` 从真实来源构造签名请求并生成解锁脚本。`RPuzzle` 按类型锁定 R 值及其哈希，并用指定 nonce 与私钥生成可验证的签名。模板测试中的真实签名验证经过 `Spend.validate`；完整脚本解释器行为由脚本执行任务单独验收。

### 已核实、尚待逐项映射的行为

| 源码事实 | Java 映射必须解决的问题 |
| --- | --- |
| ECDSA.sign 的 forceLowS 默认 false，customK 可为数值或按迭代次数调用的函数 | 不采用常见库的默认 low-S 假设；保留 nonce 选择、重试和固定 k 的拒绝行为 |
| AsyncCryptoBackend 未注册/未就绪/不支持操作时才回退；未就绪会触发后台 preload；选定后结果权威，不能在失败时偷偷回退 | 注册表按对象身份卸载，保留就绪判断、调用顺序、异步拒绝和字节返回校验；测试替换及复位边界要明确 |
| Transaction 构造默认 version=1、lockTime=0、metadata=new Map()；id 按 enc 分别返回字节和 hex | 区分返回类型、每次新建的默认状态、输入/输出别名、序列化缓存和失效时机，不把接口定义直接当不可变 record |
| WalletClient 的快速连接尝试并发启动，但按固定列表顺序选首个成功项，全部失败才转 XDM | 不能改成最快完成者胜出；保留超时清理、响应 shape 校验和最终错误文本 |
| BRC100ByteEncoding 对健康数组/Uint8Array 保留身份，拒绝稀疏数组及非字节视图；历史数字键对象只在明确边界修复 | 不能把所有 number[] 提前强制成 byte[]，也不能递归把应用 JSON 对象都当字节数组；空对象、缺失字段、循环和跨 realm 语义须落实 |
| XDM 要求 trusted 事件、当前 parent 身份和指定 origin；React Native 接受的来源规则不同，响应匹配前后有清理边界 | 为 Java 宿主桥接定义明确的消息对象与事件能力，保留两种校验流程；不能以 JVM 没有 window 为由跳过整组测试 |
| Auth Peer 同步 send 抛错与 Promise 拒绝都会涉及等待者清理；TransactionEvidenceCoordinator 有并发、取消、缓存和上下文变化 | CompletionStage 只解决返回形式，不能替代状态机、时钟、调用次数和顺序的逐项映射 |

Reader 探针的实际值、共享视图和复制结果保存在 `.cache/evidence/api-reader-observations.json`；该探针没有改动 TS 源码，也不是新增 SDK 用例。

AES 的实现选择保留待验证：`AESGCM.ts` 注释声称非标准 padding 会导致 tag 不兼容，但对 12/32 字节 IV、0/1/16/17 字节明文的 8 组实测，纯 TS 与 Node 原生 AES-256-GCM 的密文和 tag 均相同。证据为 `.cache/evidence/api-aes-observations.json`。这只能确认这 8 组结果，不能宣称所有输入兼容，也不能仅凭注释否决 JCA。后续须保留直接 AESGCM 与 SymmetricKey 的平台分支对照；SymmetricKey 使用 32 字节 IV，nativeDecrypt 当前 catch 返回 null，其调用方报 `Decryption failed!`，不能按注释误判成失败后始终回退。
