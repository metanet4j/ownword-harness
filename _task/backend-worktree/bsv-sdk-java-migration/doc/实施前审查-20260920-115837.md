# 迁移计划与环境实施前审查

## 结论

可以进入 P0 实施，当前没有阻止范围审查、接口映射和验证基础设施开发的环境问题。已完成设计且依赖闭合的内部项按用户授权先做 TDD，执行条件见 feature_list.json 的 implementationPolicy；完整模块最终验收仍以 `migration-map` 的 P0 联合验收完成为前置，当前不能声称完整模块或全部上游测试通过。

审查覆盖计划、测试契约、全部任务脚本、目标 POM、状态文件、固定上游及五个 Java 仓库，并执行了下表所列构建、冒烟与检查器验证。当前实施工程边界仅为 metanet4j-bsv-sdk；其他工程的构建/回归结果只作为准备阶段环境证据，不意味着允许修改或接入其他工程。完整 SDK 的 Java 功能映射仍为 0。

## 审查发现与处理

| 发现 | 依据与影响 | 落实方式 |
| --- | --- | --- |
| P0 原来只有一个粗粒度事项 | 同时包含范围、API、映射、运行器、重放、采集，无法单独验收和安排依赖 | 在 feature_list.json 建立七个 P0 功能项，把 migration-map 明确为联合验收；各项包含步骤、产物、依赖和验收条件 |
| 全模块 TS 基线尚未执行 | 已运行的是九个文件的 191 个冒烟用例，当前完整范围见 module-tests.json，必须含范围复核新增模块 | migration-ts-baseline 必须实际运行完整模块，失败与资源不足保留未完成 |
| manual 资源用例需要专门验证 | AESGCM.man.test.ts 输入为 536870928 字节（512 MiB + 16 字节），并同时涉及密文、解密结果及中间缓冲；本次只审查源码，未运行该用例 | 在完整 TS 基线功能项中要求资源预算、实际执行和原始规模保持。采样时内存约 15.4 GiB、可用约 3.2 GiB、磁盘可用约 724 GiB；这些观察不证明该用例资源充足，执行前需重新测量峰值需求 |
| 现有检查器依赖登记的断言和输入摘要 | audit-tests.py 比较 test-map.json 的 assertionIds 与两端结果，尚无独立运行轨迹保证所有循环样本和辅助断言都被登记，也不会从输入原始产物重新计算每个摘要 | migration-test-mapping、migration-input-replay、migration-result-capture 和 migration-evidence-gate 共同补齐；增加两端同时少登记断言/样本仍失败的反例 |
| 原始报告会被后续 clean test 覆盖 | verify.sh 的 bsv-test/bsv-build 会清理 target；Java 提交及工作树变化也会改变 javaRevision | 计划明确按运行批次保存报告；P0 实现采集与验收编排后，保留本次原始证据并绑定验收时源码版本 |
| 当前 init.sh 的状态检查较窄 | 只验证 JSON 可读及至多一个进行中事项，未自动验证整个依赖图 | 本轮独立核对新功能项的唯一 ID、无环依赖、下一项就绪和状态一致性；把持续状态门禁纳入 migration-evidence-gate |

上述未实现能力属于 P0 的交付内容；未关闭时阻止完整模块验收，已就绪内部项可按 implementationPolicy 实施并同步落实自己的测试采集。范围由 module-scope.json 决定；候选模块结论及依赖依据见[范围复核](完整模块与API映射-20260920-122800.md)。功能项的详细验收条件只在 [feature_list.json](../feature_list.json) 维护。
