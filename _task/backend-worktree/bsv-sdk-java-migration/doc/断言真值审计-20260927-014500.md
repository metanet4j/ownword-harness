## 已验证事实

工作区实际使用的 Jest 30.4.1 的 `toBeDefined` 判断为 `received !== undefined`，`toBeUndefined` 判断为 `received === undefined`。因此 `null` 满足 `toBeDefined`，不满足 `toBeUndefined` 和 `not.toBeDefined`。依据为本地 `reference/ts-stack/node_modules/.pnpm/expect@30.4.1/node_modules/expect/build/index.js:619` 和 `:787`，自测直接调用该 Jest matcher。

## 缺口分类与公开 API 前检

缺失 Map 键须通过 `containsKey` 判断：缺键读出 `Undefined.INSTANCE`，存在且值为 null 则保留 null。ARC 等 Map 断言可按此修正读取；禁止对任意 null 进行替换。

固定 TS 的可选公开字段及可返回 undefined 的读接口，依照 [现有 API 契约](完整模块与API映射-20260920-122800.md)第 166 行的统一规则，使用 `Object` 承载真实 `Undefined.INSTANCE`。下表引用数由 JDK Compiler Trees 解析具体符号获得，包含读／写引用，不含声明；排除了钱包 DTO 等同名成员，原始清单为证据目录 `member-references.tsv`。

两查询方法的现有调用点都接受 Object，因此签名放宽不需要调用方转换。四字段改为 Object 后，生产代码必须在已确认数值、脚本、字节或交易类型的路径显式转换，并保留原分支对 null／undefined 的不同处理。新增单独 presence 标志不能约束现有 public 字段的直接赋值，会造成双份状态，不采用。不会将所有可选字段不加区分地批量改写。

AsyncCryptoBackend.ready 的 null 适配已在契约第 488 行说明，但 `api-map.approvedDifferences` 与正式逐断言比较规则尚未登记。因此该项属于“设计已述、正式证据规则未登记”，保留真实 null 红灯，不声明正式对照通过。
