## 已验证事实

工作区实际使用的 Jest 30.4.1 的 `toBeDefined` 判断为 `received !== undefined`，`toBeUndefined` 判断为 `received === undefined`。因此 `null` 满足 `toBeDefined`，不满足 `toBeUndefined` 和 `not.toBeDefined`。依据为本地 `reference/ts-stack/node_modules/.pnpm/expect@30.4.1/node_modules/expect/build/index.js:619` 和 `:787`，自测直接调用该 Jest matcher。

旧 Java `assertUndefined` 把实际 `null` 改记为 `Undefined.INSTANCE` 并允许断言通过；`assertDefined`／`assertNotDefined` 错把 null 视为未定义，并只记录布尔投影。修复后三者均先记录原 actual，再执行正确语义；`assertStrictUndefined` 复用统一入口。

TS `capture-parity.cjs` 已删除 `toBeDefined` 的布尔投影，失败断言也保留真实 receiver，状态仍记为 `pass=false`。WalletWire 的独立采集器由所属代理同步修复，使用同一自测验证。

原始日志、Surefire XML、断言 JSONL 与机器报告位于 [证据目录](../.cache/evidence/assertion-semantics-957d6f4-20260927/)。其中 [affected-summary.json](../.cache/evidence/assertion-semantics-957d6f4-20260927/affected-summary.json) 为每个失败保存 Java 完整测试身份、TS 用例 ID／文件／名称和最后一条真实断言。

## 已落实的语义修复

- ARC 从 Map 读取缺键时使用 `containsKey` 区分缺键与显式 null。
- Beef 两查询缺失结果返回 Undefined；BeefTx 的 rawTx／transaction 缺省保存 Undefined、显式写入 null 仍为 null。
- TransactionOutput.satoshis、TransactionInput.unlockingScript 使用 Object 保存可选联合值；缺省／删除使用 Undefined，数值和 Script 路径显式转换。新增回归验证 addOutput 接受显式 null 金额而拒绝缺失金额，符合固定 TS。
- TransactionAdditional 三个原用例和 TransactionVerifier 的删除金额用例改为真实 Undefined 输入。首轮 1926 用例仅前三者失败；后者原错误 null 输入虽能通过，仍需修正输入来源。
- `assertNotHasProperty(Map,key)` 记录真实 `negated=true`。
- `assertCalledWithObjectUndefined` 记录全部原调用并严格要求第二参数 Undefined；`assertCalledWithWalletUndefined(List<?>)` 接收真实四参数调用；旧 int 重载强制失败，等待调用方迁移后删除。
- `assertResolvesNotThrow` 记录真实异步结果，null 不改写；resolved Error 与 rejected Promise 保留真实错误并失败。
- `toHaveBeenCalledWith` 的普通对象参数按固定 TS `canonicalCallArg` 采用浅表示；原参数不变，null／Undefined、嵌套数组及完整调用次数分别保留，`toEqual` 仍记录对象字段。

三种 synthetic helper 的 RED 反例分别为：两条真实调用被旧 helper 缩成一条伪调用；实际 null 结果被写成 Undefined；只有调用次数却通过四参数断言。新自测还保留失败调用的完整实际参数和异步错误。

## 公开 API 与后续边界

缺失 Map 键须通过 `containsKey` 判断：缺键读出 `Undefined.INSTANCE`，存在且值为 null 则保留 null。ARC 等 Map 断言可按此修正读取；禁止对任意 null 进行替换。

固定 TS 的可选公开字段及可返回 undefined 的读接口，依照 [现有 API 契约](完整模块与API映射-20260920-122800.md)第 166 行的统一规则，使用 `Object` 承载真实 `Undefined.INSTANCE`。下表引用数是修改前 JDK Compiler Trees 扫描命中的引用数，包含读／写、不含声明，排除了钱包 DTO 等同名成员。后续编译发现 TransactionSignature 的金额写入也是调用点，因此该扫描不能视为穷尽；完整源码／测试源码编译和 1926 项回归覆盖此次签名扩散。原始清单为证据目录 `member-references.tsv`。

| 符号 | 固定 TS 声明 | 修复后 Java 声明 | 生产引用／测试引用 |

两查询方法的现有调用点都接受 Object，因此签名放宽不需要调用方转换。四字段已改为 Object，生产代码在数值、脚本、字节或交易类型路径显式转换，保留 null／undefined 的不同状态。伴随公开签名为 `TransactionOutput(Script,Object)`、`TransactionInput(String,int,Object)`、`Transaction.addP2PKHOutput(Object,Object)`；钱包 DTO 的同名字段未改变。新增单独 presence 标志不能约束现有 public 字段的直接赋值，会造成双份状态，不采用。不会将所有可选字段不加区分地批量改写。

AsyncCryptoBackend.ready 的 null 适配依据契约第 488 行，在 Java 局部 helper 中断言真实 null 并保留 `toBeUndefined` 标识。根代理已在 `audit-tests.py` 为固定 caseId 与两个源码站点登记 `async-ready-null-adapter-v1`；正式采集和证据门禁由根代理统筹，本报告只证明局部真实记录与回归。

BeefTx.tx()／rawTxUint8Array() 仍使用强类型 nullable 返回值。固定 TS 前者缺失始终返回 undefined，后者直接返回可选 `_rawTx`，还需单独审计其公开返回类型与调用扩散；字段修复不能证明这两个 getter 已完全满足联合值契约。
