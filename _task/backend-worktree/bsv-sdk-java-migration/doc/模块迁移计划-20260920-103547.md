# TypeScript → Java 按模块迁移计划

## 执行目标

只迁移 metanet4j-sdk 实际需要的能力及必要依赖，分阶段替换现有底层。每个上游用例与 Java 用例的实际运行结果必须符合[测试迁移契约](测试迁移契约-20260920-101559.md)，逐个行为执行 TDD。版本和工作区基线引用 [workspace.json](../workspace.json)，产品与协议事实引用[核心认知](../../../system-design/spec/核心认知.md)。

环境准备已完成。下面是依据本地调用和 TS 源码依赖制定的阶段安排；P0 尚未完成，不把候选测试入口视为完整用例清单。阶段状态只在 [feature_list.json](../feature_list.json) 维护。

## 阶段顺序

表内路径相对于上游 `packages/sdk/src/`。每个阶段对应一个任务事项，按顺序推进。

| 阶段 / 事项 | 模块与交付内容 | 上游测试入口与验收重点 |
| --- | --- | --- |
| P0 / `migration-map` | 真实调用 → TS 能力 → Java 接口 → 上游用例/断言映射；确定底层代码落点与兼容策略，建立参考结果采集、Java 结果导出及差分检查入口 | 逐文件判定 `upstream-tests.json` 中全部条目的去向；展开入选模块的动态/参数化/属性用例。先用可复现向量及错误反例验证采集和比较工具；P0 完成后才实施生产模块 |
| P1 / `migration-primitives` | 编码、字节读写、大整数和哈希基础 | `primitives/__tests/` 中 `hex`、`utils`、`utils.property`、Reader/Writer、BigNumber、ReductionContext、Hash/HMAC 等相关测试；逐项核对边界值、前导零、符号、大小端和非法输入 |
| P2 / `migration-keys` | secp256k1、密钥、公钥、地址/WIF、ECDSA/Signature 及所需随机/DRBG 支撑 | Curve/Point/JacobianPoint、PrivateKey/PublicKey、ECDSA/ECDH、Signature、Random/DRBG 等相关测试；核对确定性签名字节、DER/compact 格式、恢复和验签失败分支；交易签名归 P6 |
| P3 / `migration-hd` | HD 派生与助记词 | `compat/__tests/HD.test.ts`、`Mnemonic.test.ts`、`Mnemonic.additional.test.ts`；核对种子、派生路径、扩展密钥、词表、校验与异常输入 |
| P4 / `migration-message-crypto` | BSM 消息签名和 ECIES/AES-CBC 所需能力 | `compat/__tests/BSM.test.ts`、`ECIES.test.ts` 及所需依赖测试；核对消息摘要、签名、恢复结果、Electrum BIE1 格式和密文向量 |
| P5 / `migration-script` | Script、OP、锁定/解锁脚本的数据模型与编解码 | `script/__tests/Script*.test.ts`、`LockingUnlockingScript.test.ts` 等相关测试；核对脚本字节、ASM、pushdata 边界及错误。需要交易上下文的执行和模板测试归 P6 |
| P6 / `migration-transaction` | Transaction 输入/输出与序列化、TransactionSignature/sighash、P2PKH、费用、UTXO 适配及必要脚本验证 | `transaction/__tests/Transaction*.test.ts`、`primitives/__tests/TransactionSignature.additional.test.ts`、`script/templates/__tests/P2PKH.async-backend.test.ts`、费用模型与所需 Spend 测试；核对交易 hex/txid、preimage、签名范围、解锁脚本、费用/找零、失败分支及异步行为 |
| P7 / `migration-sdk-adapters` | 将 metanet4j-sdk 既有 BAP/AIP、BSocial、Ordinals、Sigma、远程签名接到已验收底层；处理 base 中受影响的帮助类 | 累计重跑 P1–P6 的 TS/Java 对照；另跑既有 Java 业务回归与明确登记的适配测试。业务协议无对应 TS SDK 用例时标明 Java 业务来源，不能伪造一比一对应 |
| P8 / `migration-downstream` | 接入 component 受影响模块，检查公开接口兼容和旧依赖去向，完成全量累计验收 | 按实际影响验证 tx、tx-filter、tx-convertor、common、bap 等模块；按 parent → base → sdk → component 验证依赖，再核对所有阶段用例及每项实际结果。未替代调用或未解决测试仍存在时不得清理所需依赖或宣布完成 |

## P0 执行清单

1. 从 SDK、base 与受影响下游的真实调用出发，列出所需 TS 模块和方法、现有 Java 接口及公开泄漏的旧类型。公共底层放置需避免 `base → sdk → base` 环；跨仓模块拆分或接口破坏性调整形成具体方案后按工作区架构规则处理。
2. 为全量上游测试文件登记“纳入的模块/阶段”或“与调用无关的排除依据”，再展开入选模块的每个用例、参数行和断言。配置排除、manual、skip/todo、内部实现测试均保留记录。`AESGCM.man.test.ts` 必须明确归属；当前 ECIES 引用 `compat/aescbc`，不能仅因目录相近就把 AES-GCM 当成必要依赖或静默丢掉其手动测试。
3. 固定各阶段接口边界、输入语料和比较规则，满足 tdd 技能的测试边界要求。独立采集 TS 原始断言与可观察结果，记录其命令、配置、随机输入及 fixture 校验值。
4. 建立逐用例对照清单和可重复执行的检查入口，落实[测试迁移契约](测试迁移契约-20260920-101559.md)中的缺失、篡改与重复结果反例。单纯新增文档或运行环境冒烟不能将该事项标记完成。
5. 根据实际用例依赖冻结阶段清单、预期用例数与累计回归集。每个上游用例有唯一归属，拆成多个 Java 测试时保留完整映射；跨阶段修改必须同步映射、状态与执行计划。

## 依赖与范围处理

`TransactionSignature.ts` 引用 Script 及交易输入/输出；P2PKH 引用 Transaction 与 TransactionSignature；Transaction 又引用 P2PKH 和 Spend。因此 P6 作为一个验收阶段，内部仍按“序列化 → sighash → 签名/模板 → 费用与验证”的顺序逐用例 TDD，不一次性批量实现。

阶段表按能力划分，不以源码文件夹机械切割。若 P1–P5 的必需上游用例也依赖 P6，应在 P0 调整前置能力或合并验收阶段。不得把该用例留到后面却提前标记所属模块完成。

Transaction 对 Beef、MerklePath、默认网络服务等的源码引用需要区分运行时依赖、类型引用及实际所用方法。wallet/auth/overlay、BEEF/SPV、额外脚本模板、Schnorr/Secp256r1 等均须由调用映射判断去向，既不整包照搬，也不预先宣布排除。涉及所选模块或已纳入接口的上游测试，不能因难度、资源占用或当前失败减少范围。

旧 Java 行为和固定 TS 行为若冲突，保留最小输入与两端结果，明确是接口适配、兼容策略还是上游问题；解决前不进入该行为的完成状态，不靠修改测试预期消除差异。

## 每阶段执行与交付

1. 检查前置阶段状态，载入本阶段用例和断言清单，运行 TS 参考测试并保留实际结果。
2. 对一个已确认接口行为写 Java 测试，确认 RED 来自目标行为缺失，再完成最小实现，取得 GREEN 并核对 TS/Java 结果；循环处理本阶段全部用例。
3. 执行本阶段及此前已完成模块的累计验收，遵守测试迁移契约全部门禁。对照报告随阶段交付，命令、报告与代码版本可关联。
4. 同步阶段状态和下一步，每完成一个功能项按仓库分别提交；依赖未完成、差异未关闭或证据缺失时保持未完成状态。每阶段验收通过后才能进入下一阶段。

当前只完成计划与契约定义，逐用例映射、结果采集/比较工具和 Java 生产迁移仍待执行。
