# TypeScript → Java 整模块迁移计划

## 范围与依据

按 metanet4j-sdk 的使用情况选择完整模块，一旦选中就迁移模块全部功能和测试，不按业务用到的方法裁剪。范围定义、TDD 与结果一致性统一见[测试迁移契约](测试迁移契约-20260920-101559.md)；模块清单见 [module-scope.json](../module-scope.json)，固定上游和分支见 [workspace.json](../workspace.json)。产品和协议事实引用[核心认知](../../../system-design/spec/核心认知.md)。

完整范围与依据见[完整模块与 API 映射](完整模块与API映射-20260920-122800.md)。已确定六个完整顶层模块：`primitives`、`compat`、`script`、`transaction`、`wallet`、`auth`，其全部子目录、类型、辅助文件及测试均纳入。其余九模块的排除依据逐项记录于 module-scope.json；两项根目录测试归属未纳入的 overlay-tools。模块一经选中，不按旧 Java 调用的方法裁剪。

## Java 目标工程

用户指定任务根目录下的同级独立工程 `metanet4j-bsv-sdk`，与既有 SDK 分别管理 Git 和 Maven。六个完整模块在同一个 JAR 内按 `com.metanet4j.bsv` 下的包组织，包与测试向量目录见[工程说明](../metanet4j-bsv-sdk/README.md)。工程继承现有父 POM，但不依赖 base/sdk，避免业务向底层的反向依赖。本次工程源码、测试、POM 和配置仅修改 metanet4j-bsv-sdk；parent/base/sdk/component 只读参考，不做业务适配、下游接入或旧依赖替换。P0 的公开 API/行为映射针对新工程自身，P2 在本工程完成最终累计验收。任务根目录继续维护计划、清单和验证工具，具体工程边界见 feature_list.json 的 scope。

初始化事项 `migration-core-project` 验收 Java 25、JUnit、UTF-8 向量资源、独立 Git 基线和统一验证入口，基础测试不计入上游复刻用例。

## 阶段顺序

用户明确要求把 API 检查放在编码任务开始前。执行规则以 feature_list.json 的 implementationPolicy 为准：每个功能组在同一任务内完成 API 前检、映射、逐行为 TDD、实际结果对照和独立验收；无需先完成全部 API 设计。P0 和六模块联合验收依然是最终完成的前置，内部文件完成不等于整模块完成。

| 阶段 / 事项 | 完整交付与验收范围 |
| --- | --- |
| P0 / `migration-map` | 完成六个整模块的 API/行为与逐用例/断言映射、依赖与跨目录测试复核、Java 类型及兼容方案，补齐完整 TS 基线、输入重放和真实结果采集 |
| P1 / 编码任务 → `migration-core-modules` | 28 个 implementation-slice 按依赖实施并独立验收；全部功能和测试闭合后进入六模块联合累计验收 |
| P2 / `migration-sdk-acceptance` | 在 metanet4j-bsv-sdk 内完成六模块最终累计测试、实际结果对照、API 核对、JAR 和文档交付；只读确认其他工程未引入本任务改动 |

完整依赖图由 `module-tests.json` 的 moduleDependencies 生成，覆盖源码类型引用、测试与辅助代码。`script → auth/wallet`、`wallet ↔ auth`、`transaction → compat` 与已有基础依赖形成六模块闭环。原先把 compat 留到后续验收会漏掉交易测试的必需依赖，因此六模块采用联合验收。

内部实施顺序为基础数据与密码学 → 基础脚本和交易 → compat → wallet/auth → 依赖钱包的脚本/交易能力。保持按模块归档代码、API 和测试，逐行为 RED/GREEN；依赖未完成时不声明任何完整模块验收通过。

## 文件和脚本的职责

本计划是执行顺序的入口；比较规则引用[测试契约](测试迁移契约-20260920-101559.md)，清点与证据字段引用[检查器说明](测试完整性脚本-20260920-104440.md)，不在多份文档重新定义。以下命令均在任务根目录执行。

| 文件或入口 | 输入 → 输出及用途 |
| --- | --- |
| `workspace.json`、`env.sh`、`mvn.sh`、`pnpm.sh` | 固定仓库/工具配置 → 当前进程的隔离环境；Java/TS 操作统一经过对应入口 |
| `init.sh` | 仓库、源码、清单、工具 → 自检结果；不安装、不构建、不执行功能测试 |
| `inventory-tests.py` → `upstream-tests.json` | 全 SDK 静态测试文件与 Jest 默认发现结果 → 文件、辅助向量和排除项清单；重建会写文件，按需执行并审查差异 |
| `module-scope.json` | 人工确认的完整模块与跨目录测试归属；pending 必须逐项解决 |
| `audit-tests.py inventory` → `collect-cases.cjs` → `module-tests.json` 候选文件 | 选定完整模块 → 注册用例、静态依赖、源码复核位置和文件校验值；清点不执行测试体或 hooks |
| `audit-api.cjs inventory` → `api-catalog.json` 候选文件 | 固定 TS 源码与真实导出关系 → 声明、签名、默认值、源码位置及校验值；包含公开导出的测试辅助类，不执行源码 |
| `api-map.json`、`audit-api.cjs check` | 已复核的 Java API/行为设计 → 重新扫描源码并检查映射差集；清点及结构通过不等于 Java 已实现，详见完整模块/API 映射文档 |
| `feature_list.json` 的 features/apiBatches、`audit-api.cjs batches [--batch ID]` | 重新扫描固定源码，检查嵌入 API 分组、执行依赖、唯一源码收口/原测试归属及辅助资料覆盖；--batch 只增加该组 API 映射核对，不能替代全量 check 或实际结果验收 |
| `api-values-probe.mjs` | 固定 TS 构建产物与显式小输入 → 原始边界观察 JSON；可带 `--without-buffer` 对照平台路径，只用于 API 复核，不是 SDK 测试或结果一致性验收 |
| `run-hex-parity.py [--bn-constructor]`、`capture-hex.cjs`、`capture-bn-constructor.cjs`、`bn-constructor-parity.py`、Java 观察器 | 原始 Hex/BigNumber 构造测试 + 目标工程 clean test → 报告与实际调用/断言轨迹；复用 compare 核对内部项，不能替代完整模块 check |
| `test-hex-parity.py <批次目录> -v` | 真实运行证据 → 漏采、重复、输入/结果/异常差异及报告篡改反例检查；不计 SDK 测试 |
| `test-map.json` | 上游 ID → Java 测试入口、断言/样本标识及源码位置复核记录；映射本身不表示实际执行通过 |
| `run-ts-baseline.py`、`ts-offline-guard.cjs` | 完整冻结范围 → 真实 TS 基线与独立报告；禁止真实网络，manual 不缩小输入；仅有 TS 基线不代表 Java 迁移完成 |
| `verify.sh` | 构建或测试命令 → `.cache/evidence/` 日志和报告摘要；具体分项见下文 |
| `audit-tests.py revision` | 全部已登记 Java 仓库的提交及工作树文件 → `javaRevision`，由采集过程记录并在验收时重新核对 |
| `audit-tests.py check` | 冻结清单、映射、真实 Jest/Surefire 报告和逐断言结果 → PASS/FAIL；先重新清点上游，不代替运行测试或采集结果 |
| `audit-tests.py compare`、`test-audit.test.cjs` | 调试证据或专用测试数据 → 检查器验证；不充抵 SDK 迁移测试，也不代替正式 `check` |
| `AGENTS.md`、`README.md` | 工作规则与常用命令入口 |
| `feature_list.json`、`progress.md`、`session-handoff.md` | 阶段状态与证据、当前进展、下一次执行入口；验收后更新并提交 |

本次使用的 `verify.sh` 分项：`bsv-test` 执行目标工程 `clean test` 并核对 Surefire 实际用例；`bsv-build` 先完成同样的测试，再安装 JAR；`ts-build` 构建固定上游；`ts-smoke` 只跑已指定的九个文件。`java-build` 和 `java-smoke` 保留为准备阶段已使用的命令，本次实施不安排跨工程构建或回归。冒烟不能代替完整模块验收。

完整模块 TS 运行入口为 `./verify.sh ts-modules`，由 run-ts-baseline.py 分普通/manual 进程执行，保存独立批次的原始报告、命令、资源和网络拒绝记录；`python3 run-ts-baseline.py --verify <批次目录>` 只复核已有证据。完整基线是否通过以 feature_list.json 为准。

**完整 SDK 的输入重放、循环/属性轨迹采集及报告关联仍待 P0 完成。** Hex 与 BigNumber 构造已有可运行的局部入口，见下节；覆盖原文件中的确定性调用和非法字符循环，不表示随机/属性重放等通用基础设施已完成。

## 已就绪实施项：Hex

在任务根目录运行 `python3 run-hex-parity.py`：

1. 核对固定 TS 提交、冻结源码哈希、映射、采集器及 Java 当前提交/工作树摘要。
2. 原封不动执行 hex.test.ts 的 8 个 Jest 用例；capture-hex.cjs 只包裹两个实际函数，每次调用原实现一次，记录输入、返回值或异常并原样交还原断言。原断言源码位置从运行栈取得。
3. 通过 verify.sh bsv-test 执行目标 Java 工程 clean test。HexTest 保留原输入和断言，独立记录每次实际调用；void 记录为 undefined，SdkException/SdkTypeException 分别按已审查的 Error/TypeError 规则比较。
4. 立即把原始 Jest JSON、全部 Surefire XML、两端调用记录和日志复制到独立 `.cache/evidence/hex-parity-*` 目录，避免下次 clean 清除。manifest 绑定源码、工具、Java 版本、命令与原始报告哈希。
5. 从冻结清单核对 8 用例、19 断言、27 AST 位置，复用 audit-tests.py 的 compare 引擎逐项核对 Java 实际执行入口、输入摘要、返回值、异常类型和完整消息；任一缺失/重复/差异即失败。
6. `python3 run-hex-parity.py --verify <批次目录>` 复核当前版本仍适用的已有证据；`python3 test-hex-parity.py <批次目录> -v` 验证检查器能拒绝错误证据。源码或提交变化后重新采集，不能改旧版本号。

批次中的 hex-only.catalog.json、hex-only.mapping.json 是 compare 的临时片段，summary 明确 formalAcceptance=false，不允许用作完整模块冻结清单。正式 audit-tests.py check 继续重扫原六模块、5329 用例；本地局部入口不修改其过滤规则或完成条件。

Hex 的 TDD 按有效输入、非法字符、undefined/null、小写、奇数补零完成 5 组真实 RED→GREEN；其余 3 个原用例在已有行为下直接 GREEN，按原样保留，不人为破坏实现制造 RED。

## 累计实施项：BigNumber 构造

运行 `python3 run-hex-parity.py --bn-constructor`，在上述同一流程内增加完整 BigNumber.constructor.test.ts，并累计执行 Hex 和目标 Java 全部测试。两个 TS 原文件分进程执行，保证各自采集适配独立；上游源码和原断言均不改动。

- 原文件为 28 用例、45 静态断言、74 AST 位置；139 行断言在 8 个非法字符串上重复执行，总计 52 次。映射用 `#1` 至 `#8` 区分样本，不能用最后一条覆盖前面记录。197 行空 Buffer 条件按原表达式保留，并核对实际构造参数为字符串 `0`。
- capture-bn-constructor.cjs 在原测试导入时安装观察器，避免提前导入影响 ts-jest 首个编译入口；构造及方法均调用真实实现一次，内部嵌套调用不重复记入外部轨迹。记录构造/toString/toNumber/toArray/words 共 92 次边界调用，以及每次原 matcher 的实际输入。错误保留类型和完整消息，number 用 IEEE-754 原始位模式无损记录，数组递归保留元素类型与顺序。
- Java BigNumberConstructorTest 保留全部原用例，通过 BigNumberObservation 记录真实调用和断言实参。仅在 test 范围使用父工程已管理且缓存已有的 Jackson 3；生产 SDK 不增加该依赖。Jest toThrow(Error) 保留消息精确匹配，未指定消息的 toThrow 保留任意错误语义；实际对照额外比较类型和完整消息。
- bn-constructor-parity.py 复用 audit-tests.py compare；按固定原文件检查 28 用例、74 位置、52 次断言和 92 次调用。manifest 保存版本、命令及原始报告哈希；原始两端记录分别为 ts.bn.calls.jsonl / java.bn.calls.jsonl，逐项结果为 bn-parity-results.json。summary 按文件给出数量，formalAcceptance 始终为 false。
- `python3 test-hex-parity.py <累计批次目录> -v` 同时执行 Hex 的 7 项和 BigNumber 的 7 项工具自测。新增反例覆盖循环样本遗漏/重复、API 调用缺失、输入位模式变化、实际断言值变化、异常消息变化；不能充抵 SDK 用例。

BigNumber 构造原文件按行为完成 12 组 RED→GREEN；16 个原用例由此前实现直接满足，全部保留。该局部入口累计为 36 个原用例、71 次实际断言、101 个 AST 位置；Java 另有 1 个工程基础测试。完整 BigNumber 的后续分项已验收；局部入口仍只代表 Hex 与构造两份原文件，不充抵其他文件的验收。

## 按顺序执行

1. 读取规则、feature_list.json、progress.md 和交接，运行 ./init.sh 与 node audit-api.cjs batches；选择依赖已完成的 nextItem 编码任务，只保持一个执行项 in-progress。
2. 阅读该项 sourceFiles、testFiles 和相关 fixture 全文，在同一任务内检查对应 API：已有映射复用，缺失设计先补齐；实际参数、状态、异常及平台差异明确后再写该行为的代码。无需等待无关 API 组或全量 P0。
3. 登记本项 test-map 的完整原文件、断言/循环样本；补齐本项所需真实输入重放和两端采集，使用反例验证。任务首次完成时必须留下可复跑命令，不能把拟定入口当成已经可运行。
4. 逐行为先运行原 TS，再写 Java RED、实现 GREEN；每次只推进一个行为，不批量生成空壳或整套尚未验证的测试。
5. 本项全部 testFiles 的原测试、Java 对应测试和实际输入/结果对照通过；执行 ./verify.sh bsv-test，并累计回归此前已完成项。测试注册数从冻结清单派生，断言和动态样本另按真实轨迹核对。
6. 对 apiCompletionFiles 收口全部 API/导出能力，保存命令、源码/工具/Java 版本、Jest/Surefire 原始报告、输入及实际比较结果。全部独立验收条件满足后才将任务 done，更新嵌入 API 复核状态并提交。
7. 全部任务完成后，汇总 API、原测试、输入重放、采集与完整性反例门禁；migration-map 是最终完整模块验收前的收口，不再作为全部生产编码的开工门禁。
8. migration-core-modules 执行六模块联合累计验收，migration-sdk-acceptance 完成独立 SDK 的最终全量验证、JAR 和说明。正式 API check 和 audit-tests.py check 始终保留完整范围，局部 compare 的 formalAcceptance=false。

上述各步骤的权威清单、依赖与验收条件为 feature_list.json 的 implementationPolicy。API/行为契约仍由 API 文档与 api-map.json 维护，用例/断言记录只在 test-map.json；本计划不重复定义。

migration-test-mapping、migration-input-replay、migration-result-capture、migration-evidence-gate 改为随编码增量落实后的全量收口门禁。某编码任务缺少自己所需的重放/采集时，在该任务内补齐并验证；不以通用事项未 done 拦住所有研发，也不允许缺证据的编码任务通过。

报告在每次执行后复制到独立批次目录，绑定当时源码、Java 提交/工作树和原始报告哈希。clean test 或 Java 修改后重新采集相关验收，不修改旧报告版本号；仅任务文档变更不要求重跑无关 SDK 测试。

## 编码任务与 API 前检

feature_list.json 的 features 是执行及最终验收队列：28 个编码任务，另保留环境/范围/基线与全量收口门禁。apiBatches 的 21 项是嵌入复核清单，不单独排期，不作为 nextItem；其中 values、hash-random、curve 的 816 项映射可直接复用。

任务按功能组划分：完整大整数与模运算、哈希与随机源、曲线、字节编解码、密钥签名、对称加密、兼容算法、脚本模型/模板/执行/规范向量、交易基础/证明/广播/完整流程/验证、钱包协议/密钥/Wire/JSON/宿主/客户端，以及认证证书/会话/传输。完整原测试文件不拆成零散方法任务；Script、Transaction 等大原文件有大量参数向量，保留全部样本，不按用例数量切碎。

每个编码任务字段的含义：

| 字段 | 作用与独立验收边界 |
| --- | --- |
| sourceFiles | 当前任务实现和 API 前检范围；早期实现共享类必要行为时显式列入，允许跨任务重用 |
| apiCompletionFiles | 完整源文件的 API 最终收口责任，133 个文件恰好分配一次；done 时须完整实现，不只是设计映射 |
| testFiles | 本项完整原测试文件，133 文件/5329 用例恰好分配一次；测试数量从 module-tests.json 派生 |
| regressionTestFiles | 指定额外累计回归的原文件；此前已完成项也须回归，不重复计作本项新增用例 |
| fixtureFiles | 本项读取的原向量及辅助资料，可以共享；26 个辅助文件合起来不能漏 |
| apiBatchRefs | 由 sourceFiles 对应的嵌入 API 复核组；组未全做完时，可先对已复核且依赖闭合的行为 TDD |
| dependencies | 必须完成的实施前置；不得用与本项无关的全部设计门禁阻塞开工 |
| deliverable / acceptanceFocus | 当前功能组的交付结果和关键场景，结合公共 steps/acceptanceCriteria 验收 |
| evidence | 实际执行命令、独立证据目录、版本/报告摘要及比较结果；仅写“已完成”或只有映射不足以验收 |

## 阶段交付

每次处理一个行为：写 Java 失败测试、确认 RED、实现最小功能、取得 GREEN、核对 TS/Java 实际结果。每个完整模块及联合阶段完成时，执行[测试契约](测试迁移契约-20260920-101559.md)的累计门禁；范围内未映射、未执行、跳过、未比较、未解决差异均必须为零。

P1 和 P2 均使用默认六模块全范围检查；若显式传 `--module`，必须包含全部六模块，检查器会拒绝缺少依赖的组合。只允许整模块选择，依赖模块必须纳入累计验收。每个功能项完成后分别提交所属仓库；阶段状态只在 [feature_list.json](../feature_list.json) 维护。

只读对照旧 Java 行为与 TS 行为时若发现冲突，保留最小输入和两端结果，在新 SDK 的接口与测试契约内解决；不得修改其他工程或放宽测试预期掩盖差异。
