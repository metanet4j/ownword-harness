# TypeScript → Java 整模块迁移计划

## 范围与依据

按 metanet4j-sdk 的使用情况选择完整模块，一旦选中就迁移模块全部功能和测试，不按业务用到的方法裁剪。范围定义、TDD 与结果一致性统一见[测试迁移契约](测试迁移契约-20260920-101559.md)；模块清单见 [module-scope.json](../module-scope.json)，固定上游和分支见 [workspace.json](../workspace.json)。产品和协议事实引用[核心认知](../../../system-design/spec/核心认知.md)。

当前确定纳入 `primitives`、`compat`、`script`、`transaction` 四个完整顶层模块，包含全部子目录。Schnorr、Secp256r1、AES-GCM、PushDrop、RPuzzle、BEEF、MerklePath、广播与链追踪等位于这些模块内的能力均在范围内，即使现有 Java 业务没有直接调用。其余模块仍待依赖审查，不能视作已经排除；根测试目录两个文件已按被测接口归属 overlay-tools，选中该模块时自动纳入。

## Java 目标工程

用户指定任务根目录下的同级独立工程 `metanet4j-bsv-sdk`，与既有 SDK 分别管理 Git 和 Maven。四个完整模块暂在同一个 JAR 内按 `com.metanet4j.bsv` 下的包组织，包与测试向量目录见[工程说明](../metanet4j-bsv-sdk/README.md)。工程继承现有父 POM，但不依赖 base/sdk，避免业务向底层的反向依赖。业务工程接入在 P3 实施；具体公开 API 与兼容策略仍属于 P0。

初始化事项 `migration-core-project` 验收 Java 25、JUnit、UTF-8 向量资源、独立 Git 基线和统一验证入口，基础测试不计入上游复刻用例。

## 阶段顺序

| 阶段 / 事项 | 完整交付与验收范围 |
| --- | --- |
| P0 / `migration-map` | 完成四个整模块的 API/行为与逐用例/断言映射，复核跨目录用例和依赖，收敛 Java 公开类型及兼容策略；补齐真实 TS/Java 结果采集适配器。现有检查器可以核对证据，但不会替代采集或自动填充映射 |
| P1 / `migration-core-modules` | 完整迁移并联合验收 `primitives`、`script`、`transaction`。每个模块所有功能与测试都必须闭合；内部按基础数据与密码学、脚本、交易等依赖顺序逐行为 TDD，内部里程碑不能被标记为整模块完成 |
| P2 / `migration-compat-module` | 完整迁移 `compat`，包括 HD、Mnemonic、BSM、ECIES、Utxo 与全部辅助能力；累计验收四个模块全部测试 |
| P3 / `migration-sdk-adapters` | 将 metanet4j-sdk 的 BAP/AIP、BSocial、Ordinals、Sigma、远程签名及受影响 base 帮助类接到已验收模块；累计执行全部 TS/Java 对照及独立登记的 Java 业务回归 |
| P4 / `migration-downstream` | 接入 component 受影响模块，核对公开 API 兼容和旧依赖去向；按 parent → bsv-sdk → base → sdk → component 验证，执行完整模块和业务回归的最终累计验收 |

`module-tests.json` 记录从上游编译输出提取的静态运行时依赖：`primitives → script`、`script → primitives/transaction`、`transaction → primitives/script`，因此三个模块采用联合验收。`compat` 依赖上述模块，随后整模块验收。类型引用、动态加载、测试辅助依赖仍需 P0 人工复核，不能将静态依赖图当作所有依赖已经确认。

## 文件和脚本的职责

本计划是执行顺序的入口；比较规则引用[测试契约](测试迁移契约-20260920-101559.md)，清点与证据字段引用[检查器说明](测试完整性脚本-20260920-104440.md)，不在多份文档重新定义。以下命令均在任务根目录执行。

| 文件或入口 | 输入 → 输出及用途 |
| --- | --- |
| `workspace.json`、`env.sh`、`mvn.sh`、`pnpm.sh` | 固定仓库/工具配置 → 当前进程的隔离环境；Java/TS 操作统一经过对应入口 |
| `init.sh` | 仓库、源码、清单、工具 → 自检结果；不安装、不构建、不执行功能测试 |
| `inventory-tests.py` → `upstream-tests.json` | 全 SDK 静态测试文件与 Jest 默认发现结果 → 文件、辅助向量和排除项清单；重建会写文件，按需执行并审查差异 |
| `module-scope.json` | 人工确认的完整模块与跨目录测试归属；pending 必须逐项解决 |
| `audit-tests.py inventory` → `collect-cases.cjs` → `module-tests.json` 候选文件 | 选定完整模块 → 注册用例、静态依赖、源码复核位置和文件校验值；清点不执行测试体或 hooks |
| `test-map.json` | 上游 ID → Java 测试入口、断言/样本标识及源码位置复核记录；映射本身不表示实际执行通过 |
| `verify.sh` | 构建或测试命令 → `.cache/evidence/` 日志和报告摘要；具体分项见下文 |
| `audit-tests.py revision` | 全部已登记 Java 仓库的提交及工作树文件 → `javaRevision`，由采集过程记录并在验收时重新核对 |
| `audit-tests.py check` | 冻结清单、映射、真实 Jest/Surefire 报告和逐断言结果 → PASS/FAIL；先重新清点上游，不代替运行测试或采集结果 |
| `audit-tests.py compare`、`test-audit.test.cjs` | 调试证据或专用测试数据 → 检查器验证；不充抵 SDK 迁移测试，也不代替正式 `check` |
| `AGENTS.md`、`README.md` | 工作规则与常用命令入口 |
| `feature_list.json`、`progress.md`、`session-handoff.md` | 阶段状态与证据、当前进展、下一次执行入口；验收后更新并提交 |

现有 `verify.sh` 分项：`bsv-test` 执行新工程 `clean test` 并核对 Surefire 实际用例；`bsv-build` 先完成同样的测试，再安装 JAR；`java-build` 按五仓顺序构建并跳过测试执行；`java-smoke` 只跑已指定的业务 SDK 离线回归；`ts-build` 构建上游；`ts-smoke` 只跑已指定的九个文件。上述冒烟不能代替完整模块验收。

**尚待 P0 实现：完整模块 TS 测试运行入口、实际输入记录/重放、TS 与 Java 逐断言采集及报告关联。** 当前没有可直接生成 SDK 真实 `parity-results.json` 的完整流程；不能将规划中的入口写成已可用命令。具体实现文件及命令确定后更新本节和 README。

## 按顺序执行

| 步骤 / 阶段 | 执行动作与脚本 | 必须产出及进入下一步的条件 |
| --- | --- | --- |
| 1 / 每次开工 | 读取规则、状态和本计划，运行 `./init.sh`，核对各仓库 `git status` | 环境检查通过；本次范围、未完成项和既有无关修改明确。已有正常环境不重复安装 |
| 2 / P0 范围审查 | 对照真实业务调用、TS 完整模块源码、`module-scope.json` 和 `upstream-tests.json`；必要时重跑 `inventory-tests.py` | 全部 API/行为、类型/异常映射、依赖闭包和跨目录测试归属有记录；保留 manual、条件注册等需处理项，不按方法裁剪模块 |
| 3 / P0 清点与映射 | 用 `audit-tests.py inventory --output .cache/evidence/module-tests.candidate.json` 生成候选清单；审查与冻结清单的差异，再登记 `test-map.json` | 每个上游 ID、参数行、辅助断言、循环/属性样本均有对应方案；复核 AST 位置并记录依据。Java 入口此时可为拟定名称，创建测试后必须按真实报告校准 |
| 4 / P0 运行与采集准备 | 经 `pnpm.sh` 执行完整模块 TS 参考测试，补齐输入重放和两端采集；修改检查器时运行 `node test-audit.test.cjs` | 可重现的 TS 基线、采集器自身测试与命令说明；真实结果能绑定源码、输入、用例、断言及原始报告。接口边界满足 tdd 技能要求；上游失败保留证据并解决 |
| 5 / P1、P2 单行为 TDD | 选择一个上游行为并运行参考测试；经 `mvn.sh ... clean test -Dtest=...` 执行对应 Java RED，再实现到 GREEN，回归受影响用例 | 因目标行为缺失产生的失败证据、通过报告和同输入实际结果。逐行为推进，不先批量生成全部 Java 测试 |
| 6 / P1、P2 行为核对 | 核对该行为全部向量/断言的实际结果，校准映射及源码复核记录，提交完成的功能项；继续下一个行为 | 输入一致、原断言通过、两端实际结果一致；单行为通过不能标记完整模块完成。未完成整个阶段时正式 `check` 仍会失败 |
| 7 / 完整模块累计验收 | 通过第 4 步落实的入口执行本阶段全部 TS 测试；执行 `./verify.sh bsv-test`；把本次所有报告和采集结果传给 `audit-tests.py check` | 按测试契约和下文“阶段交付”验收；全部 API 已核对，遗漏/未执行/跳过/未比较/差异为零，才可完成阶段 |
| 8 / P3、P4 业务接入与收工 | `bsv-build` 安装已验收工程，按依赖顺序接入；执行完整模块累计测试与受影响业务回归，记录独立结果，再更新状态并分仓提交 | 业务及模块验收证据齐全。`java-build` 只证明编译；`java-smoke` 的三个用例不能代替全部受影响业务回归 |

第 2 步的 API/行为及兼容映射形成带时间戳的任务设计文档，并从本计划引用；逐用例/断言及源码复核记录保存在 `test-map.json`，避免同一映射维护两份。涉及公共接口变更时按工作区架构规则处理，避免 `base → sdk → base` 环。

P0 完成要求第 2–4 步产物齐全、范围和依赖审查完成，并提供真实执行与采集基础设施验证证据，才能把 `scopeReview` 设为 reviewed。P0 不要求尚未实现的 Java 模块通过最终 `check`，也不能把拟定映射、采集器自测或预期失败计为 SDK 用例通过。

## 单行为执行示例

固定上游 `src/primitives/__tests/Hash.test.ts` 的 `Hash → should support sha256` 注册一个用例，辅助函数实际对三个向量各执行一次整段输入和一次分段输入，共六次摘要断言。

按步骤 3 登记一个上游 ID、三个向量和六个断言标识；步骤 4/5 实际运行 TS 并记录六次结果。为 Java 创建对应测试，观察 RED，完成最小实现后执行 GREEN；步骤 6 对照六次输入和实际摘要，任何一次缺失或不同都保持未完成。`abc` 的固定预期为 `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`；Java 预期从上游向量取得，不能调用被测实现生成。

该示例说明执行要求，当前尚未完成 Java 功能迁移。具体 Java 测试入口在 P0 确定，不能把示例名称或预期值作为实际运行证据。

## 阶段交付

每次处理一个行为：写 Java 失败测试、确认 RED、实现最小功能、取得 GREEN、核对 TS/Java 实际结果。每个完整模块及联合阶段完成时，执行[测试契约](测试迁移契约-20260920-101559.md)的累计门禁；范围内未映射、未执行、跳过、未比较、未解决差异均必须为零。

P1 的检查器选择 `--module primitives --module script --module transaction`，P2 起检查全部四个模块。只允许整模块选择，依赖模块必须纳入累计验收。每个功能项完成后分别提交所属仓库；阶段状态只在 [feature_list.json](../feature_list.json) 维护。

旧 Java 行为与 TS 行为冲突时保留最小输入和两端结果，解决兼容策略后再完成对应行为；不得修改测试预期掩盖差异。
