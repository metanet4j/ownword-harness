# 整模块测试完整性检查

## 检查入口

执行顺序与各脚本分工统一见[模块迁移计划](模块迁移计划-20260920-103547.md)；本文定义检查器命令、证据格式和能力边界。在任务目录运行：

```bash
# 检查器自身的正常与反例测试，不属于 SDK 移植测试。
node test-audit.test.cjs

# 生成候选清单；复核差异后才能更新版本管理中的 module-tests.json。
python3 audit-tests.py inventory --output .cache/evidence/module-tests.candidate.json

# 当前即可运行：重新清点固定上游，核对冻结清单和迁移证据；不完整返回 1。
python3 audit-tests.py check
```

`inventory` 加载上游自身 Jest 配置，递归清点选中模块全部测试，显式包含默认排除的 manual 文件。在 Jest 完成注册后读取 describe/test 树，展开 `each` 和注册阶段循环；按文件、完整名称路径及同名出现序号生成稳定 ID。清点专用环境清空 hooks 并跳过测试体，输出标记 `collectionOnly`，不会把清点记作测试执行通过。

`check` 每次重新清点固定且干净的上游，对比冻结清单内全部源码/测试/辅助文件的 SHA-256、模块范围、注册用例及 AST 位置。删掉冻结清单中的文件或用例会失败，不能通过同步减少 Java 映射骗过检查。

`compare` 只核对提供的清单与证据，供检查器自测和问题定位使用；不重新核对源码，不能代替迁移验收的 `check`。

## 证据核对

`test-map.json` 是逐用例 Java 映射和源码语义复核的版本化记录，当前为空，不能自动填成“已通过”。每个上游 ID 对应一个或多个不同的 Java 实际测试，禁止一个 Java 测试重复冒充多个上游用例。

验收时提供真实执行生成的 Jest JSON、Surefire XML 以及两端结果采集文件：

```bash
python3 audit-tests.py check \
  --ts-report .cache/evidence/ts-modules.json \
  --java-report metanet4j-bsv-sdk/target/surefire-reports/TEST-实际测试类.xml \
  --observations .cache/evidence/parity-results.json
```

以上报告路径为格式示例，目前尚未生成。多份报告重复传递对应参数。P1 与最终验收均使用默认六模块完整范围。只接受完整模块名，所选模块的依赖必须同时纳入，不能传函数、文件路径或用例名缩小范围。

检查器逐项核对：

1. 上游用例集合与 Java 映射集合完全相等，没有缺失、多余或重复映射。
2. Jest 实际报告包含全部文件、完整名称和参数行；总数相同但漏跑/重复另一用例仍失败。skip/todo/only、失败和未执行均拒绝。
3. 每个映射的 Java 类/方法确实出现在 Surefire XML，失败、错误、跳过、重复记录以及汇总数矛盾均拒绝。额外 Java 业务回归不充抵上游映射。
4. 每个用例及每个映射断言均有两端结果；输入/前置状态校验值相等，结果在保留 JSON 类型、数组顺序和字节编码的表示下精确比较。
5. 上游版本、清单和原始报告的校验值与结果文件一致；缺少结果、旧报告混用或单字节变化均失败；`check` 重新计算当前 Java 源码摘要，拒绝旧版本的结果。
6. AST 标出的注册、断言、循环及条件位置均有显式复核记录；尚未完成范围审查不能通过最终 `check`。

完整 TS 参考基线使用 `./verify.sh ts-modules`；执行、资源和网络 fixture 规则见[TS 完整基线](TS完整基线-20260920-124400.md)。`compare-ts` 复用逐文件/完整名称/出现次数及原始状态核对，不要求尚未实现的 Java 映射；它不能替代正式 `check`。

## 数据格式

映射的单条结构如下；ID 必须取自清单，Java 名称必须与 Surefire 的 `classname`、`name` 一致。参数化 Java 测试需要登记每次调用的实际名称。

```json
{
  "upstreamCommit": "固定上游提交",
  "cases": [{
    "id": "上游用例 ID",
    "java": [{"className": "完整类名", "name": "实际测试方法名"}],
    "assertionIds": ["断言或循环数据行的唯一 ID"]
  }],
  "siteReviews": [{
    "id": "清单中的源码位置 ID",
    "status": "reviewed",
    "caseIds": ["对应上游用例 ID"],
    "note": "具体语义、未注册分支处理及循环/属性输入语料的复核依据"
  }]
}
```

结果文件包含 `upstreamCommit`、`javaRevision`（`python3 audit-tests.py revision` 输出的已登记 Java 仓库提交和工作树摘要，含 metanet4j-bsv-sdk）、`catalogSha256`、`tsReportSha256` 和 `javaReportSha256`（报告文件 SHA-256 列表）。`cases` 中每条包含 `id`、`inputSha256`、`tsInputSha256`、`javaInputSha256` 和 `ts`/`java` 两组断言结果，三份输入校验值必须相同。每条断言结果为 `{"id":"断言 ID","value":{"type":"hex","value":"0001"}}`；大整数使用十进制字符串，异常和语言类型适配按[测试契约](测试迁移契约-20260920-101559.md)登记。不能由手工编写或复制 TS 输出来冒充 Java 实际输出。

## 能证明的范围

脚本能检验文件、已注册用例、映射、执行记录和已登记结果的完整性。它不能独自证明任意程序的语义等价，也不能仅凭 Jest 注册列表知道测试体内每个循环/属性样本；AST 清单不是完整的控制流或别名分析。

因此还必须逐项复核全部 API、断言、条件注册、辅助断言及循环/属性语料，落实确定性输入重放和真实采集。未复核位置保持未完成，检查器不代写 reviewed 记录。真实 TS/Java 结果采集适配器尚待 P0 实现，当前检查器只负责验证输入证据。

## 验证证据

检查器按 TDD 实现，RED/GREEN 日志保存在 `.cache/evidence/audit-red-*.log` 和 `audit-green-*.log`。`node test-audit.test.cjs` 的 31 项自测通过，覆盖参数化/循环/manual 清点、缺失/重复映射、漏跑、跳过、旧报告、输入不一致、字节/异常/类型不一致和缺少断言结果。

依赖清点包含源文件的类型引用及测试辅助代码；新增反例先复现 script 漏掉 auth/wallet，再修正为 24/24 通过，证据为 `scope-dependency-red.log`、`scope-dependency-green.log`。模块范围结论与已选列表矛盾会拒绝清点；未逐项决定的候选模块仍阻止最终验收。总范围审核标记 scopeReview 继续等待 P0 联合验收。

真实模块的空 Java 映射必须使 `python3 audit-tests.py check` 失败；删除基准中的一个用例必须使重新清点核对失败。原始日志分别保存为 `audit-current.log`、`audit-tampered-catalog.log`。这些预期失败证明门禁能阻止虚报完成，不代表 SDK 迁移已有用例通过。
