# TypeScript → Java 单元测试迁移契约

## 范围与事实来源

用户要求：“java 的所有单元测试一比一复刻 typescript……每一个单元测试都必须通过。无遗漏，无错误。”本契约将该要求作为迁移验收门槛，沿用“只迁移 metanet4j-sdk 需要模块”的原始范围。

用户进一步要求：“每个用例运行测试的结果，和 ts sdk 中一致。另外分阶段按模块迁移。”每个用例必须有两端实际执行与结果对照证据。阶段顺序和执行清单见[模块迁移计划](模块迁移计划-20260920-103547.md)。

上游固定提交以 `../workspace.json` 为准。用户明确要求以完整模块为迁移单位：metanet4j-sdk 是否调用只用于决定选哪些模块；模块一经纳入，其全部功能、公开接口、子目录、辅助文件和测试全部迁移，不能继续按调用的方法裁剪。模块边界采用上游 `packages/sdk/src/` 顶层目录，范围由 [module-scope.json](../module-scope.json) 维护。

整模块依赖也须闭合；跨目录测试应归属到其覆盖模块。不能因未被业务调用、测试困难、资源需求、上游默认排除、失败或实现缺失，将已选模块中的任何能力或测试划出范围。尚未确定的模块/跨目录测试标记待审查，不能自动当作排除。

本次工程源码、Java 测试、POM 和配置仅落在 `metanet4j-bsv-sdk`；其他 Java 工程只读参考，业务适配及下游接入不属于本次交付。完整模块及测试要求不因工程范围收紧而缩减。

接口与测试边界覆盖入选模块全部能力。遇到上游内部实现断言或 Java 无对应接口，必须记录差异并解决接口映射，禁止无声删除断言。现有用例全部复刻也不自动证明全部 API 已迁移；完整模块的公开 API/行为清单仍需单独核对。

## 一比一的含义

- 每个上游文件、完整 suite/case 名和参数化数据行具有可追踪的唯一标识，关联至少一个明确的 Java 用例；不以总测试数相同代替逐项对应。
- 保留输入、fixture、已知向量、前置条件、正常/边界/异常场景及每一条断言的语义。语言专属类型、异常名称和异步机制通过明确的映射适配。
- 参数化、动态生成、snapshot 与属性测试需单独登记；保留生成器约束、seed/replay 信息和等价断言，不能折成一个弱化的成功用例。
- Java 预期值来自固定上游向量或经执行核对的参考结果，不由被测 Java 实现生成。
- 其他工程既有 Java 业务回归只作为准备阶段参考证据，本次不改写或接入这些测试。目标工程的基础测试独立登记，不冒充 TS 复刻用例；新增 Java 行为测试应有上游对应，Java 特有适配显式标明来源和理由。

## 逐用例运行结果一致

每个用例使用相同输入、fixture 和前置状态，分别执行固定版本 TS 与对应 Java 实现。记录原始测试状态，以及各断言观察到的返回值、序列化结果、异常、可见状态变化或调用行为；保留断言位置与实际执行次数。只比较 PASS/FAIL、Jest/Surefire 用例数，或者两个实现各自的往返成功，都不足以证明一致。

对照记录必须包含上游提交、Java 提交或未提交补丁摘要、模块/阶段、上游文件与完整用例名、参数行标识、Java 类与方法、输入及 fixture 校验值、断言标识、TS 实测值、Java 实测值、比较规则、差异及原始运行日志路径。同名用例和循环内多条断言须能区分；不得用后一次结果覆盖前一次。原始值与用于跨语言比较的表示同时保留。

| 结果类型 | 一致性规则 |
| --- | --- |
| 哈希、密钥、签名、密文、脚本、交易、preimage | 逐字节相等；可用无损 hex 表示字节，保留长度、前导零及字节序。上游直接断言的 hex/base64 字符串仍按字符串精确比较 |
| 大整数、金额、索引、长度 | 精确数值相等；跨语言记录使用无损表示，大整数不经 JavaScript Number 转换；协议字段宽度和符号另行保留 |
| 字符串、数组、对象 | 保留字符串大小写与 Unicode 内容、数组顺序、元素类型和字段值；区分缺失、undefined、null 与空值。仅消除预先登记的语言表示差异 |
| 异常与失败分支 | 相同输入触发相同语义的失败；异常类型显式映射，上游断言的消息/错误码/抛出时机保留原断言语义，禁止把所有异常统一视为通过 |
| 状态、副作用、异步结果 | 核对上游观察的状态变化、返回/拒绝结果、调用参数、次数及有意义的顺序；运行耗时不当作业务结果。性能/资源断言若在范围内，保留并单独验证其约束 |

涉及随机、时钟、网络模拟或属性生成的用例，先固定可控输入再比较：

- 随机密钥、nonce、IV 等使用相同测试熵或记录并重放的输入；两种语言仅使用相同 seed 并不保证得到相同数据。不得修改生产随机源来追求一致。
- 属性测试保留上游生成器约束和执行次数，同时导出实际生成的输入语料供 Java 重放，记录 seed、replay path、样本标识和收缩结果。已有 `utils.property.test.ts` 的至少 300 次约束必须保留。
- 随机源自身等无法要求两次独立运行输出字节相同的测试，必须保留原始随机测试，明确对照其原有行为断言，并补足可控输入的差分验证；未明确比较方式的用例保持待解决，不自动放宽成“两边都通过”。
- snapshot 保留上游快照及其来源；网络场景使用相同响应 fixture 和失败情形；禁止用真实资金或广播交易获取测试结果。

参考执行和采集适配器不得删改原始断言或改变生产行为。原始 TS 测试、对应 Java 测试和跨语言结果比较均须通过；TS 返回值不能被复制成 Java 的实际输出，也不能由 Java 计算自己的预期值。采集与比较工具必须用缺失结果、重复标识、单字节篡改、异常不符等反例证明能够拒绝错误。

用户明确授权的行为修复须按独立差异 ID 登记，不能声称该输入与 TS 一致，也不能扩大到其他方法或模块。当前授权和精确范围见 [WUA-ZERO-CAPACITY](完整模块与API映射-20260920-122800.md#api-writer-zero-capacity)；相关 Java 额外回归与上游 5329 用例分开计数，原始用例、断言和 TS 基线不删改。结果比较器只能精确识别已授权差异，未登记或超出范围的差异仍失败。

映射表、确定性输入和必要预期向量随代码版本管理；原始日志可留在任务证据目录，但必须能按记录的命令重新生成。缺少结果文件、用例未执行、断言未触达或比较失败均返回非零，不能产生通过报告。

## TDD 执行

遵循 [tdd 技能](../../../../.agents/skills/tdd/SKILL.md)：一次处理一个测试行为，先写 Java 测试并确认因目标行为缺失而失败（RED），再完成最小实现使其通过（GREEN），然后验证已完成用例仍通过。不得先批量生成全套测试再补实现。

盘点、读取上游测试、运行已有测试及建立映射不属于新增 Java 测试。当前环境阶段只执行这些准备工作；不能将其作为 Java RED/GREEN 证据。

## 必须满足的验收门禁

1. 固定上游提交与运行清单；比较静态发现、测试执行清单和 Java 映射，解释动态用例、配置排除、skip/todo、only 的每项差异。
2. 迁移范围内未映射、遗漏、重复冒充、未实现均为 0；每个参数化向量和每项断言均有对应。
3. 上游参考用例与 Java 对应测试全部通过，逐用例实际结果按本契约一致；失败、错误、跳过、禁用、todo、未执行、未比较、未解决差异均为 0。上游已 skip/todo 的用例仍需记录并解决，不得从分母静默移除。
4. Java 使用 `clean test`，按模块核对 Surefire XML 实际 testcases；不得用 `skipTests`、ignoreFailure、排除失败用例或仅 BUILD SUCCESS 通过验收。
5. 保存固定版本、逐项映射、RED/GREEN 命令及结果、最终报告、fixture 校验信息。断言或测试数量变更必须说明原因；不得为绿色结果放宽预期。
6. 上游自身有错误、冲突或无法稳定复现时，保留失败证据，单列待解决事项；未关闭不得声明迁移完成。
7. 每阶段验收覆盖本阶段全部用例，并重跑此前已完成模块的测试和结果比较。跨模块用例必须明确归属与依赖；存在待后续阶段完成的必需用例时，相关模块不得标记完成，应调整顺序或合并验收阶段。

阶段报告分别列出范围内用例数、两端执行/通过数、已比较/一致数、未映射/遗漏/跳过/差异数、断言与参数向量核对结果及证据路径。范围可以包含尚未迁移的后续模块，但不得据此宣称整体通过。所有阶段完成后，按最终范围执行一次累计验收，逐项核对全量映射。

这些门禁用于提供可核验的测试完整性证据；在实际执行与逐项审核之前，不声明“全部通过”或“无遗漏”。

## 可执行检查

[测试完整性脚本说明](测试完整性脚本-20260920-104440.md)定义 `audit-tests.py` 的清点、冻结清单核对、用例映射、Jest/Surefire 执行记录及逐断言结果比较入口。`check` 必须重新清点固定上游；不能只对人工维护的清单或总数作比较。脚本自测通过仅代表检查器工作，不能计入 SDK 迁移测试通过数。
