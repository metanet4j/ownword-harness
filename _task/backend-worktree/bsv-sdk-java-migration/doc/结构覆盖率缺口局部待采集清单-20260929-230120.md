## 4. 探针口径与已知差异

### chronicle-opcodes

- 入口：`Spend.constructor`（构造函数 Proxy 记录原入参）+ `Spend.validate`（记录是否通过）。
  每个用例 2 个样本；`OP_RIGHT slice fix` 用例 4 轮 API 调用，共 8 个样本。
- 构造入参口径与原 `spends.jsonl.gz` 向量字段一一对应（`lockingChunks` / `unlockingChunks`
  / `verifyFlags` / `isRelaxed`），两侧都按序列化结果比较，因此脚本字节、ASM 隐含在
  `lockingChunks` 与 `Spend.validate` 结果里。
- `Spend.validate` 只记布尔通过与抛错二值；异常身份与消息由断言轨迹（`toThrow`）比较，避免把
  跨语言异常措辞混进输入样本。
- 已核对：77 次 `validate` 调用（73 例 × 1 + 1 例 × 4）与冻结计划一致；74 个用例全部有样本。

### simplified-fetch-transport-additional

- 入口：`constructor`（baseUrl + 注入的 fetch mock 身份）+ `send`
  （真正交给注入 fetch 的 `url` / `method` / 小写化头列表 / body 描述 + send 结局）；
  6 个 `deserializeRequestPayload` 用例第 2 个样本是解析结果。
- 传输的 `fetchClient` 是生产类的 `public final` 字段：采集态通过构造时注入一层 `Recorder`
  包装（委托原 mock），原 mock 的身份、行为与调用次数不变；原断言
  `assertSame(fetch, fetch(transport))` 在采集态核对的是被包装的 mock。
- 请求头统一小写，两侧构造顺序一致（payload 头在前，随后 6 个 `x-bsv-auth-*`）。
- `send` 只在监听者缺失 / content-type 缺失这两条错误路径上不会触发 fetch，此时第一个样本字段
  按 TS 原值记为 `null`（与 TS 侧一致）。
