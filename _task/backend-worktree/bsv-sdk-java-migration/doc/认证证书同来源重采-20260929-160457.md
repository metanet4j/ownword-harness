## 任务级同来源对照

`python3 local-task-parity.py --task migration-impl-auth-certificates --local …（六项）--output .cache/evidence/auth-certificates-same-source-20260929` 产出 `task-parity.json`：50／50 例、128／128 条断言，`missingCases`、`missingAssertions`、`uncompared`、`extraJavaAssertions` 均为 0，`javaRevision=0a119349…`、`javaTargetCommit=1da225e`。汇总时逐用例核对输入摘要一致、两侧断言身份与顺序一致、实际断言与冻结计划一致，并复用 `audit-tests.py` 的 `compare_actuals` 比较实际值（Java 的 `null` 在 `void-completion-null-adapter-v1` 站点对应 TS 的 `undefined`）。

反例（`negative/`）：改写 `Certificate.test.ts:33:5` 的 Java 实际值被拒并报 `实际结果不一致`；只给一个局部时按冻结清单报出 35 个缺失用例并非零退出。

## 门禁改动

- `local-evidence-gate.py`：断言篡改原先固定改写第一条记录；语义规则站点（如 `validateCertificates` 的 `not.toThrow`）由专用规则先行拒绝，篡改走不到逐值比较。现按 `audit-tests.py` 的固定语义表跳过这些站点，取第一条真正经过比较的记录，拒绝原因必须是 `实际结果不一致`；此前通过的其他局部行为不变（keyderiver、http-wallet-json 复跑一致）。
- `local-task-parity.py`：新增 implementation-slice 任务级汇总入口，把登记的标准局部还原成带 TS 文件／用例名与 Java 注册身份的行，复用清点器的比较规则，并强制运行来源等于当前 Java 工作树、冻结用例恰好覆盖一次。改写实际值与缺少局部两类反例均被拒。

## 边界

本项 `taskAcceptance` 为局部任务级验收，`formalAcceptance=false`；六模块最终门禁仍要求当前源码下单次双侧全量输入、逐断言实例与条件分支证据（`python3 audit-tests.py check`、无过滤 `node audit-api.cjs check`）。除 wallet-keys 六文件与本项六文件外，其余 68 个局部仍绑定旧执行器或旧 Java 版本，须在最终单次全量运行中重采。
