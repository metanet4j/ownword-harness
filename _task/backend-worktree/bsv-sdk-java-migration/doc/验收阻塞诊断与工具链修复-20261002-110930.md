## 二、已定位并修复的六类问题

### 1. 五个 `replay-*.py` 转换器丢弃 `expected` 与 `kind`（403 条断言）

这五个转换器构造断言行时只取三个字段：

```python
'value': {'matcher': item['matcher'], 'negated': item['negated'], 'actual': item['actual']}
```

上游 `capture-parity.cjs` 正常记录了 `expected`，五个局部的 raw 轨迹也全部含该字段（203/203、79/79、62/62、40/40、19/19），字段在转换环节丢失。

| 局部 | 文件与行 | 条数 |
| --- | --- | --- |
| validation-helpers | `replay-validation-helpers.py:130` | 203 |
| wallet-error | `replay-wallet-error-inputs.py:122` | 79 |
| brc100-byte-encoding | `replay-brc100-inputs.py:125` | 62 |
| werr-constructors | `replay-werr-inputs.py:106` | 40 |
| json-byte-encoding | `replay-json-byte-inputs.py:108` | 19 |

修复：补 `'expected': item['expected']` 与 `'kind': 'assertion'`，与标准转换器 `emit-assertion-observations.py:112` 的产物形状对齐。

**修复效果（用各转换器自身 `assertions_for()` 重放 run-41 的 raw 轨迹）**：0/403 → 390/403。

### 2. `capture-parity.cjs` 对 `toThrow` 的 expected 未取类名（61 条）

`toThrow(WERR_INVALID_PARAMETER)` 传入的是类。`actual` 侧有专门处理，但 `expected` 落到通用分支 `canonical(args[0])`，`String(类)` 退化为整段 class 源码文本：

```
TS   expected = "class WERR_INVALID_PARAMETER extends Error {\n    constructor(parameter, mustBe) {..."
Java expected = "WERR_INVALID_PARAMETER"
```

同文件第 51 行的 `canonicalCallArg` 已按类名处理函数参数，`toBeInstanceOf` 也取了 `.name`，`toThrow` 是遗漏。

修复：`toThrow` 与 `toBeInstanceOf` 同走 `canonicalCallArg`。已验证该函数对非函数入参与 `canonical` 逐类型等价（字符串/数字/null/undefined/数组/对象），改动只影响类参数。

### 3. `ZERO_ARITY_MATCHERS` 漏收 `toThrow`

`toThrow`/`not.toThrow` 同样是零实参 matcher（只判定 actual 是否抛出），但不在集合内，导致两侧「无期望」记法不同时误报。已补入。

### 4. `matcher_semantics` 的形状守卫顺序缺陷

```python
if not all(isinstance(left.get(key), type(right.get(key))) for key in ('matcher', 'negated')):
    return False
if left['matcher'] != right['matcher'] or ...   # 此处可能 KeyError
```

类型一致但同为 `None` 时，下一行直接下标访问抛 `KeyError`。已改为先校验键存在且非 None。

### 5. `EMPTY_EXPECTATIONS` 缺第四种「无期望」记法

Java 采集器对 `not.toThrow` 以 `{"type":"null"}` 记「无期望」，而该集合只有 `[]`、`{"type":"undefined"}`、`{"type":"array","value":[]}` 三种。已补入。全仓 Java 侧使用该形态的共 5 条，其中 4 条属已登记缺口。

### 6. 跨语言断言记法登记（10 条）

八条异常类断言与两条 `toMatch` 断言：两侧 `actual` 逐字节相同，仅 `expected` 按固定约定不同（TS 基类 `Error` 或原消息 ↔ Java `SdkException`/`SdkTypeException`；Java 把原正则补成 `.*` 包裹）。已按既有 `void-completion-null-adapter-v1` 模式在 `SEMANTIC_CASES`、输入计划 `comparisonRules` 与 `compare_actuals` 三处同步登记。

**注意**：`cross-language-input-rules.json` 只作用于输入行（`audit-tests.py` 的 `normalize_input_rows`），不处理断言值；这十条登记在 `SEMANTIC_CASES`，未使用该表。
