# system-design 任务指南

本目录存放设计与任务文档，不修改业务代码。以下目录路径相对工作区根 `ownword`；状态文件相对本目录。

## 开工顺序

1. 定位任务目录 `_task/system-design`。
2. 完整阅读本文件。
3. 阅读 `feature_list.json`、`progress.md`；续接任务时再读 `session-handoff.md`。

未完成以上步骤，不得修改设计文档。

## 目录与预览

- 核心认知：`_task/system-design/spec/核心认知.md`，事实来源与 DRY 遵循根 AGENTS.md。
- PRD：`_task/system-design/spec/prd`，描述原型无法可靠表达的产品事实。
- 后端设计：`_task/system-design/spec/backend`；原型：`designs/own-word-prototype`，具体事项以 `feature_list.json` 的产出路径为准。
- 高保真原型必须使用设计系统，默认 `designs/react-spectrum-s2`；必须使用 `baoyu-design`，任一缺失则停止原型设计并反馈。
- 不读取 `_task/system-design/spec/draft`。

在工作区根目录运行 `python -m http.server 4311 --bind 127.0.0.1 --directory designs`，访问 `http://127.0.0.1:4311/<项目目录>/`。

## Git 提交

- 原型在对应 `designs/` 独立子仓库提交；任务文档在根仓库提交，根仓库忽略 `designs/*`。
- 原型提交必须带当前 PRD 版本，格式 `(PRD v0.1_${datetime})`；根仓库不限。
- 当前 PRD 版本及权威来源路径记入 `feature_list.json` 当前事项，提交前查该记录及来源；不明或冲突时先向用户确认，确认前禁止提交，不猜版本。

## 事实来源

- 设计文档记录当前事项的需求与实现方案，引用核心认知，不重复定义核心事实。
- `feature_list.json` 只记录事项范围、状态、依赖、完成证据及文档引用，不承载设计事实。
- `progress.md`、`session-handoff.md` 只记录过程与交接，不承载设计事实。

- 设计结论引用 `reference` 或其他明确证据；资料冲突与架构决策遵循根 AGENTS.md，先按事实来源优先级处理，无法消解时才请用户裁决。

## 工作规则

- 同时只允许一个 `in-progress` 事项。开始前先在 `feature_list.json` 写清目标、依赖、完成条件。
- 涉及现有系统时，结合设计文档、代码、日志、数据或最小实验取证。
- 未确认信息标为“待确认”，写明负责人或验证方式。禁止把假设写成事实。
- 修改范围限于当前事项。未经用户要求，不修改 `spec`、`reference`、`designs`、`backend` 或任何代码。

## 原型验证范围

- 原型作为产品文档，默认只验证本次改动：一个正常场景、一个相关边界场景，并查看受影响页面截图。
- 不默认运行全量回归、整套专项测试或穷举屏宽／语言／主题组合；不为小改动新增大批自动化用例。
- 用户明确要求扩大验证，或最小验证发现关联问题时，再扩大范围；扩大前说明原因，只检查相关部分。
- 交付时如实说明已验证内容与未验证范围，不把既有测试结果表述为本次通过。
- 此规则仅适用于原型迭代，不降低生产代码或真实服务的验证要求。

## 完成标准

设计事项标记 `done` 前必须满足，按实际产物适用，不缩减已明确的事项验收条件：

- 事实来源符合上文要求；PRD 含可验证验收标准，实现设计逐项映射；仅改原型时遵循原型验证范围，不补建未要求的 PRD 或实现设计。
- 阻塞性“待确认”已清零。
- 用户或指定人员已复核事实、范围、验收标准、实现映射和待确认项；证据写入 `feature_list.json` 与 `progress.md`。代理先完成产出与验证并交付审阅，人工复核前不得标记 `done`。

## 收工顺序

1. 更新 `feature_list.json` 状态与证据。
2. 更新 `progress.md` 的完成项、风险、决策、文件与验证结果。
3. 跨会话任务更新 `session-handoff.md`，写明唯一下一步。
