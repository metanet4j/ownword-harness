# ADR-001：统一 OwnWord 产品版本与跨端文档职责

> 日期：2026-11-17。**治理方向已获得用户确认**；目录、具体模型和 v0.4.0 基线仍为 needs-review，不等于版本发布审批。

## 背景

OwnWord 已有 v0.1.0 身份、v0.2.0 内容、v0.3.0 Artifact 与 v0.4.0 公开主页的产品/原型设计；正式前端、原型和多个 metanet4j 后端依赖来自**独立 Git 仓库**，有不同的真实实施及验收节奏。

用户希望文档成为后续开发指南，让前后端采用一致的领域语言，并明确表示**全部设计文档采用一个版本**。需要同时保留真实工程的依赖版本和未关闭的主网/扩展验收门禁。

## 决策

1. **OwnWord 只有一个产品目标版本**（例如 v0.4.0），PRD、Domain、Contracts、Frontend 和 Backend 实现设计均服务同一个目标。
2. 跨版本稳定事实只在 `核心认知.md` 定义。共享领域模型放 `domain/`，系统交互与测试放 `contracts/`，分端实现放 `frontend/` 和 `backend/`。
3. 模块设计审批、原型确认、代码实现、局部测试、真实钱包/主网验收采用**独立状态**，不另创五套产品语义化版本号，也不强制同时完工。
4. npm、Maven 和各仓库 Git Branch/Commit 是工程依赖与交付事实，**不强制跟随** OwnWord 产品版本。
5. 在 `versions/v0.4.0.yaml` 汇总文档、原型、前端和后端可核实的 Git SHA 与未关闭门禁。未批准时记为设计目标；正式发布必须锁定不可变的文档主仓和各交付仓库提交。
6. 目录 `README.md` 是稳定开发入口，历史设计文档与旧 PRD 保留；新独立 Markdown 仍按根仓库规则带时间戳，避免破坏旧链接。

## 结果与成本

收益：开发人员按一个产品版本找到对应领域语言、端口、前后端实现和 BDD；保留原型先行和多个组件分步实施的能力；历史通过 Git 回溯，无需在每次增量发布复制全部设计。

成本：版本清单必须有人维护，开发或发布审批时检查 API/领域变更影响；独立仓库需要精确提交 SHA 而不能仅记分支名。

## 验证与生效边界

- [前端 v0.2.0 验收报告](../../../../知识库/前端/ownword-v0.2.0/README.md)记录已验证和未通过的门禁。
- [领域设计](../domain/README.md)、[契约](../contracts/README.md)与两端实现指南尚待本轮人工评审；未经评审不建立新发布 Tag，不改 npm/Maven 版本。
