## 3. P1：计划完整性/验收口径问题

1. **规模数字错误**：计划第 1 节与 6.5 节写“31 个 pom.xml / component 31 模块”。实测总 25 个 pom（component 21 子模块 + 根 = 22，parent/base/sdk 各 1），与 6.1 节“25 个 pom”自相矛盾。
2. **P1 版本号门禁不完整**：`metanet4j-parent/pom.xml` 的 `<metanet4j.version>0.1.0</metanet4j.version>` 不在 `grep <version>0.1.0</version>` 统计内；只改子模块 parent 版本会找不到 0.2.0 父 POM。P1 验收应同时校验属性值与父版本。84/82 的差异（2 处 sdk 本就是 0.2.0）也要写明，避免“84 处→0.2.0”歧义。
3. **`<java.version>11</java.version>` 覆盖共 13 处**（parent + 12 子模块），计划只说“每个子 pom 删除”，没有清单/门禁；漏一个就会把 `maven.compiler.release` 拉回 11（Boot 4 最低 17）。
4. **显式钉死清单不全**：除已列的 commons-lang3/jakarta.json/guava/bcprov/fastjson/ES，还有 lombok、hibernate-validator、slf4j、log4j、jackson、junit、lettuce、mysql-connector-java、commons-collections4、hutool、mapstruct。另 `fastjson` 实际是 **1.2.76**，不是计划写的 1.2.83。
5. **新坐标的版本来源没写**：store-sql 目前不写版本，靠 parent depMgmt（`com.baomidou:mybatis-plus-boot-starter`、`com.alibaba:druid-spring-boot-starter`）。只改模块 artifactId 而 parent 不改 artifactId/版本，会报 `version is missing`（Boot BOM 不管这两个坐标）。计划需明确 parent 属性 `mybatis-plus=3.5.17`、`druid=1.2.28` 及 depMgmt 条目改造。
6. **component-model 的 springfox 依赖替换没落地**：该模块直接声明 `io.springfox:springfox-swagger2`（无版本）；parent 换成 springdoc 后，模块不改就会 `version is missing`。另外 `@ApiModel`/`@ApiModelProperty` 不是简单换 import：注解名要换 `@Schema`，`value` 要换 `name`（`ListResult` 会编译失败）。
7. **jspecify 依赖假设错误**：sdk 依赖树无 spring-core（jsonrpc4j 的 spring 依赖是 optional），parent 也不带 spring；`org.jspecify:jspecify` 不会自动出现。计划“Spring 7 自带，不额外引依赖”对 sdk 不成立，需显式加 `org.jspecify:jspecify`（Boot BOM 管理 1.0.1）或换方案。
8. **B 档验证没有可执行的 compose/命令**：只写了 Mongo/ES 7.17.5/Kafka + 复用 zookeeper，但无镜像 tag、端口、Mongo 账号（yml 要 `bschema/bschema123`）、ES 安全开关、Kafka broker 接入 zookeeper 的方式和启动命令；本地也没有 mongo/es/kafka 镜像。计划应附 compose 文件或 docker run 清单 + 拉起/清理命令。
9. **编译插件事实与 Gate0 不符**：parent 显式 `maven-compiler-plugin:3.8.1`（compiler 3.8.1 会执行，而不是 Gate0 说的 3.15.0）。探针证明 3.8.1 + `maven.compiler.release=25` 可用，但计划要么显式升 3.15.0/删除版本、保留 annotationProcessorPaths，要么把这个偏差写清楚。
10. **`mvn -v` 说明有偏差**：不设 `JAVA_HOME` 时 Maven 3.9.16 跑在 JDK 8（sdkman current=8），必须以计划模板的 `JAVA_HOME=...25.0.4.1-tem` 调用；否则 `--release 25` 直接失败。
11. **D11 表述与现状不符**：4 仓库当前不在 `dev`，而在与 `dev` 同点的 `feature/java25`；§8 已解释，但决策记录 D11 写“4 仓库均 dev”。
12. **测试类数量 26 不准**：component-test `*Test*.java` 实为 24 个（含重复 CommonTest、非测试的 LocalTestUtxoProvider）。

## 4. 准入结论与条件

**结论：当前计划不准入直接实现。** 版本矩阵、环境准备、Cloud/Boot 兼容判断、坐标存在性这些主干工作可信；问题集中在 Boot 4 的破坏性变更清单不完整、遗留显式钉死未清理、迁移文件清单漏项、测试门禁定义失真。

建议按以下顺序修订后准入：

1. 把 §2 的 P0-1..P0-9 逐条写进计划的“改动清单”和“Gate”，每条给验收命令/断言。
2. 重做三份权威清单，并让 Gate 只认清单：
   - 25 个 pom + 13 处 `java.version` 覆盖 + 84 处版本字面量 + `metanet4j.version` 属性；
   - `grep -rln '^import javax\.'` 的 31 个文件（迁 30，标出 `AesCrypto` 不动）；
   - Boot 4 迁移的 6 个 import + 3 个文件 + Druid 包名。
3. 明确测试门禁：加 vintage 还是迁 Jupiter；mockito 版本同步；把“用例通过”改成“指定用例列表且实际执行数 > 0”。
4. 补齐 B 档 compose/命令与依赖安装顺序（parent `-N install` 前置）。
5. 先跑一次“只修 P0 依赖/包名、不改业务逻辑”的编译探针（parent→base→sdk→component），确认 P2/P3/P4 绿，再进入源码迁移。

修完上述 P0、P1 中的 1–7 条后，即可进入实现阶段。
