## 二、映射表口径（逐条核实，不猜）

每个局部的入口都从**它自己已跑通的单局部 Java 采集记录**里提取，三条来源互相印证：

1. `full-evidence-locals.json[局部].java_run_manifest` 的 `command`——当时真实的适配器调用
   （`--replay` / `--plan` / `--corpus` / `--report` 实参）；
2. 该适配器源码 java 分支里的 `-Dmigration.*` 与自有 env 赋值（入口名 + 取值表达式）；
3. 取值表达式按上面的实参解析成绝对路径或 `{runDir}` 占位符。

逐条核实后才写入条目，任一不成立即记 `unresolved`：

- **属性名确实被该局部 Java 源码读取**（`System.getProperty("<名>")`；本轮同时修掉
  `java_property_replays()` 正则漏连字符（`migration.origin-header.corpus`）的报表缺口）；
- **引用文件存在**（语料／计划／断言索引）；
- **登记的单局部 `java-inputs.jsonl` 覆盖该局部计划的全部用例**（即该入口当年真的跑通过）；
- **语料内 sampleId 与本轮计划逐项相同**（重放会把语料 sampleId 原样写成 Java 输入行）——
  已加进 `serial_plan()` 的运行期前置校验，不符即在 Maven 之前中止。

结果：**36 个局部／736 例**接通，2 个局部／7 例列明原因未接通（见第五节）。

其中 `utils.test.ts` 的 9 个局部共用同一个 `migration.utils.corpus`，而一个属性只能取一个值 →
全量阶段把这 8 份冻结语料拼成一份（第 9 个 `byte-base58` 走自己的 `migration.byte.utils.plan`）。
拼接前提已核实并在运行期强制：`UtilsInputReplay` 按 `javaMethod` 分组消费，8 份语料的
`javaMethod` **互不重叠**（重叠即报错中止），拼后每个用例的样本仍唯一。

## 三、注入点改动（`run-full-java-capture.py`）

1. **A1 向量**：Maven 前 `env['MIGRATION_VECTOR_JAVA_INPUTS'] = <runDir>/java-vector-inputs.raw.jsonl`；
   Maven 后调 `java-vector-inputs.py`，失败计入 `problems`；报告新增 `vectorInputs`。
2. **wallet-wire 4 项 recipe（必须一起给，已写进注释）**：
   `-Dmigration.walletWire.plan=<计划>/replay-inputs.jsonl`、`-Dmigration.parity.largeArrays=true`、
   `MIGRATION_WALLET_WIRE_ASSERTION_INDEX=<计划>/assertion-index.json`、
   `MIGRATION_WALLET_WIRE_JAVA_LARGE_ACTUALS=<runDir>/java-large-actuals.jsonl`。
   只给 `largeArrays` 不给 `walletWire.plan`：raw 变小但见证不产出（`largeActual` 因 `PLAN == null`
   直接 return）；只给 `walletWire.plan` 不给 `largeArrays`：839 MB 轨迹复现。
3. **A2**：按映射表逐局部注入 `-Dmigration.*`（33 个）与自有 env（4 个）；`raw-convert` 局部
   （`validation-helpers` 147、`auth-fetch-property` 1、`utils-property` 3）在 Maven 后由

4. `EXCLUDED_TS_INPUT_ENVS` 仍**只含** `MIGRATION_HASH_PBKDF2_TS_INPUTS`；未改 SDK 源码。

### 3.1 `largeArrays` 的爆炸半径与「摘要还原」

`migration.parity.largeArrays` 是 JVM 级开关。实测（同一份 TS 断言轨迹对照）：

| 断言 | 最大字节数组 | 开开关后 |
| --- | --- | --- |
| `WalletWireIntegrationTest#preservesLargeTypedBeef` ×4 | 4 194 304 | 摘要（**与本轮 TS 一致，必需**） |
| `TransactionPerformanceTest#deepSourceGraph` | 186 101 | 摘要（**TS 是全量数组 → 会不一致**） |
| `PushDropTest#passesVariousTestVectors#37` | 70 000 | 摘要（同上，已实跑对照：70000 → 71） |
| `ProtoWalletNativeHashTest#nativeDigest…` | 65 536 | 不触发（要求严格大于） |

本轮 `ts-assertions.jsonl` 里只有 wallet-wire 那 4 条是摘要形态，其余都是全量值。

**修复**：`repair_digest_actuals()`（同一文件）在 `emit-assertion-observations.py` 之后、把 Java 最终
断言里被摘要化、而本轮 TS 记全量数组的节点**按 sha256 验证后**还原——只有 TS 数组按字节重算出的
length＋sha256 与 Java 摘要完全一致才替换（此时该数组就是 Java 记录器当时摘要的那串字节），
对不上就原样保留并记 `problems`。用 `full-run-14` 真实的 PushDrop 断言做过正／反向验证：
正向 `repairedCount=1`、还原结果与 TS 逐字段相同；篡改 sha256 后 `repairedCount=0` 且报问题。

### 3.2 顺带定位：`emit-assertion-observations.py` 曾被 OOM 杀死

`full-run-14` 的 `java-assertions.jsonl` 只有 **1036/56744** 行，原因是该脚本
`Path(raw).read_text().splitlines()` 读 800 MB 原始轨迹时被 OOM kill（`dmesg` 有对应记录：
`Killed process … (python3) anon-rss:5947096kB`，`java-capture-report.json` 里 `assertions.error`
是空字符串）。**wallet-wire recipe 同时解决这个问题**：4 条 189 MB 行摘要化后，
原始轨迹从 **800.2 MB 降到约 43 MB**（>1 MB 的行合计 773.2 MB，其中 757.5 MB 是 wallet-wire 的 4 条）。
