## 2. 关键判断：迁移可行，且不需要保留 bitcoinj

勘察确认了两件决定方案形态的事实：

**其一，业务侧完全不使用 bitcoinj 的联网能力。** `msg` 包只用 `Translate.toTx()`（5 处，把 `msg.protocol.Transaction` 包装成 `bitcoin.api.base.Tx` 供 BIP143 计算）和 `Message`（1 文件，仅作构造参数透传）。网络消息类、peer 连接、区块同步、广播协议在 main 与 test 中均为 0 引用。这是纯离线的构造 + 签名 + 序列化代码。

**其二，网络参数只用主网。** `MainNetParams.get()` 33 处（最高频静态调用），`TestNet3Params`/`RegTestParams` 在 main 中为 0，仅测试里出现 10 处用于地址编码断言。

因此新 SDK 缺失的 P2P 栈、`NetworkParameters`、coin 选择、钱包密钥存储，对本工程都不是阻塞项。

## 4. 阶段划分

原则：自底向上，一次一个仓库，每个阶段都以"该仓库单元测试全绿"为出口条件；跨仓库的回归放在最后。

### 阶段 0：基线冻结与依赖接线（无源码改动）

1. 在 boot4 工作区记录迁移前基线：四仓库 `clean test` 的逐模块执行数、集成测试执行数、关键 hex 向量。
2. 清理 `metanet4j-tx-validator` 的冗余 bitcoinj 声明（源码零引用，单独一步、可独立验证）。
3. 处理 `bitcoinj-legacy` 硬编码 1.0.4 与 `metanet4j-parent` 的 `bitcoinjsv.version` 属性。

出口：基线数字归档，代码零改动，全量测试仍绿。

### 阶段 1：metanet4j-base（3 文件，最小面）

改 `base/aip/AipHelper.java`、`base/bap/BapHelper.java` 与对应测试。AIP 消息签名是全仓最高风险点之一：它手工拼 `Bitcoin Signed Message` 格式并做公钥恢复，`EcKeyLiteExtend` 的注释明确记载上游 `ECKeyLite.signMessage` 有 bug 才自行实现。替换时必须用固定向量逐字节验证 `formatMessageBytesForSigning` + `recoverFromSignature` 的输出不变。

出口：base 单元测试全绿且执行数不低于基线；AIP 签名向量与迁移前逐字节一致。

### 阶段 2：metanet4j-sdk 的基础设施层

先做不涉及业务协议的四组：

1. **地址与密钥基础**：`address/AddressEnhance`、`PrivateKey`、`PublicKey`（WIF 前缀、`Net.MAINNET/TESTNET3` 解码）。
2. **脚本层**：`script/ScriptExtend`（见 §5 风险 1，改继承为组合）、`utils/ScriptHelper`。
3. **签名哈希**：`script/SigHashExtend` 改为调用 `TransactionSignature.formatBip143`。
4. **序列化与 bean**：`utils/TxHelperExtend`、`BobHelper`、`TxoHelper`、`utils/ReadUtils`。

出口：sdk 模块可编译；上述四组的定向测试全绿；`bitcoinSerialize` 等价物的 hex 与基线逐字节相同。

### 阶段 3：metanet4j-sdk 的交易组装与签名器

`signers/`（`TransactionExtend`、`OrdinalsTransactionSigner`、`RemoteTransactionSigner`、`ExtendForSignTransaction`）、`transcation/`（`TransactionBuilder`、`LockingScriptBuilder`、`UnSpendableDataLockBuilder`）、`input/`、`output/`。

本阶段处理最重的结构性改动：`TransactionSigner` 继承链改为委托；`getConnectedOutput()` 的隐式 UTXO 反查改为显式传入 prevOutput/prevValue。

出口：sdk 全部单元测试绿；`OrdTransactionBuilderContractTest` 等 Ordinals 定向测试绿。

### 阶段 4：metanet4j-sdk 的业务协议层

`bap/`（11 文件，含 `BapBase` 的 HD 派生链与 `BapProviderKeyBag`）、`sigma/`（4 文件）、`ordinals/`（4 文件）、`crypto/`（5 文件，含 `MasterPrivateKey`、`CryptoHelper`）、`remote/`（8 文件）、`utxo/`。

BAP 身份派生是全系统地址根：根私钥、支付账户、加密、ordinal 四类子密钥的派生路径必须逐一比对迁移前后的 `xprv`/`xpub` 与最终地址。

出口：sdk 全量单元测试绿（基线 203 例，且 bitcoinjsv 相关测试全部重新执行）；BAP 全部派生路径的地址与迁移前一致。

### 阶段 5：metanet4j-component

按依赖顺序：`component-common`（`BitcoinSchemaTransaction` 用 `correctlySpends`）→ `tx-filter` → `tx-convertor`（`TxBean`/`TxActor`）→ `component-tx`（`BschemaCustomTransactionSigner`）→ `component-bap`、`component-bsocial`、`component-test`、`store-mongo`。

出口：component 单元测试绿；`BapTestFixture`/`BsocialTestFixture` 生成的 fixture hex 与基线一致。

### 阶段 6：移除 bitcoinjsv 并做全量验收

1. 从 `metanet4j-parent` 删除 `bitcoinjsv.version`、`bitcoinj-base` 管理项与 `io.bitcoinsv.jcl` 5 项；从各模块删除 bitcoinj 依赖声明。
2. 确认 `io.bitcoinsv`、`com.madgag.spongycastle`、`com.lambdaworks:scrypt`、`com.squareup:okhttp` 不再出现在任何模块的依赖树中。
3. 全量验收：四仓库串行 `-Punit-coverage clean test jacoco:report jacoco:check`，再跑集成测试。

出口：全仓 `io.bitcoinsv.bitcoinjsv` 引用为 0；单元与集成执行数不低于基线；`verify-unit.py --mode accept --scope all` 通过。

## 5. 风险与受控措施

**风险 0 — 隔离仓库只读（review 实测发现的最高优先级阻塞）。** 主机根分区 `/dev/sdc` 在 `/` 挂载为 `ro`，`~/.m2/metanet4j`（488M 隔离仓库）位于该分区，Maven 无法 `install`，报 `Read-only file system`；boot4 上次验收也因此跳过了 `install`。
已实测：在只读仓库上用 `-o` 离线模式可完成 `test`（`metanet4j-base` 实测 20 例全绿、6.3 秒）。但 component 必须解析新产出的 sdk jar，只读仓库里只有 9-29/9-30 的旧产物，因此阶段 5/6 无法验收。
**措施**：胡先生 2026-10-03 裁决由其本人把 `/` 重新挂载为可写，沿用原 `~/.m2/metanet4j-settings.xml`，不做仓库搬迁。**开工前必须先验证** `mvn install` 能写入隔离仓库，否则只推进到阶段 4。

**风险 1 — `ScriptExtend` 等继承链不可延续。** 业务侧靠继承 bitcoinjsv 类型嵌入其内部结构：`ScriptExtend extends Script` 覆写 `getScriptSigWithSignature` / `getNumberOfBytesRequiredToSpend`（依赖 `getNumberOfSignaturesRequiredToSpend`、`SIG_SIZE`）、`TransactionExtend extends Transaction`、`SigHashExtend extends SigHash`、`ExtendForSignTransaction extends TransactionSigner.ProposedTransaction`、`EcKeyLiteExtend extends ECKeyLite`；`RedeemDataExtend` 还直读公有字段 `keys`/`redeemScript`。
新 SDK 的 `Script` 构造器私有、只能经 `fromBinary` 工厂创建，`isLockingScript()` 在基类直接抛异常，继承模式不可行。**措施**：这五个类全部改为组合或独立函数，判定逻辑（`isSentToOrdinals`、`isSentToMultiSig`、`isSentToAddress`、`isPayToScriptHash`）迁入自建的脚本识别器。

**风险 2 — BAP 的 HD 派生语义不对齐。** `DeterministicHierarchy.deriveChild(List<ChildNumber>, boolean, boolean, ChildNumber)` 是多步路径派生，BIP44 路径 `m/44'/236'/0'/0/i'` 叠加 BAP 私有布局；新 SDK 的 `HD.deriveChild(long)` 是单 index 步进，`KeyDeriver` 走的是 BRC-42/43 语义而非 BIP32 路径。**措施**：写路径适配层，逐条比对四类子密钥的 xprv/xpub 与最终地址；`HDUtils.parsePath/formatPath`（15 处）由自建工具承接。

**风险 3 — `getConnectedOutput()` 的隐式 UTXO 反查。** 该方法在 main 中被调用 21 处，是 bitcoinj 提供的"input → outpoint → 上游交易 → output"反查链，签名时用来取 prevValue。新 SDK 没有这个概念，UTXO 由外部携带。**措施**：6 个 signer/builder 类的调用点改为显式接收 prevOutput/prevValue；金额类型由 `Coin`（long satoshis）改为新 SDK 的 `Object`，并加 long 精度断言。

**风险 4 — 脚本反编译字符串是对外协议。** `ScriptOpCodes.getOpCodeName()` 的输出直接进入 Bob/Txo cell 渲染（`BobHelper.java:145,153`、`TxoHelper.java:75,79,118,122`）。若新 SDK 的 `OP.name()` 命名与旧库不一致，前端展示会变。
review 实测：新 SDK 的 `OP` 以 `OP_0`/`OP_1` 为主注册名（`OP.java:205,212` 分别注册 `OP_FALSE`/`OP_TRUE` 为别名），与 bitcoinjsv `getOpCodeName` 的返回一致，实际差异面比预估小。**措施**：阶段 2 仍做一次全 opcode 命名对照并固化为常量映射表，不依赖上游命名，但按低风险处理。

**风险 5 — hex fixture 需重新生成且必须逐字节一致。** `bitcoinSerialize()` 在 main 中 2 处、在 test 中 25 处，既是 fixture 的生产方式（`BapTestFixture`、`BsocialTestFixture`、Mongo/MySQL 集成测试），也是断言比对对象（`assertArrayEquals`）。**措施**：阶段 0 冻结全部相关 hex 基线；每个阶段结束时与基线逐字节比对，不一致即阻断，不接受"重新生成基线"。

**风险 6 — 金额精度。** 新 SDK 内部以 `double` 表示 satoshis（`Transaction.satoshisOrZero` 返回 `double`），旧 `Coin` 是 `long`。超过 2^53 satoshi（约 90 万 BSV）会失真。**措施**：迁移期在适配层用 long 承载金额，转入新 SDK 时断言取值范围；把该限制写入任务文档。

**风险 7 — `TxActor.isCoinBase` 无测试覆盖。** 唯一调用点在 `UtxoConvertor.java:29`，测试中 `TxActor` 零出现。**措施**：阶段 5 自建该判定时同步补测试，否则回归无法发现其退化。
