# JungleBus Java 25 实现计划

目标是将 `js-junglebus` 的完整已实现能力迁移为独立 Java 25 SDK，按阶段完成协议对照、编码、验证和提交。

## 1. 依据与范围

原仓库已完整 clone 到 `reference/js-junglebus`，准确提交、Git tree、版本和来源验证以[来源锁定清单](../../../reference/sources.lock.json)为准。当前包版本为 `0.4.4`，全部业务源码共四个文件、833 行。

| 本地依据 | 已核实内容 |
| --- | --- |
| [index.ts](../../../reference/js-junglebus/src/index.ts) | 客户端配置、12 个公开方法、HTTP 请求、Token 刷新、交易二进制补取 |
| [subscription.ts](../../../reference/js-junglebus/src/subscription.ts) | 三类通道、回调队列、暂停与恢复、当前高度、重新订阅及清理 |
| [interface.ts](../../../reference/js-junglebus/src/interface.ts) | 配置、交易、地址、区块头和控制消息类型 |
| [protobuf.ts](../../../reference/js-junglebus/src/protobuf.ts) | 两个业务 Protobuf 消息的字段编号与类型 |
| [yarn.lock](../../../reference/js-junglebus/yarn.lock) | 固定依赖包括 `centrifuge 3.0.1`、业务 `protobufjs 7.2.5`、`better-queue 3.8.12` |
| [LICENSE](../../../reference/js-junglebus/LICENSE) | 实际许可证为 Open BSV，与 package.json 的 MIT 标注不同 |

迁移覆盖 REST 查询、登录及匿名 Token、连接 Token 刷新、连接事件、区块交易／控制／Mempool 订阅、JSON 与 Protobuf、Lite Mode、交易缺失时补取、顺序处理、背压、重连与取消。覆盖所有公开方法、返回实体和可观察状态，不按现有业务调用裁剪。

`onPayment`、`PaymentRequest` 只有类型声明，没有执行路径，登记为上游保留能力，不凭声明增加支付流程。SDK 负责获取数据与报告事件；交易解析、Merkle 验证、数据库、业务回滚和业务幂等由调用方负责。将来接入 OwnWord 时遵循[核心认知](../../../_task/system-design/spec/核心认知.md)的 Indexer 与事实来源边界。

## 2. Java 实现方案

采用单个 Maven JAR，坐标 `com.metanet4j:metanet4j-junglebus`，包名 `com.metanet4j.junglebus`。工程独立放在本任务目录的 `metanet4j-junglebus/`，使用自己的 Git 仓库和 `feature/java25` 分支；根仓显式忽略工程源码，保存任务资料。

| 部分 | 方案与目的 |
| --- | --- |
| 工具链 | Java 25，`--release 25`，Maven；使用现有隔离工具链，不启用 preview 特性 |
| REST 与 WebSocket | JDK `HttpClient`、`WebSocket`，共用连接配置与 Token 状态 |
| JSON | 使用现有后端采用的 Jackson 系列，具体补丁版在 J01 锁定；保留服务端字段名 |
| Protobuf | 固定 `protoc` 与匹配的 `protobuf-java`；从业务字段定义生成消息，外层协议使用与 JS 基线相匹配的官方 schema |
| 模型 | 不可变 `record`；对外交易及证明保持小写 hex，内部消息使用字节数组或生成类型 |
| 异步 API | `CompletableFuture`；交易和状态处理器返回 `CompletionStage<Void>`，队列等待其完成 |
| 并发 | 每条订阅串行处理区块交易及控制消息，Mempool 使用独立串行队列；虚拟线程处理等待，定时器统一调度 |
| 生命周期 | 客户端和订阅支持 `AutoCloseable`；明确连接、订阅、队列、任务和调用方注入资源的所有权 |
| 测试 | JUnit、共享协议样本、本地 HTTP／WebSocket 服务；实现阶段选择最小的测试服务依赖 |

JSON 和 Protobuf 共用同一连接及订阅状态机，只替换编解码。WebSocket 外层是 Centrifugal 协议，publication 内层才是 JungleBus 业务消息；仅生成两个业务消息类不能完成连接。

当前官方 [centrifuge-java](https://github.com/centrifugal/centrifuge-java) 的资料及源码使用 Protobuf 和 OkHttp，版本兼容性也有约束。本计划以保留原 SDK 双格式为目标，采用 JDK WebSocket 实现本仓库实际需要的协议子集。J01 必须读取锁定的 `centrifuge 3.0.1` 依赖源码，清点本 SDK 实际依赖的连接、订阅、取消、发布暂停／恢复命令、Token 刷新、心跳、服务端 disconnect／unsubscribe 推送、错误码与重试规则，以及可恢复订阅的 epoch／offset／recovered 行为，再锁定外层 schema 和帧样本。自动恢复等委托给 JS 依赖的行为也在迁移范围内，不能仅按四个业务源码文件裁剪。官方 Java SDK作为行为对照，不同时引入第二套连接实现。

`uint32` 对外使用 `long` 并检查范围；`block_index`、控制消息 `transactions` 等 `uint64` 对外使用 `BigInteger`，避免有符号 `long` 和 JS Number 的精度损失。Protobuf 生成类型到业务模型的无符号转换必须有边界样本。未知状态码保留原数值，不因 enum 无匹配值丢弃消息。

## 3. API 与协议迁移清单

Java 方法使用 lowerCamelCase。异步失败通过 future 异常完成；`getLastError()` 提供诊断信息。错误包含 HTTP 状态或服务端错误码、通道及原因，不能把失败伪装成成功的空值。

| 上游 API | Java 对应 | 协议或职责 |
| --- | --- | --- |
| `Login` | `login` | POST `/v1/user/login`，请求为 username／password |
| `SetToken` | `setToken` | 更新共用 Token；返回或读取行为在 API 契约中明确 |
| `GetTokenFromSubscription` | `getTokenFromSubscription` | POST `/v1/user/subscription-token`，请求字段为 `id` |
| `GetLastError` | `getLastError` | 最近错误及明确的更新规则 |
| `Connect` | `connect` | 连接与握手，完成后才表示连接可用 |
| `Disconnect` | `disconnect` | 主动断开，停止自动重连；允许后续显式连接 |
| 客户端 `Subscribe` | `subscribe` | 缺 Token 时获取匿名 Token，自动连接并创建订阅；明确等待订阅确认的语义 |
| `GetTransaction` | `getTransaction` | GET `/v1/transaction/get/{txId}` |
| `GetBlockHeader` | `getBlockHeader` | GET `/v1/block_header/get/{heightOrHash}`；提供高度与哈希重载 |
| `GetBlockHeaders` | `getBlockHeaders` | GET `/v1/block_header/list/{heightOrHash}?limit={limit}`；上游注释最大值为 10000，服务端边界在 J01 验证 |
| `GetAddressTransactions` | `getAddressTransactions` | GET `/v1/address/get/{address}` |
| `GetAddressTransactionDetails` | `getAddressTransactionDetails` | GET `/v1/address/transactions/{address}`；源码声明与真实详情返回结构需样本验证 |
| 订阅 `Subscribe` | 订阅 `subscribe` | 重新启动订阅，避免重复通道和监听器 |
| `UnSubscribe` | `unsubscribe` | 取消全部所属通道，并清理相关任务 |
| `GetCurrentBlock` | `getCurrentBlock` | 保留服务端 BLOCK_DONE 报告高度的查询能力，恢复游标另行管理 |

普通 REST 查询使用 `token` 请求头，不擅自改成 `Authorization: Bearer`。刷新为 GET `/v1/user/refresh-token`，也使用 `token` 头。原始交易补取为 GET `/v1/transaction/get/{txId}/bin`；上游该路径未带 Token，是否需要鉴权在 J01 以部署样本确认。

WebSocket 路径为 `/connection/websocket`，Protobuf 模式增加 `?format=protobuf`。默认 JSON，默认根据输入 scheme 推断 TLS；解析主机、端口、http／https／ws／wss 时使用 `URI`，测试显式 `useSSL` 覆盖和无 scheme 输入。

| 用途 | 普通模式通道 | Lite Mode 通道 |
| --- | --- | --- |
| 区块交易 | `query:{subscriptionId}:{fromBlock}` | `lite:{subscriptionId}:{fromBlock}` |
| 控制 | `query:{subscriptionId}:control` | 同普通模式，仍是 `query` |
| Mempool | `query:{subscriptionId}:mempool` | `lite:{subscriptionId}:mempool` |

控制码保留 `WAITING=100`、`ERROR=101`、`PAUSED=102`、`BLOCK_DONE=200`、`REORG=300`。区块交易和非错误控制事件沿同一队列分发；控制 ERROR 进入错误处理器。REORG 在上游只作为事件传递，Java 保留通知能力，不能宣称已完成业务数据回滚。

交易的 Protobuf 字段严格保持：`id=1/string`、`block_hash=2/string`、`block_height=3/uint32`、`block_index=4/uint64`、`block_time=5/uint32`、`transaction=6/bytes`、`merkle_proof=7/bytes`。控制消息严格保持：`statusCode=1/uint32`、`status=2/string`、`message=3/string`、`block=4/uint32`、`transactions=5/uint64`。

JSON 订阅中的交易和证明由 base64 转 hex，Protobuf 的 bytes 转 hex；缺失证明返回空串。普通模式缺失交易正文时先获取 `/bin`，成功后调用业务处理器；Lite Mode 不补取。REST 返回字段的实际编码单独核对，不能套用订阅的转换规则。

## 4. 行为兼容与修正

以下是源码观察和拟采用的 Java 行为。J01 为每项建立可执行对照，记录有意差异，避免把修正称为逐字复制。

| 本地源码观察 | Java 处理方案与验收 |
| --- | --- |
| 登录和匿名 Token 请求遇到非 200 时写入 error，但仍返回 null | 异常完成 future；保留状态码，鉴权失败不继续订阅 |
| `Subscribe` 始终传入交易和 Mempool 包装函数，使底层建立调用方未请求的通道 | 需要区块交易或状态时，成对建立区块通道和控制通道；仅状态处理器也保留区块通道以驱动查询，内部处理事件而不补取正文或调用不存在的交易处理器。需要 Mempool 时建立 Mempool 通道；全部处理器缺失时报参数错误。任何进一步减少通道的方案须先取得服务端行为证据 |
| 包装函数未等待调用方异步回调；队列完成不必然代表业务处理完成 | 等待 `CompletionStage`，失败报告后停止该订阅的处理与游标推进，允许调用方从安全高度重启 |
| BLOCK_DONE 一到达便更新 currentBlock，发生在队列处理之前 | 区分服务端报告高度与安全重放起点。J01 定义游标计算及对外读取契约，覆盖未完成回调、失败、旧连接事件和 REORG。不能仅凭收到 BLOCK_DONE 或队列暂时为空提交进度；跨通道块边界未获证实前，降级为从原始 fromBlock 重放，并明确重复交付与带宽成本 |
| 队列超过 20000 才发布 pause，低于 10000 后按 2 秒检查恢复 | 保留高低水位和默认检查间隔；增加明确容量上限。区块溢出停止并报告，从安全游标恢复；Mempool 溢出明确报告无法保证历史补回，不静默丢弃 |
| pause／start 发布没有错误处理，取消订阅未清理局部暂停定时器 | 等待命令结果；失败走错误及恢复流程。取消后不再发送旧通道命令，所有定时任务可清理；已开始的业务回调不能保证撤回，其晚到完成不得推进新一代订阅的游标 |
| `/bin` 补取未检查 HTTP 状态 | 状态和正文解码成功后才交付，失败不将错误页转成交易 hex |
| 重连根据 currentBlock 替换高度通道；进度只保存在内存 | 按安全游标重新订阅，允许重复交付并向调用方说明幂等要求；进程重启由调用方提供持久化高度 |
| 地址详情方法声明 `Address[]`，与“包含交易正文及证明”的注释不足以共同确定契约 | 保留方法能力，使用实际响应样本确定详情 DTO，允许兼容新增字段 |

客户端状态至少区分未连接、连接中、已连接和已关闭；订阅状态至少区分未订阅、订阅中、已订阅、暂停、失败和已关闭。主动 disconnect 不自动重连，close 为终态；unsubscribe 可再次 subscribe。状态改变由单一串行控制入口管理，旧连接的延迟回调不能覆盖新连接状态。控制入口不能阻塞等待业务处理器，业务处理器调用 unsubscribe／disconnect／close 不得形成互相等待。

J01 明确取消完成的边界：取消成功完成后，不再启动该订阅旧一代的新回调；已开始回调可以结束，但其结果失效。旧队列释放并从安全起点恢复，明确协议取消失败／超时、业务回调永不完成以及 close 的处理规则，避免以等待业务回调完成作为取消的必要条件。关闭只清理 SDK 自有资源，不能关闭调用方注入的资源。

Mempool 与区块流之间不承诺统一顺序，断线恢复不承诺 exactly-once。恢复起始高度是否包含该块、BLOCK_DONE 与交易的跨通道顺序，必须在 J01 核对。服务端报告高度不能作为持久化提交点；J01 必须确定调用方读取安全重放起点的方式，覆盖进程重启。未经保证的跨通道顺序不能凭正常样本推断；无法证实块完成边界时使用原始 fromBlock，禁止使用“报告高度减一”等固定回退量宣称不会跳过未完成交易。

J01 先在 `reference` 之外建立 JS 隔离副本和测试驱动，用锁文件安装依赖，不修改原始参考源码。原仓库只有 Jest 配置及 fetch mock 初始化，没有实际测试文件，因此不能宣称“原测试已全部迁移”；用源码行为、固定样本和 JS／Java 输出对照建立基线。

进入 J02 的条件由迁移实施者逐项验收：

1. JS 隔离副本能运行；15 个方法、构造入口、配置、公开状态和新增安全重放起点读取方式均有明确 Java 签名、默认值、失败及完成语义。
2. 已读取固定 JS 依赖并完成外层协议清单；schema 的准确来源及摘要、直接／传递依赖版本、JSON／Protobuf 的命令及响应帧样本可追溯。特别核对 Protobuf 模式下 pause／start 的 application data 编码，不能将其误当作 ControlResponse。
3. 游标与生命周期规则明确：块边界不能证实时的原始 fromBlock 降级、失败后重启、取消期间的队列与回调、旧连接事件和 REORG 的进度处理均有反例用例。状态订阅保留查询驱动通道。
4. 已确定队列的计数和字节上限、高低水位、超限动作，以及请求／命令超时与重试规则。字节限制覆盖编码膨胀、待处理与在途消息、交易补取；流量控制不能阻塞心跳、取消及命令回复。默认值在契约中写明，J05 实际验证。
5. REST 结果的本地契约明确。缺少真实详情样本时保留已知字段及可读取的未知字段，不用假样本证明线上结构；订阅 base64 转 hex 与 REST 编码处理分别记录。

目标部署的协议版本、地址详情实际返回、REST 字节字段编码、`/bin` 鉴权、重放包含边界及服务端块完成保证属于线上待验项，负责人仍为迁移实施者。线上证据可以来自对应服务端源码、明确协议保证及真实只读调用；本地模拟验证实现行为，不能充当部署事实。缺少账号／订阅 ID 时可以按已确定的本地契约及保守降级继续 J02–J05，但 J06 必须将交付标为“本地基线验证通过，线上兼容待验”，不能宣称目标服务已验收。

## 6. 验证与完成条件

核心用例覆盖：URL／TLS、全部 REST 路径、登录及匿名 Token、刷新互斥、控制码、三类通道、双格式与 Lite、base64／hex、缺失交易及证明、整数边界、异步回调顺序、背压边界、断线重放、REORG 通知、错误与关闭清理。

外层协议另测：JSON 多消息换行、Protobuf varint 长度前缀、WebSocket 分片、请求 ID 与回复匹配、服务端推送、心跳以及超时清理。按[官方客户端协议](https://centrifugal.dev/docs/transports/client_protocol)理解 framing，再用固定 JS 基线确认实际兼容版本。
